## 1. Why This Is Needed

flash_base provides blocking erase/program operations. flash_data adds a fixed-size record journal in one reserved erase unit. Application code reserves Flash and performs these operations from main.

---

## 2. Scope and calling contract

Files: `src/flash.hpp`, `src/flash.cpp`. Supported families: **STM32F4/F7/G0**.
L0 is not implemented: its erased value and programming protocol differ from G0.

Call blocking Flash operations from the **main loop**, with SysTick running.
Do not call from interrupts or critical sections. The driver neither disables
nor enables interrupts. Do not access the destination range concurrently, execute
code being modified, or use an overlapping source buffer.

`System::GetTick()` supplies the waits through `System::WaitBits()`.

Readiness waits call `System::WaitBits()` directly. LOCK checks, error clearing
and completion cleanup are visible in the write/erase methods.
The shared `wait_operation()` waits for completion and checks Flash errors.

| Family | Timeout per hardware operation |
| --- | --- |
| F4/F7 | 50000 ms (50 s) |
| G0 | 1000 ms (1 s) |

These are the agreed [ST F4](https://raw.githubusercontent.com/STMicroelectronics/stm32f4xx-hal-driver/master/Src/stm32f4xx_hal_flash.c),
[F7](https://raw.githubusercontent.com/STMicroelectronics/stm32f7xx-hal-driver/master/Src/stm32f7xx_hal_flash.c)
and [G0](https://raw.githubusercontent.com/STMicroelectronics/stm32g0xx-hal-driver/master/Inc/stm32g0xx_hal_flash.h)
defaults. The timeout is restarted for each physical write, not for the complete buffer.

**Timing limitation:** reading from a busy Flash bank can stall instruction fetch,
including SysTick and its vector fetch. GetTick then does not measure real elapsed
time reliably. No routines are moved into RAM. A timeout does not cancel the
hardware operation: wait for `flash_base::ready()` before further Flash access.
CR cleanup is skipped while the controller is busy; the next operation replaces
old operation fields after readiness. For `flash_data`, repeat `SetUp()` after a
timeout before reading/resuming the log.

## 3. Sector map and banks

`flash_config.h` format 4 is generated by the drivers from the base's selected
device/mode map (the source erase maps remain format 3). GetFlashSector(index)
returns `{address, size, bank, number}` by value. The caller supplies a valid index
below FLASH_SECTOR_COUNT. erase_sector() checks its own index argument.
`number` is the hardware SNB/PNB selector, not the logical index.
For F429ZI 2 MiB, bank 2 starts at `0x08100000`, logical index 12, SNB selector 16.

Geometry is selected automatically from the records, without a family table:
uniform page size, sequential addresses and selectors within each bank, with
one or two banks in address order. Such maps use constants and multiplication,
not a stored per-page array. Each bank retains its own start address and first
hardware selector; bank sizes need not be equal, and gaps remain unmapped.
Other maps keep flash_sectors[] internally. Use GetFlashSector() for both forms:

```cpp
// After checking index < FLASH_SECTOR_COUNT:
const FlashSector page = GetFlashSector(index);
const uint32_t address = page.address;
```

STM32_FLASH_UNIFORM_PAGES is generated as 1/0, not a user setting. Uniform maps
do not declare flash_sectors[]: migrate direct indexing or range-for consumers
to GetFlashSector() and FLASH_SECTOR_COUNT. Update the drivers and the template
STM32-base_files/cmake/flash_config.h.in together, then refresh the cached template
and regenerate the project. Stale config format 3 is rejected explicitly.
Family-neutral geometry does not port hardware Flash operations beyond F4/F7/G0.

The default bank type follows `FLASH_DUAL_BANK`. `init()` does not change option
bytes. It checks an explicit argument against the map, the applicable hardware
mode bit on switchable devices, and rejects active bank swap with `InitError`.
Single-only and dual-only devices use their fixed mode. Check `init()` once
before direct operations; `flash_data::SetUp()` does this for the log.
Unlock/erase/write do not recheck the mode. Do not change bank mode or mapping
while using the initialized driver. `mass_erase()` accepts a bank mask: **1** = bank 1, **2** = bank 2,
**3** = both; absent banks and other masks return `Error`.

## 4. API and programming widths

```cpp
static SysInitStatus init(bank_type tb = /* generated mode */);
static SysStatus enable_access();
static bool ready();
static SysStatus erase_sector(uint32_t sector);
static SysStatus mass_erase(uint8_t bank);
template<typename T>
static SysStatus write(uint32_t addr, const T* data, uint32_t size = 1);
template<typename T>
static T read(uint32_t addr);
```

`init()` / `flash_data::SetUp()` return `SysInitStatus`. Unlock, program, erase,
and `write_data()` return `SysStatus`: `OK`, `Error`, `Timeout`; `write_data()`
also returns `NotInit` before a successful setup. Hardware error flags remain
available in `FLASH->SR` until the next operation or `clear_errors()`.
Only defined W1C completion/error flags are cleared, not reserved bits.

`enable_access()` checks the actual `CR.LOCK`, writes the two keys only when
locked, and verifies unlock. Already unlocked means `OK`. Direct write/erase
requires a successful `init()` followed by unlock; there is no software unlock flag.

`write<T>()` accepts element sizes 1/2/4/8 bytes. `size` is the element count.
The caller validates the source buffer, count multiplication/rounding overflow,
destination range and alignment. Direct write does not check these arguments or
walk the sector map. A zero element count returns `OK` without an operation.
`read<T>()` is a raw typed read: the caller supplies a valid, aligned address.
Hardware width and PSIZE are selected at compile time. G0 uses one physical
64-bit implementation; F4/F7 use 8/16/32-bit implementations.

| Family | Hardware programming | Destination alignment |
| --- | --- | --- |
| F4/F7 | 8/16/32-bit; 64-bit input is split into two separately checked 32-bit writes | 1/2/4 bytes respectively; 4 for 64-bit input |
| G0 | 64-bit, two consecutive 32-bit stores separated by ISB | 8 bytes |

F4/F7 assume **VDD 3–3.3 V, without external VPP**. Erase uses x32 parallelism;
x64 PSIZE is not used. The x64/VPP restriction is documented in
[RM0090, programming parallelism](https://www.st.com/resource/en/reference_manual/rm0090-stm32f4xx-reference-manual-stmicroelectronics.pdf).

G0 assembles each 64-bit value using `memcpy`, so the source need not be 8-byte
aligned. The last block is padded with `0xFF`; the caller must reserve and validate
the whole padded block. Padding cannot later be programmed as a separate
record. Entirely `0xFF` blocks are **not skipped**; programming them consumes ECC
state even though the readable data remain `0xFF`.

After every hardware write the driver waits and checks SR. Processing stops on
the first error. A 64-bit F4/F7 write can therefore fail after its first half;
programming a buffer is not atomic.

## 5. Cache maintenance

Before modifying Flash and after completion (including an error once ready),
the driver invalidates affected Flash cache contents:

- F7: only the affected Flash range in Cortex-M7 D-cache, rounded to 32-byte lines;
  Cortex-M7 I-cache and ART are reset when enabled.
- F4: Flash accelerator instruction/data caches are reset when enabled.
- G0: the Flash instruction cache is reset when enabled.

Mass erase covers the selected banks. SRAM D-cache is not globally cleaned or
invalidated. Cache enable state is preserved. Destination access during the
operation is forbidden, including from callbacks/interrupts.

## 6. flash_data: one sector, fixed-size records

```text
F4/F7: [ status byte ][ payload ] ...
G0:    [ commit: 8 bytes ][ invalid: 8 bytes ][ payload ][ padding ] ...
```

F4/F7 use a one-byte header; G0 uses a **16-byte header**. Physical marker values:

| Record state | F4/F7 status | G0 commit word | G0 invalidation word |
| --- | --- | --- | --- |
| Free | `FF` | `FFFFFFFFFFFFFFFF` | `FFFFFFFFFFFFFFFF` |
| Writing | `7F` | `00000000FFFFFFFF` | `FFFFFFFFFFFFFFFF` |
| Ready | `0F` | `0000000000000000` | `FFFFFFFFFFFFFFFF` |
| Invalidated | `00` | unchanged | `FFFFFFFF00000000` |

Any non-erased G0 invalidation word takes priority over the commit word.
`Data_Status` is the single definition of values used for programming, scanning
and API results; there are no separate marker constants. On G0, `DATA_WRITING`
and `DATA_OK` belong to the first word, and `DATA_NOT_VALID` to the second.
Determine the record state from both words. G0 enum values have changed to the
encoding above; use named enumerators in application code. F4/F7 values are unchanged.
`DATA_CORRUPT` is removed.

`stride = header_size + ceil(size / sizeof(status_t)) * sizeof(status_t)`;
`header_size` is 1 on F4/F7 and 16 on G0. Offsets are stored in bytes and advanced
by `stride`. Capacity is checked using `next_offset > sector.size - stride`;
scanning stops at `sector.size - stride`. No division by the variable record size
or slot-index multiplication is used.

The scan reads markers **only at complete record boundaries**. FF bytes inside
payload/padding do not affect it. It selects the last ready record and appends
after the last occupied slot. Incomplete, invalidated and unknown-marker records
are skipped by a full stride.

`SetUp()` validates sector, buffer, nonzero payload size, stride overflow,
alignment and capacity before scanning. It unlocks and returns `InitOK` only on
success. A zero `stride` denotes an uninitialized log; no separate initialized
flag is stored. The payload size must stay the same when reopening an existing log.

`write_data()` performs the following checked steps:

1. Write the writing marker to a new slot.
2. Write the payload after the entire header, leaving G0's second word erased.
3. Write the ready marker to the first word.
4. Invalidate the previous ready record, if present: its status byte on F4/F7,
   or its second 64-bit word on G0.

Until the new commit succeeds, the previous record remains selected. After
commit, the new record remains selected even if invalidating the old record
fails; `write_data()` returns that invalidation error. Both records can then be
ready in Flash, and a subsequent scan selects the newer one. Failed slots are
not retried.

`read_data()` copies only a completed record. It returns `NO_DATA` for an empty
log, `DATA_NOT_VALID` if only incomplete/invalid records exist or setup has not
succeeded, and `DATA_OK` for the latest completed record. Unknown/damaged marker
states use `DATA_NOT_VALID`; payload integrity is not checked.

The old nonzero-to-nonzero G0 commit produced `PROGERR` in the user's G031 test.
The new first-word transition ends with a **full 64-bit zero**, the permitted
reprogramming exception in main Flash. The second word is programmed only once,
when a newer record has been committed.
See [RM0444, main memory programming / PROGERR](https://www.st.com.cn/resource/en/reference_manual/rm0444-stm32g0x1-advanced-armbased-32bit-mcus-stmicroelectronics.pdf).

**Format change on G0:** the former 8-byte-header log is incompatible with the
16-byte header. Use an erased log sector before testing this version; `SetUp()`
does not erase or migrate existing records. Hardware verification of the new
format is left to the user. F4/F7 keep their existing record layout.

**One-sector limitation:** when full, the sector is erased before the next record.
Power loss during erase/rewrite can lose the last saved version. An erase error
invalidates the RAM selection; call `SetUp()` again before further log operations.
There is no CRC or second-sector recovery. On ECC Flash, interruption during
programming can also cause ECCD/NMI on later reading; this driver does not add an
NMI recovery handler. A status protocol alone does not guarantee recovery from
all interrupted hardware operations. [ST AN4894, EEPROM emulation robustness](https://www.st.com/content/st_com/en/technical-documents/an4894-how-to-use-eeprom-emulation-on-stm32-mcus-stmicroelectronics_asset/chunk-003-topic-an4894-high-cycle-data-area-of-flash-memory.html).

## 7. Usage Examples

Use a sector reserved by the project for settings, not a sector containing code.
Run this from the main loop after System initialization:

```cpp
struct Settings { uint32_t threshold; uint16_t mode; };
Settings cfg{100, 1};
flash_data storage(settings_sector, reinterpret_cast<uint8_t*>(&cfg), sizeof(cfg));
if (storage.SetUp() != SysInitStatus::InitOK) {
    // Handle initialization error.
    return;
}
if (storage.read_data() == flash_data::Data_Status::DATA_OK) {
    // cfg contains the latest completed record.
}
cfg.threshold = 150;
const SysStatus saved = storage.write_data();
if (saved != SysStatus::OK) {
    const uint32_t flags = FLASH->SR;
    // Inspect saved and flags before issuing another Flash operation.
    (void)flags;
}
```

Independent example; check device/package availability and every returned status.

```cpp
#include "flash.hpp"
static uint8_t payload[16]{};
// Example only: erase unit 3 must be explicitly reserved outside the image.
constinit flash_data settings(3, payload, sizeof payload);
// In main, after System/RCC initialization:
if (settings.SetUp() == SysInitStatus::InitOK) {
    auto saved = settings.read_data();
    // If saved != DATA_OK, initialize payload with application defaults.
    // On a save request: check settings.write_data() == SysStatus::OK.
}
```

## 8. Edge Cases

Flash operations belong in main with SysTick running. A busy code bank may stall instruction fetch and SysTick, so the timeout is not a wall-clock guarantee. One-sector compaction can lose the last record on power failure; there is no payload CRC or second-sector recovery.

## 1. Зачем это нужно

flash_base выполняет блокирующее стирание и программирование. flash_data добавляет журнал записей фиксированного размера в одной зарезервированной единице стирания. Память резервирует приложение, операции выполняются из main.

---

## 2. Область поддержки и порядок вызова

Файлы: `src/flash.hpp`, `src/flash.cpp`. Семейства: **STM32F4/F7/G0**.
L0 не реализован: стёртое значение и протокол программирования отличаются от G0.

Блокирующие операции вызываются из **main loop**, при работающем SysTick.
Вызовы из прерываний и критических секций запрещены контрактом API. Драйвер не
выключает и не включает IRQ. Нельзя параллельно обращаться к изменяемому диапазону,
исполнять изменяемый код или использовать перекрывающийся источник данных.

Ожидания используют `System::WaitBits()` и `System::GetTick()`. Согласованные
пределы: **F4/F7 — 50000 мс (50 с), G0 — 1000 мс (1 с)**. Это значения ST HAL,
ссылки приведены в английском разделе. Предел применяется к каждой аппаратной
операции; для записи буфера он начинается заново после каждого записанного блока.

Ожидание готовности вызывает `System::WaitBits()` напрямую. Проверки LOCK,
очистка ошибок и завершение явно расположены в методах записи/стирания.
Общая `wait_operation()` ожидает завершение и проверяет ошибки Flash.

**Ограничение таймаута:** чтение занятого банка может остановить выборку кода,
векторов и обработчика SysTick. GetTick тогда не отражает реальное прошедшее время.
Перенос исполнения в RAM не добавлен. `Timeout` не отменяет аппаратную операцию:
перед дальнейшим доступом дождитесь `flash_base::ready()`. Пока контроллер занят,
поля CR не сбрасываются; следующая операция заменит их после готовности.
После таймаута `flash_data` повторите `SetUp()` перед чтением/продолжением журнала.

## 3. Карта и банки

`flash_config.h` формата 4 генерируется драйверами из выбранной базой карты
модели/режима. Исходные карты стирания остаются формата 3. GetFlashSector(index)
возвращает `{address, size, bank, number}` по значению. Вызывающий обеспечивает
index < FLASH_SECTOR_COUNT; erase_sector() проверяет свой индекс самостоятельно.
number — аппаратный селектор SNB/PNB. У F429ZI 2 МиБ второй банк начинается
с `0x08100000`: логический индекс 12, селектор SNB 16.

Равномерная геометрия определяется по данным, без отдельного списка семейств:
одинаковый размер страниц, последовательные адреса и аппаратные номера внутри
каждого банка, один или два банка в порядке адресов. Для неё используются
константы и умножение, таблицы по одной строке на страницу нет. Начало и первый
аппаратный номер каждого банка берутся из карты; размеры банков могут отличаться.
Разрывы между банками, включая G4, сохраняются.

Неравномерная геометрия остаётся табличной. Единый доступ в обоих случаях:
GetFlashSector(index). STM32_FLASH_UNIFORM_PAGES=1/0 выставляет генератор,
пользовательский параметр не добавлялся. При равномерной геометрии flash_sectors[]
не объявлен: прямую индексацию и range-for заменяют на GetFlashSector() и
FLASH_SECTOR_COUNT. Пример обращения приведён в английском разделе выше.

Драйверы и шаблон STM32-base_files/cmake/flash_config.h.in обновляются совместно.
После обновления нужно освежить кешированную копию шаблона и пересоздать
конфигурацию проекта; старый формат 3 отклоняется явно. Универсальная генерация
геометрии не добавляет аппаратный порт Flash-драйвера для других семейств.

Режим по умолчанию следует `FLASH_DUAL_BANK`. `init()` проверяет явный аргумент,
аппаратный режим переключаемых МК и bank swap; несовпадение или swap дают
`InitError`. Option bytes не меняются. Фиксированные single/dual МК используют
свой режим. Для прямых операций `init()` вызывается один раз с проверкой результата;
у журнала это делает `SetUp()`. Разблокировка, запись и стирание повторно режим
не проверяют. Изменять режим или отображение банков во время работы нельзя.

`mass_erase()` принимает маску: **1** — банк 1, **2** — банк 2, **3** — оба.
Несуществующий банк или другая маска дают `Error`.

## 4. Статусы операций и ширина записи

Сигнатуры приведены выше. `init()` и `SetUp()` возвращают `SysInitStatus`.
`enable_access()`, `write()`, `erase_sector()`, `mass_erase()`, `write_data()` —
`SysStatus`: `OK`, `Error`, `Timeout`. Без успешного `SetUp()` запись журнала
возвращает `NotInit`. Ошибки контроллера остаются в `FLASH->SR` до следующей
операции или `clear_errors()`. Очистка затрагивает только определённые W1C-флаги.

Разблокировка проверяет аппаратный `LOCK`, пишет ключи только при необходимости
и проверяет результат. Уже разблокированная Flash даёт `OK`. Для прямой записи
и стирания сначала требуются успешные `init()` и `enable_access()`.

`write<T>()`: размер элемента 1/2/4/8 байт, `size` — число элементов. Источник,
переполнение размера/округления, диапазон назначения и выравнивание проверяет
вызывающий код. Прямая запись не проверяет эти аргументы и не обходит карту.
Нулевое число элементов даёт `OK` без операции. `read<T>()` — прямое типизированное
чтение; допустимость и выравнивание адреса обеспечивает вызывающий код.
Аппаратная ширина и PSIZE выбираются при компиляции. Для G0 используется одна
64-битная реализация, для F4/F7 — реализации записи 8/16/32 бит.

- **F4/F7:** питание 3–3,3 В, без внешнего VPP. Запись 8/16/32 бит; 64-битный
  элемент записывается двумя отдельными операциями по 32 бита с проверкой каждой.
  PSIZE x64 не используется. Стирание — x32. Назначение выровнено на 1/2/4 байта
  соответственно; для 64-битного входа достаточно 4 байт.
- **G0:** назначение выровнено на 8 байт. Один 64-битный блок записывается двумя
  последовательными 32-битными обращениями с ISB между ними. Значение собирается
  через `memcpy`, источник может быть невыровненным. Хвост дополняется `FF`;
  вызывающий код проверяет вместимость всего дополненного блока. Padding нельзя потом
  использовать для отдельной записи. Блоки из одних `FF` не пропускаются:
  программирование меняет ECC, даже если читаемое значение остаётся прежним.

После каждой аппаратной записи проверяются готовность и SR. Первая ошибка
останавливает операцию. Буфер и 64-битное значение F4/F7 не записываются атомарно.

## 5. Кеш

До изменения Flash и после завершения, включая ошибку при готовом контроллере:

- **F7:** инвалидируется только изменяемый диапазон Flash в D-cache с округлением
  до 32-байтовых линий. I-cache ядра и ART сбрасываются, если включены.
- **F4:** сбрасываются включённые instruction/data cache Flash-акселератора.
- **G0:** сбрасывается включённый instruction cache Flash.

При массовом стирании обслуживаются выбранные банки. Глобальная очистка D-cache
SRAM не выполняется. Состояние включения кешей сохраняется. Параллельный доступ
к назначению запрещён, включая callback/IRQ.

## 6. Журнал flash_data

```text
F4/F7: [ статус: 1 байт ][ данные ] ...
G0:    [ готовность: 8 байт ][ невалидность: 8 байт ][ данные ][ padding ] ...
```

Заголовок F4/F7 — один байт, G0 — **16 байт**. Физическая кодировка:

| Состояние записи | Статус F4/F7 | Первый блок G0 | Второй блок G0 |
| --- | --- | --- | --- |
| Свободно | `FF` | `FFFFFFFFFFFFFFFF` | `FFFFFFFFFFFFFFFF` |
| Идёт запись | `7F` | `00000000FFFFFFFF` | `FFFFFFFFFFFFFFFF` |
| Готово | `0F` | `0000000000000000` | `FFFFFFFFFFFFFFFF` |
| Невалидна | `00` | без изменения | `FFFFFFFF00000000` |

Любое нестёртое значение второго блока G0 имеет приоритет над первым.
`Data_Status` — единственное определение значений для записи, поиска и
результата API; отдельных констант маркеров нет. На G0 `DATA_WRITING` и `DATA_OK`
относятся к первому блоку, `DATA_NOT_VALID` — ко второму. Состояние всей записи
определяется по обоим блокам. Численные значения enum G0 изменены согласно
таблице; в прикладном коде используйте именованные значения enum. Значения F4/F7
не изменены. `DATA_CORRUPT` удалён.

`stride = header_size + ceil(size / sizeof(status_t)) * sizeof(status_t)`;
`header_size` — 1 для F4/F7, 16 для G0. Смещения хранятся в байтах и увеличиваются
на `stride`. Вместимость проверяется по `next_offset > sector.size - stride`;
поиск ограничен `sector.size - stride`. Деления на переменный размер записи и
умножения индекса слота нет.

Поиск читает маркеры **на границах полных записей**; `FF` внутри данных/padding
не влияет на него. Выбирается последняя готовая запись, добавление выполняется
после последнего занятого слота. Незавершённые, невалидные и записи с неизвестным
маркером пропускаются целиком.

`SetUp()` проверяет сектор, буфер, ненулевой размер, переполнение stride,
выравнивание и вместимость до сканирования. Затем разблокирует Flash и выполняет
поиск. Нулевой `stride` означает отсутствие инициализации; отдельный флаг
не хранится. При повторном открытии журнала размер данных должен быть прежним.

`write_data()` проверяет результат каждого этапа:

1. Записывает промежуточный маркер нового слота.
2. Записывает данные после всего заголовка; второй блок G0 остаётся стёртым.
3. Записывает готовность в первый блок.
4. Помечает предыдущую готовую запись невалидной, если она есть: байтом статуса
   F4/F7 либо вторым 64-битным блоком G0.

До успешной записи готовности выбрана прежняя запись. После этого выбрана новая,
даже если инвалидировать предыдущую не удалось; `write_data()` возвращает ошибку
инвалидации. Тогда во Flash могут остаться две готовые записи, и повторный поиск
выберет более позднюю. Неудачные слоты повторно не используются.

`read_data()` копирует только готовую запись. Пустой журнал возвращает `NO_DATA`.
Если есть только незавершённые/невалидные записи, либо не было успешного `SetUp()`,
возвращается `DATA_NOT_VALID`. При наличии готовой записи возвращается `DATA_OK`.
Неизвестные/повреждённые маркеры считаются `DATA_NOT_VALID`; целостность самих
данных не проверяется.

Прежний переход между двумя ненулевыми значениями дал `PROGERR` в тесте пользователя
на G031. Теперь первый блок завершается **полным 64-битным нулём** — разрешённым
исключением повторного программирования основной Flash. Второй блок записывается
один раз, после успешного сохранения новой записи.
Источник — [RM0444, программирование основной памяти / PROGERR](https://www.st.com.cn/resource/en/reference_manual/rm0444-stm32g0x1-advanced-armbased-32bit-mcus-stmicroelectronics.pdf).

**Смена формата G0:** журнал с прежним 8-байтным заголовком несовместим с новым
16-байтным. Для проверки этой версии нужен стёртый сектор журнала. `SetUp()`
не стирает и не преобразует существующие записи. Новый формат на железе проверяет
пользователь. Формат записей F4/F7 сохранён.

**Ограничение одного сектора:** при заполнении он стирается перед следующей
записью. Потеря питания при стирании/перезаписи может уничтожить последнюю версию.
Ошибка стирания отменяет выбор записи в RAM; перед дальнейшей работой повторите
`SetUp()`. CRC и восстановление через второй сектор не добавлены. На ECC Flash
обрыв программирования может привести к ECCD/NMI при последующем чтении;
обработчик восстановления NMI не добавлен. Одних статусов недостаточно для
гарантии восстановления после любого обрыва аппаратной операции.
[ST AN4894, устойчивость EEPROM emulation](https://www.st.com/content/st_com/en/technical-documents/an4894-how-to-use-eeprom-emulation-on-stm32-mcus-stmicroelectronics_asset/chunk-003-topic-an4894-high-cycle-data-area-of-flash-memory.html).

Пример выше использует зарезервированный проектом сектор настроек и проверяет
результаты `SetUp()` / `write_data()`. Сектор с кодом использовать нельзя.

## 7. Примеры использования

Отдельный пример; проверьте наличие блока/пинов в корпусе и каждый возвращаемый статус.

```cpp
#include "flash.hpp"
static uint8_t payload[16]{};
// Example only: erase unit 3 must be explicitly reserved outside the image.
constinit flash_data settings(3, payload, sizeof payload);
// In main, after System/RCC initialization:
if (settings.SetUp() == SysInitStatus::InitOK) {
    auto saved = settings.read_data();
    // If saved != DATA_OK, initialize payload with application defaults.
    // On a save request: check settings.write_data() == SysStatus::OK.
}
```

## 8. Угловые случаи

Операции Flash вызываются из main с работающим SysTick. Занятый банк кода может остановить выборку инструкций и SysTick: таймаут не гарантирует реальное время. При стирании единственного сектора потеря питания может уничтожить последнюю запись; CRC данных и восстановления через второй сектор нет.
