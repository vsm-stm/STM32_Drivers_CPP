## 1. Why This Is Needed

Two independent layers:

- **`flash_base`** — a thin wrapper over the Flash controller's registers: unlocking, erasing a
  sector/bank, writing a word/row, ready status. Common code for all families, the differences are
  hidden behind `#if defined(...)` (see §3-5).
- **`flash_data`** (inherits `flash_base` privately — it doesn't extend the public API, but builds a
  new abstraction on top of it) — a simple journaling mechanism for storing one data structure in
  one sector with wear leveling: each data record is written to a new slot in the sector rather than
  over the old one, to wear the Flash cells evenly (see §6).

The file `flash_config.h` is **generated by CMake** (similarly to `irq_registry_config.h`, see
[IRQ_Registry.md](IRQ_Registry.md)) for a specific chip: the list of sectors (`flash_sectors[]`), their
count (`FLASH_SECTOR_COUNT`) and mode (`FLASH_DUAL_BANK`) are taken from the datasheet of the selected
MCU at CMake configuration time, rather than hardcoded in the driver — see §2.

## 2. flash_sectors[] — Generated Sector Map

Example of an actual generated file (`STM32F429ZI`, 2 MB Flash, single-bank):

```cpp
// Auto-generated by CMake — do not edit manually.
// Device: STM32F429ZI   Flash: 2048K   Mode: single-bank
inline constexpr uint32_t FLASH_SECTOR_COUNT = 12U;
inline constexpr bool     FLASH_DUAL_BANK    = false;

inline constexpr FlashSector flash_sectors[] = {
    { 0x08000000UL,  16384UL }, // Sector  0 -  16K
    { 0x08004000UL,  16384UL }, // Sector  1 -  16K
    { 0x08008000UL,  16384UL }, // Sector  2 -  16K
    { 0x0800C000UL,  16384UL }, // Sector  3 -  16K
    { 0x08010000UL,  65536UL }, // Sector  4 -  64K
    { 0x08020000UL, 131072UL }, // Sector  5 - 128K
    ...
    { 0x080E0000UL, 131072UL }, // Sector 11 - 128K
};
```

On F4/F7 the sectors are **unequal in size** (a characteristic feature of these families — the first
sectors are small for more granular storage of settings, the last ones are large) — hence the
`{address, size}` structure per sector, rather than one "sector size" constant. On G0/L0 (a
page-based scheme, `PNB` instead of `SNB`) the pages are usually the same size, but the table format is
the same — the `flash_base` code makes no distinction between "sector" and "page", it simply indexes
`flash_sectors[]`.

`FLASH_DUAL_BANK` controls whether `bank_type` in `flash_base::init()` is interpreted as an
actual bank selection or just a pass-through parameter (see §3) — the sector layout of **both**
banks in dual-bank mode is entirely in `flash_sectors[]` regardless; `bank_type` doesn't switch which
table is used, it only checks the argument's compatibility with the current build mode.

## 3. Unlocking and Protection Against Accidental Writes

```cpp
bool flash_base::init(bank_type tb) {
    if constexpr (FLASH_DUAL_BANK)
        return (tb == bank_type::SINGLE_BANK || tb == bank_type::DUAL_BANK);
    return true;
}

bool flash_base::enable_access() {
    if (!flash_access_enabled) {
        FLASH->KEYR = 0x45670123;   // Key1
        FLASH->KEYR = 0xCDEF89AB;   // Key2 — must immediately follow Key1
        flash_access_enabled = 1;
        return true;
    }
    return false;
}
```

`KEYR` is a hardware procedure: two fixed keys (values from the Reference Manual, not a
secret — the protection is not against outsiders, but against an **accidental** write caused by a
stray pointer) must be written strictly in sequence. Any **other** write to `KEYR` between Key1 and
Key2 (for example, if some other code touching `FLASH->KEYR` accidentally ends up between these two
lines) **locks** Flash in hardware until the next MCU reset — it cannot be recovered in software.
That is why both lines sit next to each other with nothing in between in the code, and the global flag
`flash_access_enabled` guarantees that the procedure runs **exactly once** during the program's
lifetime — calling `enable_access()` again does not resupply the keys (which isn't needed anyway: Flash
stays unlocked until the next reset), and it immediately returns `false`.

## 4. write() — Family-Specific Writing

```cpp
template<typename T>
static void write(uint32_t addr, T* data, uint32_t size = 1);
```

`static_assert(sizeof(T) == 1 || 2 || 4 || 8)` — Flash can only be written with these element
widths; any other type size is a compile-time error, not a runtime failure from accessing an
unaligned register.

**G0/L0 — only 64-bit writes**, whatever `T` is:

```cpp
for (uint32_t i = 0; i < total; i += 8) {
    uint64_t dword = /* assemble 8 bytes from data, pad with 0xFF if there is less than 8 bytes of data */;
    *reinterpret_cast<volatile uint32_t*>(addr + i)     = (uint32_t)(dword);
    *reinterpret_cast<volatile uint32_t*>(addr + i + 4) = (uint32_t)(dword >> 32);
    while (!ready()) {}
}
```

The hardware of these families physically accepts programming only as a pair of consecutive
32-bit words, which together form one 64-bit Flash word — even if the calling code writes a single
`uint8_t`, the driver pads the missing bytes with the value `0xFF` (Flash after erasing = all bits 1,
writing `0xFF` into the "extra" bytes is a no-op and doesn't corrupt neighboring data).

**F4/F7 — the write width is selected via `PSIZE`**:

```cpp
FLASH->CR |= ((sz == 8) ? 3 : (sz >> 1)) << FLASH_CR_PSIZE_Pos;   // sz=1→0, sz=2→1, sz=4→2, sz=8→3
for (uint32_t i = 0; i < size; i++) {
    *reinterpret_cast<volatile T*>(addr + i * sizeof(T)) = data[i];
    while (!ready()) {}
    __DSB();
}
```

Here the Flash controller itself supports an arbitrary element width (byte/half-word/word/
double word) — `PSIZE` simply tells it what size the next write will be.

Both branches are united by a common protocol: `while(!ready())` before starting, `FLASH_CR_PG`
(allow programming) set on entry and cleared on exit, `__disable_irq()`/`__enable_irq()` around the
whole operation (writing to flash while the core itself is executing code from that same flash — an
interrupt in the middle of the operation is not permitted on most of these MCUs), `while(!ready())`
after every word.

## 5. erase_sector() / mass_erase()

```cpp
void flash_base::erase_sector(uint8_t sector) {
    if (sector >= FLASH_PAGE_COUNT) return;
    while (!ready()) {}
    clear_errors();
    FLASH->CR |= CR_EARSE_BIT;             // SER (F4/F7) or PER (G0/L0)
    FLASH->CR |= sector << CR_SERCTOR_Pos; // SNB or PNB
    FLASH->CR |= FLASH_CR_STRT;
    while (!ready()) {}
    FLASH->CR &= ~(CR_SERCTOR_Msk | 0);
    FLASH->CR &= ~CR_EARSE_BIT;
}
```

The erase bits and the position of the sector/page number differ by family (`#define`s
`CR_EARSE_BIT`/`CR_SERCTOR_Pos`/`CR_SERCTOR_Msk` at the top of `rtc.cpp`... that is, `flash.cpp`) —
after the operation these bits must be **cleared**, otherwise the next access to Flash (even an
ordinary code read from it after returning from the function) could be interpreted by the hardware as
yet another erase command.

`mass_erase(bank)` takes a **bit mask** of banks (`bit 0` = bank 1, `bit 1` = bank 2) — `0`
(nothing selected) and `> 3` (outside the two banks) are both rejected immediately. Erasing bank
2 (`MER2`) on STM32G0 is commented out with the note `// todo check if MER2 is supported` — **not
implemented**; calling `mass_erase(2)` or `mass_erase(3)` on G0 will erase only bank 1, if it is
selected by bit 0, and will silently skip bank 2.

## 6. flash_data — a Wear-Leveling Log in a Single Sector

The storage format inside the sector is a sequence of "status + data" records, each
written **once**; old records are not overwritten directly, but invalidated:

```
[ status_t ][ data ... ][ padding ][ status_t ][ data ... ][ padding ] ...
|<---sz--->|<----------size------->|
|<--------------------stride------------------->|
```

`status_t` is `uint8_t` on F4/F7 (the minimum write unit there is 1 byte), `uint64_t` on G0
(the minimum write is 64 bits, see §4) — hence `stride = sz + ceil(size / sz) * sz`:
the data is rounded up to a multiple of `sz`, so the next record always starts at an aligned
address suitable for the next status write.

**Three statuses** (`Data_Status`):

- `DATA_OK` — a valid, current record (all ones after erasing, except for overwritten
  bits — in fact this is a special, incomplete value, not simply "0xFF...FF", see the code
  `static_cast<status_t>(-1) >> (sizeof(status_t)*4)`).
- `DATA_NOT_VALID` (`0x00`) — the record was explicitly invalidated before writing a new one
  (Flash only allows changing bits `1→0`, so writing zero over any previous value is always
  physically possible without erasing).
- `NO_DATA` (`0xFF...FF`, "clean" Flash after erasing) — nothing has ever been written here
  yet.
- Anything else is treated as `DATA_CORRUPT` (a partial write, power loss in the middle of
  the operation, etc.).

**`find_offset()`** (called in the constructor via `SetUp()`) scans the sector from the
beginning, skipping `DATA_NOT_VALID` records, until it finds `DATA_OK` (current data — `offset`
points to it) or `NO_DATA` (free space — the new record is written here). Any other status
is `DATA_CORRUPT`, and `offset` is reset to 0 (the sector will be erased on the next `write_data()`).

**`write_data()`** — three cases:

1. **There is space and the current data is not corrupted** — first **invalidate** the current
   record (`status = DATA_NOT_VALID`, a clean zero write — doesn't require erasing), `offset++`, then
   write the new record (status `DATA_OK`, then data) into the new slot.
2. **The sector is full OR the data is corrupted** — erase the entire sector (`erase_sector()`),
   `offset = 0`, write the new record from scratch.
3. Order of writing the new record: **status `DATA_OK` first, then the data** (see the code —
   `write(..., &ok)` comes before `write(..., data, size)`). The comment in the source claims that
   this separation protects against reading an incomplete record after a power loss — but if power is
   lost exactly **between** these two writes, the result is the opposite of what one might expect:
   on the next startup `find_offset()` will see the already-written `DATA_OK`, and `read_data()`
   will copy data that hasn't finished being written yet (partially `0xFF`/garbage), as if it were
   correct. This mismatch between the comment in the code and its actual behavior is worth keeping in
   mind when working with this module — to guarantee "don't read data that lost power in the middle of
   being written," the order should be swapped to "data first, then status".

**`read_data()`** — returns the `status` saved by `find_offset()`; the data is copied into
the user's buffer only if `status == DATA_OK`.

## 7. Usage Examples

### Direct Write/Read Through flash_base

```cpp
flash_base::init();
flash_base::enable_access();

uint32_t value = 0x12345678;
flash_base::erase_sector(5);
flash_base::write<uint32_t>(flash_sectors[5].address, &value);

uint32_t back = flash_base::read<uint32_t>(flash_sectors[5].address);
```

### flash_data — Journaled Settings Storage with Wear Leveling

```cpp
struct Settings { uint32_t threshold; uint16_t mode; };

Settings cfg{100, 1};
flash_data storage(/*sector=*/10, reinterpret_cast<uint8_t*>(&cfg), sizeof(cfg));
storage.SetUp();                 // init() + enable_access() + find_offset()

if (storage.read_data() == flash_data::Data_Status::DATA_OK) {
    // cfg is already filled with the last saved values
}

cfg.threshold = 150;
storage.write_data();            // a new record in the next free slot of the sector
```

## 8. Edge Cases

- **`enable_access()` performs the unlock strictly once during the program's lifetime** —
  repeated calls do not resupply the keys (which isn't required anyway — Flash stays unlocked
  until reset), and instead immediately return `false`.
- **An incorrect key sequence locks Flash until the MCU resets** — this is hardware
  behavior, not a driver bug; the only way to recover is a reset.
- **`mass_erase()` bit 2 (bank 2) is not implemented on G0** (`// todo check if MER2 is
  supported`) — calling it with this bit set won't cause an error, but also won't erase the second
  bank.
- **`write_data()` writes the status before the data** — if power is lost between these two
  writes, `read_data()` on the next startup will return `DATA_OK` with incomplete/garbage data (see
  the discussion in §6, point 3) — this is not protection against power loss in the middle of the
  data write itself, only against reading a stale record as current.
- **The `stride` arithmetic assumes `size` and `sz` are small relative to the sector size** —
  `find_offset()`/`write_data()` do not check for `offset * stride` overflowing `uint32_t`, only for
  it exceeding `flash_sectors[sector].size`.
- **`__disable_irq()`/`__enable_irq()` around the whole of `write()`** — during programming,
  interrupts are completely disabled, including the system tick (`SysTick`) — a long series of
  writes (for example, writing a whole sector in large blocks) will noticeably "freeze"
  `System::GetTick()` for the duration of the operation.

## 1. Зачем это нужно

Два независимых слоя:

- **`flash_base`** — тонкая обёртка над регистрами Flash-контроллера: разблокировка, стирание
  сектора/банка, запись слова/строки, статус готовности. Общий код для всех семейств, различия
  спрятаны за `#if defined(...)` (см. §3-5).
- **`flash_data`** (наследует `flash_base` приватно — не расширяет публичный API, а строит новую
  абстракцию поверх него) — простой journaling-механизм для хранения одной структуры данных в
  одном секторе с wear leveling: каждая запись данных пишется в новый слот сектора, а не поверх
  старой, чтобы равномерно износить ячейки Flash (см. §6).

Файл `flash_config.h` — **сгенерирован CMake** (аналогично `irq_registry_config.h`, см.
[IRQ_Registry.md](IRQ_Registry.md)) под конкретный чип: список секторов (`flash_sectors[]`), их
количество (`FLASH_SECTOR_COUNT`) и режим (`FLASH_DUAL_BANK`) берутся из даташита выбранного МК
на этапе конфигурации CMake, а не хардкодятся в драйвере — см. §2.

## 2. flash_sectors[] — сгенерированная карта секторов

Пример реального сгенерированного файла (`STM32F429ZI`, 2 МБ Flash, single-bank):

```cpp
// Auto-generated by CMake — do not edit manually.
// Device: STM32F429ZI   Flash: 2048K   Mode: single-bank
inline constexpr uint32_t FLASH_SECTOR_COUNT = 12U;
inline constexpr bool     FLASH_DUAL_BANK    = false;

inline constexpr FlashSector flash_sectors[] = {
    { 0x08000000UL,  16384UL }, // Sector  0 -  16K
    { 0x08004000UL,  16384UL }, // Sector  1 -  16K
    { 0x08008000UL,  16384UL }, // Sector  2 -  16K
    { 0x0800C000UL,  16384UL }, // Sector  3 -  16K
    { 0x08010000UL,  65536UL }, // Sector  4 -  64K
    { 0x08020000UL, 131072UL }, // Sector  5 - 128K
    ...
    { 0x080E0000UL, 131072UL }, // Sector 11 - 128K
};
```

На F4/F7 сектора **неравного размера** (характерная особенность этих семейств — первые сектора
маленькие для более гранулярного хранения настроек, последние большие) — отсюда структура
`{address, size}` на сектор, а не одна константа "размер сектора". На G0/L0 (постраничная схема,
`PNB` вместо `SNB`) страницы обычно одного размера, но формат таблицы тот же — код `flash_base`
не делает разницы между "сектор" и "страница", просто индексирует `flash_sectors[]`.

`FLASH_DUAL_BANK` управляет тем, интерпретируется ли `bank_type` в `flash_base::init()` как
реальный выбор банка или просто проходной параметр (см. §3) — раскладка секторов **обоих**
банков в режиме dual-bank всё равно целиком в `flash_sectors[]`, `bank_type` не переключает,
какая таблица используется, только проверяет совместимость аргумента с текущим режимом сборки.

## 3. Разблокировка и защита от случайной записи

```cpp
bool flash_base::init(bank_type tb) {
    if constexpr (FLASH_DUAL_BANK)
        return (tb == bank_type::SINGLE_BANK || tb == bank_type::DUAL_BANK);
    return true;
}

bool flash_base::enable_access() {
    if (!flash_access_enabled) {
        FLASH->KEYR = 0x45670123;   // Key1
        FLASH->KEYR = 0xCDEF89AB;   // Key2 — должен идти СРАЗУ следом за Key1
        flash_access_enabled = 1;
        return true;
    }
    return false;
}
```

`KEYR` — аппаратная процедура: два фиксированных ключа (значения из Reference Manual, не
секрет — защита не от посторонних, а от **случайной** записи из-за сбойного указателя) должны
быть записаны строго последовательно. Любая **другая** запись в `KEYR` между Key1 и Key2
(например, если между этими двумя строками случайно окажется другой код, трогающий `FLASH->KEYR`)
аппаратно **блокирует** Flash до следующего сброса МК — восстановить программно нельзя. Поэтому
в коде обе строки идут рядом без ничего между ними, и глобальный флаг `flash_access_enabled`
гарантирует, что процедура выполняется **ровно один раз** за время жизни программы — повторный
вызов `enable_access()` не переподаёт ключи (это и не нужно: Flash остаётся разблокированным до
следующего сброса), а сразу возвращает `false`.

## 4. write() — запись, специфичная по семействам

```cpp
template<typename T>
static void write(uint32_t addr, T* data, uint32_t size = 1);
```

`static_assert(sizeof(T) == 1 || 2 || 4 || 8)` — Flash пишется только этими шириной элемента;
любой другой размер типа — ошибка компиляции, а не рантайм-сбой при обращении к невыровненному
регистру.

**G0/L0 — только 64-битная запись**, что бы ни было в `T`:

```cpp
for (uint32_t i = 0; i < total; i += 8) {
    uint64_t dword = /* собрать 8 байт из data, паддинг 0xFF если данных меньше 8 */;
    *reinterpret_cast<volatile uint32_t*>(addr + i)     = (uint32_t)(dword);
    *reinterpret_cast<volatile uint32_t*>(addr + i + 4) = (uint32_t)(dword >> 32);
    while (!ready()) {}
}
```

Хардвер этих семейств физически принимает программирование только парой последовательных
32-битных слов, которые вместе формируют одно 64-битное слово Flash — даже если вызывающий код
пишет один `uint8_t`, драйвер дополняет недостающие байты значением `0xFF` (Flash после стирания
= все биты 1, дозапись `0xFF` в "лишние" байты — no-op, не портит соседние данные).

**F4/F7 — ширина записи выбирается через `PSIZE`**:

```cpp
FLASH->CR |= ((sz == 8) ? 3 : (sz >> 1)) << FLASH_CR_PSIZE_Pos;   // sz=1→0, sz=2→1, sz=4→2, sz=8→3
for (uint32_t i = 0; i < size; i++) {
    *reinterpret_cast<volatile T*>(addr + i * sizeof(T)) = data[i];
    while (!ready()) {}
    __DSB();
}
```

Здесь Flash-контроллер сам поддерживает произвольную ширину элемента (байт/полуслово/слово/
двойное слово) — `PSIZE` просто сообщает ему, какого размера будет следующая запись.

Обе ветки объединены общим протоколом: `while(!ready())` перед стартом, `FLASH_CR_PG` (разрешить
программирование) на входе и снято на выходе, `__disable_irq()`/`__enable_irq()` вокруг всей
операции (запись во flash во время которой само же ядро выполняет код из той же flash — прерывание
посреди операции недопустимо на большинстве этих МК), `while(!ready())` после каждого слова.

## 5. erase_sector() / mass_erase()

```cpp
void flash_base::erase_sector(uint8_t sector) {
    if (sector >= FLASH_PAGE_COUNT) return;
    while (!ready()) {}
    clear_errors();
    FLASH->CR |= CR_EARSE_BIT;             // SER (F4/F7) или PER (G0/L0)
    FLASH->CR |= sector << CR_SERCTOR_Pos; // SNB или PNB
    FLASH->CR |= FLASH_CR_STRT;
    while (!ready()) {}
    FLASH->CR &= ~(CR_SERCTOR_Msk | 0);
    FLASH->CR &= ~CR_EARSE_BIT;
}
```

Биты стирания и позиция номера сектора/страницы различаются по семействам (`#define`'ы
`CR_EARSE_BIT`/`CR_SERCTOR_Pos`/`CR_SERCTOR_Msk` в начале `rtc.cpp`... то есть `flash.cpp`) —
после операции биты обязательно **сбрасываются**, иначе следующее обращение к Flash (даже обычное
чтение кода из неё после возврата из функции) могло бы быть аппаратно интерпретировано как ещё
одна команда стирания.

`mass_erase(bank)` принимает **битовую маску** банков (`бит 0` = банк 1, `бит 1` = банк 2) — `0`
(ничего не выбрано) и `> 3` (за пределами двух банков) обе отклоняются немедленно. Стирание банка
2 (`MER2`) на STM32G0 закомментировано с пометкой `// todo check if MER2 is supported` — **не
реализовано**, вызов `mass_erase(2)` или `mass_erase(3)` на G0 сотрёт только банк 1, если он
выбран битом 0, и молча пропустит банк 2.

## 6. flash_data — wear-leveling лог в одном секторе

Формат хранения внутри сектора — последовательность записей "статус + данные", каждая
записывается **один раз**, старые записи не перезаписываются напрямую, а инвалидируются:

```
[ status_t ][ data ... ][ padding ][ status_t ][ data ... ][ padding ] ...
|<---sz--->|<----------size------->|
|<--------------------stride------------------->|
```

`status_t` — `uint8_t` на F4/F7 (минимальная единица записи там — 1 байт), `uint64_t` на G0
(минимальная запись — 64 бита, см. §4) — отсюда `stride = sz + ceil(size / sz) * sz`:
данные округляются вверх до кратного `sz`, чтобы следующая запись всегда начиналась с
выровненного адреса, годного для очередной записи статуса.

**Три статуса** (`Data_Status`):

- `DATA_OK` — валидная, актуальная запись (все единицы после стирания, кроме перезаписанных
  битов — по факту это специальное неполное значение, не просто "0xFF...FF", см. код
  `static_cast<status_t>(-1) >> (sizeof(status_t)*4)`).
- `DATA_NOT_VALID` (`0x00`) — запись была явно инвалидирована перед записью новой (Flash
  разрешает менять биты только `1→0`, поэтому запись нуля поверх любого предыдущего значения
  всегда физически возможна без стирания).
- `NO_DATA` (`0xFF...FF`, "чистый" Flash после стирания) — здесь ещё никогда не писали.
- Что угодно ещё — трактуется как `DATA_CORRUPT` (частичная запись, потеря питания посреди
  операции и т.п.).

**`find_offset()`** (вызывается в конструкторе через `SetUp()`) сканирует сектор с начала,
пропуская `DATA_NOT_VALID`-записи, пока не найдёт `DATA_OK` (актуальные данные — `offset`
указывает на них) или `NO_DATA` (свободное место — новую запись писать сюда). Любой другой статус
— `DATA_CORRUPT`, `offset` сбрасывается на 0 (сектор будет стёрт при следующей `write_data()`).

**`write_data()`** — три случая:

1. **Есть место и текущие данные не повреждены** — сначала **инвалидировать** текущую запись
   (`status = DATA_NOT_VALID`, чистая запись нуля — не требует стирания), `offset++`, затем
   записать новую запись (статус `DATA_OK`, потом данные) в новый слот.
2. **Сектор заполнен ИЛИ данные повреждены** — стереть весь сектор (`erase_sector()`),
   `offset = 0`, записать новую запись с нуля.
3. Порядок записи новой записи: **сначала статус `DATA_OK`, затем данные** (см. код —
   `write(..., &ok)` идёт до `write(..., data, size)`). Комментарий в исходнике утверждает, что
   такое разделение защищает от чтения неполной записи после потери питания — но при потере
   питания именно **между** этими двумя записями результат обратный тому, что можно ожидать:
   `find_offset()` при следующем старте увидит уже записанный `DATA_OK`, а `read_data()`
   скопирует ещё не дозаписанные (частично `0xFF`/мусорные) данные, как будто они корректны.
   Это несоответствие между комментарием в коде и его фактическим поведением стоит иметь в виду
   при работе с этим модулем — для гарантии "не читать данные, потерявшие питание посреди
   записи" порядок стоило бы поменять на "сначала данные, потом статус".

**`read_data()`** — возвращает `status`, сохранённый `find_offset()`; данные копируются в
пользовательский буфер только если `status == DATA_OK`.

## 7. Примеры использования

### Прямая запись/чтение через flash_base

```cpp
flash_base::init();
flash_base::enable_access();

uint32_t value = 0x12345678;
flash_base::erase_sector(5);
flash_base::write<uint32_t>(flash_sectors[5].address, &value);

uint32_t back = flash_base::read<uint32_t>(flash_sectors[5].address);
```

### flash_data — журналируемое хранение настроек с wear leveling

```cpp
struct Settings { uint32_t threshold; uint16_t mode; };

Settings cfg{100, 1};
flash_data storage(/*sector=*/10, reinterpret_cast<uint8_t*>(&cfg), sizeof(cfg));
storage.SetUp();                 // init() + enable_access() + find_offset()

if (storage.read_data() == flash_data::Data_Status::DATA_OK) {
    // cfg уже заполнен последними сохранёнными значениями
}

cfg.threshold = 150;
storage.write_data();            // новая запись в следующий свободный слот сектора
```

## 8. Угловые случаи

- **`enable_access()` вызывает разблокировку строго один раз за время жизни программы** —
  повторные вызовы не подают ключи заново (это и не требуется — Flash остаётся разблокированным
  до сброса), а сразу возвращают `false`.
- **Некорректная последовательность ключей блокирует Flash до сброса МК** — это аппаратное
  поведение, не ошибка драйвера; единственный способ восстановиться — перезагрузка.
- **`mass_erase()` бит 2 (банк 2) не реализован на G0** (`// todo check if MER2 is supported`) —
  вызов с этим битом не вызовет ошибку, но и не сотрёт второй банк.
- **`write_data()` записывает статус до данных** — при потере питания между этими двумя записями
  `read_data()` на следующем старте вернёт `DATA_OK` с неполными/мусорными данными (см. разбор в
  §6, пункт 3) — не защита от потери питания посреди самой записи данных, только от чтения
  устаревшей записи как актуальной.
- **`stride`-арифметика предполагает `size` и `sz` небольшими относительно размера сектора** —
  `find_offset()`/`write_data()` не проверяют переполнение `offset * stride` за пределы
  `uint32_t`, только за пределы `flash_sectors[sector].size`.
- **`__disable_irq()`/`__enable_irq()` вокруг всей `write()`** — на время программирования
  прерывания полностью выключены, включая системный тик (`SysTick`) — долгая серия записей
  (например, всего сектора большими блоками) заметно "заморозит" `System::GetTick()` на время
  операции.
