## 1. Why This Is Needed

The module has two layers:

| Class | What it does |
| --- | --- |
| `flash_base` | Low-level blocking erase and program operations on internal Flash. |
| `flash_data` | A small "settings storage": a journal of fixed-size records inside **one** reserved erase unit (sector/page). Saving a new version appends a record; reading returns the latest complete one. |

The application is responsible for reserving the Flash area (so that it does not overlap the firmware image) and for calling these operations from `main`.

## 2. Scope and calling contract

- **Files:** `src/flash.hpp`, `src/flash.cpp`.
- **Families:** STM32F4, F7, G0. (L0 is not implemented — its erased value and programming protocol differ from G0.)

**Calling rules:**

- Call from the **main loop** with SysTick running.
- Never from interrupts or critical sections. The driver itself does not disable or enable interrupts.
- Do not access the destination range concurrently, do not execute code from the range being modified, and do not use an overlapping source buffer.

**Waiting.** Waits use `System::WaitBits()` with `System::GetTick()`. LOCK checks, error clearing and cleanup are done explicitly in the write/erase methods; the shared `wait_operation()` waits for completion and checks the Flash error flags.

| Family | Timeout per hardware operation |
| --- | --- |
| F4/F7 | 50000 ms (50 s) |
| G0 | 1000 ms (1 s) |

These are ST HAL defaults ([F4](https://raw.githubusercontent.com/STMicroelectronics/stm32f4xx-hal-driver/master/Src/stm32f4xx_hal_flash.c), [F7](https://raw.githubusercontent.com/STMicroelectronics/stm32f7xx-hal-driver/master/Src/stm32f7xx_hal_flash.c), [G0](https://raw.githubusercontent.com/STMicroelectronics/stm32g0xx-hal-driver/master/Inc/stm32g0xx_hal_flash.h)). The timeout restarts for every physical write, not once for the whole buffer.

> **Timeout limitation.** While a Flash bank is busy, reading from it stalls instruction fetch — including the SysTick handler and its vector. `GetTick()` then does not track real time reliably. No code is moved to RAM.
>
> A `Timeout` does **not** cancel the hardware operation. Wait for `flash_base::ready()` before any further Flash access. While the controller is busy, CR is not cleaned up; the next operation overwrites the old fields once ready. For `flash_data`, call `SetUp()` again after a timeout before reading or continuing the log.

## 3. Sector map and banks

**Where the map comes from.** `flash_config.h` (format 4) is generated by the drivers from the device/mode map chosen by the base project (the source erase maps stay format 3).

```cpp
// After checking index < FLASH_SECTOR_COUNT:
const FlashSector page = GetFlashSector(index);   // {address, size, bank, number}
const uint32_t address = page.address;
```

- `GetFlashSector(index)` returns the sector by value. The caller ensures `index < FLASH_SECTOR_COUNT`; `erase_sector()` checks its own argument.
- `number` is the **hardware** selector (SNB on F4/F7, PNB on G0), not the logical index. Example: F429ZI 2 MiB — bank 2 starts at `0x08100000`, logical index 12, SNB selector 16.

**Uniform vs. table geometry.** The generator detects geometry from the data, without a family list:

- *Uniform:* equal page size, consecutive addresses and selectors within each bank, one or two banks in address order. Computed with constants and multiplication — no per-page array. Each bank keeps its own start address and first selector; bank sizes may differ and gaps stay unmapped.
- *Non-uniform:* kept as the internal `flash_sectors[]` table.

Always use `GetFlashSector()` — it works for both. `STM32_FLASH_UNIFORM_PAGES` (1/0) is generated, not a user setting. For uniform maps `flash_sectors[]` is **not declared**, so replace direct indexing or range-for loops with `GetFlashSector()` and `FLASH_SECTOR_COUNT`.

**Updating.** Update the drivers and `STM32-base_files/cmake/flash_config.h.in` together, refresh the cached template and regenerate the project. A stale format-3 config is rejected explicitly. The generic geometry does not port the Flash operations to families other than F4/F7/G0.

**Banks:**

- The default bank type follows `FLASH_DUAL_BANK`.
- `init()` does **not** change option bytes. It checks an explicit argument against the map, checks the hardware mode bit on switchable devices, and returns `InitError` on mismatch or when bank swap is active. Single-only and dual-only devices use their fixed mode.
- Call `init()` once (and check it) before direct operations; `flash_data::SetUp()` does it for the log. Unlock/erase/write do not re-check the mode, so do not change bank mode or mapping while the driver is in use.
- `mass_erase(mask)`: **1** = bank 1, **2** = bank 2, **3** = both. Absent banks and other masks → `Error`.

## 4. API and programming widths

```cpp
static SysInitStatus init(bank_type tb = /* generated mode */);
static SysStatus enable_access();
static bool ready();
static SysStatus erase_sector(uint32_t sector);
static SysStatus mass_erase(uint8_t bank);
template<typename T>
static SysStatus write(uint32_t addr, const T* data, uint32_t size = 1);
template<typename T>
static T read(uint32_t addr);
```

**Return values:**

| Function | Type | Values |
| --- | --- | --- |
| `init()`, `flash_data::SetUp()` | `SysInitStatus` | `InitOK` / `InitError` |
| unlock, write, erase | `SysStatus` | `OK`, `Error`, `Timeout` |
| `flash_data::write_data()` | `SysStatus` | `OK`, `Error`, `Timeout`, `NotInit` (before a successful `SetUp()`) |

Hardware error flags stay in `FLASH->SR` until the next operation or `clear_errors()`. Only defined write-1-to-clear flags are cleared, never reserved bits.

**Unlocking.** `enable_access()` reads the real `CR.LOCK`, writes the two keys only if locked, and verifies the result. Already unlocked → `OK`. Direct write/erase requires a successful `init()` followed by `enable_access()`; there is no software "unlocked" flag.

**`write<T>(addr, data, count)`:**

- element size 1, 2, 4 or 8 bytes; `count` is the number of elements;
- `count = 0` → `OK`, nothing happens;
- **the caller validates** the source buffer, size overflow, destination range and alignment — direct writes do not check them or consult the sector map.

**`read<T>(addr)`** is a raw typed read; the address must be valid and aligned.

Hardware width and PSIZE are chosen at compile time:

| Family | Hardware programming | Destination alignment |
| --- | --- | --- |
| F4/F7 | 8/16/32-bit; a 64-bit element is split into two separately checked 32-bit writes | 1/2/4 bytes respectively; 4 for 64-bit elements |
| G0 | 64-bit: two consecutive 32-bit stores separated by ISB | 8 bytes |

**F4/F7** assume **VDD 3–3.3 V without external VPP**: erase uses ×32 parallelism, ×64 PSIZE is never used ([RM0090, programming parallelism](https://www.st.com/resource/en/reference_manual/rm0090-stm32f4xx-reference-manual-stmicroelectronics.pdf)).

**G0:**

- each 64-bit value is assembled with `memcpy`, so the source needs no 8-byte alignment;
- the last block is padded with `0xFF` — the caller must reserve and validate the **whole** padded block; that padding cannot later be programmed as a separate record;
- all-`0xFF` blocks are **not skipped**: programming them changes ECC state even though the data still reads `0xFF`.

After every hardware write the driver waits and checks SR, stopping at the first error. So a buffer write is **not atomic** — an F4/F7 64-bit write can fail after its first half.

## 5. Cache maintenance

Before modifying Flash, and after the operation (also after an error, once ready), the driver invalidates stale Flash cache contents:

| Family | What is invalidated |
| --- | --- |
| F7 | Only the affected Flash range in the Cortex-M7 D-cache (rounded to 32-byte lines); I-cache and ART are reset if enabled |
| F4 | Flash accelerator instruction/data caches, if enabled |
| G0 | Flash instruction cache, if enabled |

- Mass erase covers the selected banks.
- SRAM D-cache is not cleaned or invalidated globally.
- Cache enable states are preserved.
- No access to the destination during the operation — including from callbacks and interrupts.

## 6. flash_data: one sector, fixed-size records

**Record layout:**

```text
F4/F7: [ status byte ][ payload ] ...
G0:    [ commit: 8 bytes ][ invalid: 8 bytes ][ payload ][ padding ] ...
```

The header is 1 byte on F4/F7 and **16 bytes** on G0. Marker values in Flash:

| Record state | F4/F7 status | G0 commit word | G0 invalidation word |
| --- | --- | --- | --- |
| Free | `FF` | `FFFFFFFFFFFFFFFF` | `FFFFFFFFFFFFFFFF` |
| Writing | `7F` | `00000000FFFFFFFF` | `FFFFFFFFFFFFFFFF` |
| Ready | `0F` | `0000000000000000` | `FFFFFFFFFFFFFFFF` |
| Invalidated | `00` | unchanged | `FFFFFFFF00000000` |

- On G0, any non-erased invalidation word overrides the commit word; the state is determined from both.
- `Data_Status` is the single definition used for programming, scanning and API results. On G0, `DATA_WRITING`/`DATA_OK` refer to the first word, `DATA_NOT_VALID` to the second.
- G0 enum values changed to this encoding — use the named enumerators, not numbers. F4/F7 values are unchanged. `DATA_CORRUPT` was removed.

**Record size (stride):**

```text
stride = header_size + ceil(size / sizeof(status_t)) * sizeof(status_t)
header_size = 1 (F4/F7) or 16 (G0)
```

Offsets are in bytes and advance by `stride`. Capacity check: `next_offset > sector.size - stride`; scanning stops at `sector.size - stride`. No division by the record size is used.

**Scanning** reads markers **only at record boundaries**, so `0xFF` bytes inside payload/padding do not confuse it. It selects the last ready record and appends after the last occupied slot. Incomplete, invalidated and unknown records are skipped by a full stride.

**`SetUp()`** checks the sector, buffer, non-zero payload size, stride overflow, alignment and capacity **before** scanning, then unlocks Flash. It returns `InitOK` only on success. `stride == 0` means "not set up" (no separate flag). Reopen an existing log with the **same** payload size.

**`write_data()`** — each step is checked:

1. Write the "writing" marker into a new slot.
2. Write the payload after the full header (G0's second word stays erased).
3. Write the "ready" marker (first word).
4. Invalidate the previous ready record, if any: its status byte on F4/F7, its second 64-bit word on G0.

What survives a failure:

- Until step 3 succeeds, the **previous** record stays selected.
- After step 3 the **new** record is selected, even if step 4 fails; `write_data()` then returns that error. Flash may hold two ready records — the next scan picks the newer one.
- Failed slots are not reused.

**`read_data()`** copies only a complete record:

| Result | When |
| --- | --- |
| `DATA_OK` | latest complete record copied into the buffer |
| `NO_DATA` | the log is empty |
| `DATA_NOT_VALID` | only incomplete/invalid/unknown records, or `SetUp()` did not succeed |

Payload integrity itself is not checked (no CRC).

**Why the G0 format changed.** The old commit step overwrote one non-zero value with another, which produced `PROGERR` in a test on G031. Now the first word ends as a **full 64-bit zero** — the allowed re-programming exception for main Flash — and the second word is programmed only once, after a newer record is committed. See [RM0444, main memory programming / PROGERR](https://www.st.com.cn/resource/en/reference_manual/rm0444-stm32g0x1-advanced-armbased-32bit-mcus-stmicroelectronics.pdf).

**G0 format break:** logs with the old 8-byte header are incompatible. Start from an erased log sector; `SetUp()` does not erase or migrate old records. F4/F7 keep their existing layout.

> **One-sector limitation:**
>
> - When the sector is full, it is erased before the next record. Power loss during erase/rewrite can lose the last saved version.
> - An erase error drops the RAM selection — call `SetUp()` again before further log operations.
> - No CRC and no second-sector recovery.
> - On ECC Flash an interrupted programming can cause ECCD/NMI on a later read; no NMI recovery handler is provided.
>
> A status protocol alone cannot recover from every interrupted hardware operation — see [ST AN4894, EEPROM emulation robustness](https://www.st.com/content/st_com/en/technical-documents/an4894-how-to-use-eeprom-emulation-on-stm32-mcus-stmicroelectronics_asset/chunk-003-topic-an4894-high-cycle-data-area-of-flash-memory.html).

## 7. Usage Examples

Use a sector **reserved for settings**, never one that contains code.

**A constinit byte buffer** (recommended — no start-up code):

```cpp
#include "flash.hpp"

static uint8_t payload[16]{};
// Example only: erase unit 3 must be explicitly reserved outside the image.
constinit flash_data settings(3, payload, sizeof payload);

// In main, after System/RCC initialization:
if (settings.SetUp() == SysInitStatus::InitOK) {
    auto saved = settings.read_data();
    // If saved != DATA_OK, fill payload with application defaults.
    // On a save request: check settings.write_data() == SysStatus::OK.
}
```

**A struct with an error check.** `reinterpret_cast` is not a constant expression, so this object cannot be `constinit`; it is created at run time inside `main`:

```cpp
struct Settings { uint32_t threshold; uint16_t mode; };
Settings cfg{100, 1};

flash_data storage(settings_sector, reinterpret_cast<uint8_t*>(&cfg), sizeof(cfg));
if (storage.SetUp() != SysInitStatus::InitOK) {
    // Handle initialization error.
    return;
}
if (storage.read_data() == flash_data::Data_Status::DATA_OK) {
    // cfg now holds the latest complete record.
}
cfg.threshold = 150;
const SysStatus saved = storage.write_data();
if (saved != SysStatus::OK) {
    const uint32_t flags = FLASH->SR;
    // Inspect saved and flags before issuing another Flash operation.
    (void)flags;
}
```

## 8. Edge Cases

| Situation | Behaviour |
| --- | --- |
| Called from an interrupt | Not allowed — main loop only, SysTick running. |
| Code runs from the bank being written | Instruction fetch and SysTick stall; the timeout is not a wall-clock guarantee. |
| `Timeout` returned | The hardware operation may still be running — wait for `ready()`. |
| Power loss while the full sector is erased | The last record can be lost (no second sector). |
| Corrupted payload | Not detected — no CRC. |

## 1. Зачем это нужно

Модуль состоит из двух уровней:

| Класс | Что делает |
| --- | --- |
| `flash_base` | Низкоуровневое блокирующее стирание и программирование внутренней Flash. |
| `flash_data` | Небольшое «хранилище настроек»: журнал записей фиксированного размера в **одной** зарезервированной единице стирания (секторе/странице). Сохранение новой версии добавляет запись; чтение возвращает последнюю завершённую. |

Приложение отвечает за резервирование области Flash (чтобы она не пересекалась с прошивкой) и за вызов операций из `main`.

## 2. Область поддержки и порядок вызова

- **Файлы:** `src/flash.hpp`, `src/flash.cpp`.
- **Семейства:** STM32F4, F7, G0. (L0 не реализован — у него другое стёртое значение и протокол программирования.)

**Правила вызова:**

- Вызывайте из **основного цикла** при работающем SysTick.
- Никогда — из прерываний и критических секций. Драйвер сам прерывания не выключает и не включает.
- Нельзя параллельно обращаться к изменяемому диапазону, исполнять код из изменяемой области и использовать перекрывающийся буфер-источник.

**Ожидание.** Ожидания используют `System::WaitBits()` и `System::GetTick()`. Проверка LOCK, очистка ошибок и завершение явно выполняются в методах записи/стирания; общая `wait_operation()` ждёт завершения и проверяет флаги ошибок Flash.

| Семейство | Предел на одну аппаратную операцию |
| --- | --- |
| F4/F7 | 50000 мс (50 с) |
| G0 | 1000 мс (1 с) |

Это значения ST HAL ([F4](https://raw.githubusercontent.com/STMicroelectronics/stm32f4xx-hal-driver/master/Src/stm32f4xx_hal_flash.c), [F7](https://raw.githubusercontent.com/STMicroelectronics/stm32f7xx-hal-driver/master/Src/stm32f7xx_hal_flash.c), [G0](https://raw.githubusercontent.com/STMicroelectronics/stm32g0xx-hal-driver/master/Inc/stm32g0xx_hal_flash.h)). Отсчёт начинается заново для каждой физической записи, а не один раз на весь буфер.

> **Ограничение таймаута.** Пока банк Flash занят, чтение из него останавливает выборку инструкций — в том числе обработчика SysTick и его вектора. `GetTick()` тогда не отражает реальное время. Перенос кода в RAM не выполняется.
>
> `Timeout` **не отменяет** аппаратную операцию. Перед дальнейшим доступом к Flash дождитесь `flash_base::ready()`. Пока контроллер занят, CR не очищается; следующая операция перезапишет поля после готовности. Для `flash_data` после таймаута повторите `SetUp()` перед чтением или продолжением журнала.

## 3. Карта и банки

**Откуда берётся карта.** `flash_config.h` (формат 4) генерируется драйверами из карты модели/режима, выбранной базовым проектом (исходные карты стирания остаются формата 3).

```cpp
// После проверки index < FLASH_SECTOR_COUNT:
const FlashSector page = GetFlashSector(index);   // {address, size, bank, number}
const uint32_t address = page.address;
```

- `GetFlashSector(index)` возвращает сектор по значению. Условие `index < FLASH_SECTOR_COUNT` обеспечивает вызывающий; `erase_sector()` проверяет свой аргумент сам.
- `number` — **аппаратный** селектор (SNB на F4/F7, PNB на G0), а не логический индекс. Пример: F429ZI 2 МиБ — второй банк начинается с `0x08100000`, логический индекс 12, селектор SNB 16.

**Равномерная и табличная геометрия.** Генератор определяет геометрию по данным, без списка семейств:

- *Равномерная:* одинаковый размер страниц, последовательные адреса и селекторы внутри банка, один или два банка по порядку адресов. Вычисляется константами и умножением — таблицы по строке на страницу нет. У каждого банка своё начало и первый селектор; размеры банков могут различаться, разрывы между ними (в том числе у G4) сохраняются.
- *Неравномерная:* остаётся внутренней таблицей `flash_sectors[]`.

Всегда используйте `GetFlashSector()` — он работает в обоих случаях. `STM32_FLASH_UNIFORM_PAGES` (1/0) выставляет генератор, это не пользовательская настройка. При равномерной геометрии `flash_sectors[]` **не объявлен** — прямую индексацию и range-for замените на `GetFlashSector()` и `FLASH_SECTOR_COUNT`.

**Обновление.** Драйверы и шаблон `STM32-base_files/cmake/flash_config.h.in` обновляются вместе; затем обновите кешированную копию шаблона и пересоздайте конфигурацию проекта. Устаревший формат 3 отклоняется явно. Универсальная геометрия не переносит сами операции Flash на семейства кроме F4/F7/G0.

**Банки:**

- Режим по умолчанию следует `FLASH_DUAL_BANK`.
- `init()` **не меняет** option bytes. Он сверяет явный аргумент с картой, проверяет аппаратный бит режима на переключаемых МК и возвращает `InitError` при несовпадении или активном bank swap. МК только с одним или только с двумя банками используют свой фиксированный режим.
- Перед прямыми операциями вызовите `init()` один раз (с проверкой результата); у журнала это делает `SetUp()`. Разблокировка/стирание/запись режим повторно не проверяют — не меняйте режим и отображение банков во время работы.
- `mass_erase(маска)`: **1** — банк 1, **2** — банк 2, **3** — оба. Несуществующий банк или другая маска → `Error`.

## 4. Статусы операций и ширина записи

```cpp
static SysInitStatus init(bank_type tb = /* сгенерированный режим */);
static SysStatus enable_access();
static bool ready();
static SysStatus erase_sector(uint32_t sector);
static SysStatus mass_erase(uint8_t bank);
template<typename T>
static SysStatus write(uint32_t addr, const T* data, uint32_t size = 1);
template<typename T>
static T read(uint32_t addr);
```

**Возвращаемые значения:**

| Функция | Тип | Значения |
| --- | --- | --- |
| `init()`, `flash_data::SetUp()` | `SysInitStatus` | `InitOK` / `InitError` |
| `enable_access()`, `write()`, `erase_sector()`, `mass_erase()` | `SysStatus` | `OK`, `Error`, `Timeout` |
| `flash_data::write_data()` | `SysStatus` | `OK`, `Error`, `Timeout`, `NotInit` (до успешного `SetUp()`) |

Флаги ошибок контроллера остаются в `FLASH->SR` до следующей операции или `clear_errors()`. Сбрасываются только определённые флаги «запись единицы сбрасывает» (W1C), зарезервированные биты не трогаются.

**Разблокировка.** `enable_access()` читает реальный `CR.LOCK`, пишет ключи только если Flash заблокирована, и проверяет результат. Уже разблокирована → `OK`. Для прямой записи/стирания нужны успешные `init()` и затем `enable_access()`; программного флага «разблокировано» нет.

**`write<T>(addr, data, count)`:**

- размер элемента 1, 2, 4 или 8 байт; `count` — число элементов;
- `count = 0` → `OK` без операции;
- **вызывающий код проверяет** источник, переполнение размера, диапазон назначения и выравнивание — прямая запись их не проверяет и карту не обходит.

**`read<T>(addr)`** — прямое типизированное чтение; адрес должен быть допустимым и выровненным.

Аппаратная ширина и PSIZE выбираются при компиляции:

| Семейство | Аппаратная запись | Выравнивание назначения |
| --- | --- | --- |
| F4/F7 | 8/16/32 бит; 64-битный элемент пишется двумя отдельными 32-битными записями с проверкой каждой | 1/2/4 байта соответственно; для 64-битного элемента — 4 |
| G0 | 64 бит: два последовательных 32-битных обращения с ISB между ними | 8 байт |

**F4/F7** рассчитаны на **питание 3–3,3 В без внешнего VPP**: стирание — ×32, PSIZE ×64 не используется ([RM0090, параллелизм программирования](https://www.st.com/resource/en/reference_manual/rm0090-stm32f4xx-reference-manual-stmicroelectronics.pdf)).

**G0:**

- каждое 64-битное значение собирается через `memcpy`, поэтому источник может быть невыровненным;
- хвост дополняется `0xFF` — вызывающий код резервирует и проверяет **весь** дополненный блок; это дополнение потом нельзя запрограммировать отдельной записью;
- блоки из одних `0xFF` **не пропускаются**: их программирование меняет ECC, хотя данные по-прежнему читаются как `0xFF`.

После каждой аппаратной записи драйвер ждёт и проверяет SR, останавливаясь на первой ошибке. Поэтому запись буфера **не атомарна** — 64-битная запись на F4/F7 может прерваться после первой половины.

## 5. Кеш

До изменения Flash и после операции (в том числе после ошибки, когда контроллер готов) драйвер сбрасывает устаревшее содержимое кешей Flash:

| Семейство | Что сбрасывается |
| --- | --- |
| F7 | Только изменяемый диапазон Flash в D-cache Cortex-M7 (с округлением до 32-байтных линий); I-cache и ART — если включены |
| F4 | Кеши инструкций/данных Flash-акселератора, если включены |
| G0 | Кеш инструкций Flash, если включён |

- При массовом стирании обслуживаются выбранные банки.
- Глобальная очистка/инвалидация D-cache для SRAM не выполняется.
- Состояние включения кешей сохраняется.
- Во время операции доступ к назначению запрещён — в том числе из callback и прерываний.

## 6. Журнал flash_data

**Формат записи:**

```text
F4/F7: [ статус: 1 байт ][ данные ] ...
G0:    [ готовность: 8 байт ][ невалидность: 8 байт ][ данные ][ дополнение ] ...
```

Заголовок — 1 байт на F4/F7 и **16 байт** на G0. Значения маркеров во Flash:

| Состояние записи | Статус F4/F7 | Первый блок G0 | Второй блок G0 |
| --- | --- | --- | --- |
| Свободно | `FF` | `FFFFFFFFFFFFFFFF` | `FFFFFFFFFFFFFFFF` |
| Идёт запись | `7F` | `00000000FFFFFFFF` | `FFFFFFFFFFFFFFFF` |
| Готово | `0F` | `0000000000000000` | `FFFFFFFFFFFFFFFF` |
| Невалидна | `00` | без изменения | `FFFFFFFF00000000` |

- На G0 любое нестёртое значение второго блока важнее первого; состояние определяется по обоим.
- `Data_Status` — единственное определение значений для записи, поиска и результатов API. На G0 `DATA_WRITING`/`DATA_OK` относятся к первому блоку, `DATA_NOT_VALID` — ко второму.
- Численные значения enum на G0 изменились по этой таблице — используйте именованные значения, а не числа. Значения F4/F7 не изменились. `DATA_CORRUPT` удалён.

**Размер записи (stride):**

```text
stride = header_size + ceil(size / sizeof(status_t)) * sizeof(status_t)
header_size = 1 (F4/F7) или 16 (G0)
```

Смещения хранятся в байтах и растут на `stride`. Проверка вместимости: `next_offset > sector.size - stride`; поиск ограничен `sector.size - stride`. Деления на размер записи нет.

**Поиск** читает маркеры **только на границах записей**, поэтому байты `0xFF` внутри данных/дополнения ему не мешают. Выбирается последняя готовая запись, новая добавляется после последнего занятого слота. Незавершённые, невалидные и неизвестные записи пропускаются целиком.

**`SetUp()`** **до** поиска проверяет сектор, буфер, ненулевой размер данных, переполнение stride, выравнивание и вместимость, затем разблокирует Flash. `InitOK` возвращается только при успехе. `stride == 0` означает «не настроен» (отдельного флага нет). Существующий журнал открывайте с **тем же** размером данных.

**`write_data()`** — результат каждого шага проверяется:

1. Записать маркер «идёт запись» в новый слот.
2. Записать данные после всего заголовка (второй блок G0 остаётся стёртым).
3. Записать маркер «готово» (первый блок).
4. Пометить предыдущую готовую запись невалидной, если она есть: байтом статуса на F4/F7, вторым 64-битным блоком на G0.

Что остаётся при сбое:

- До успеха шага 3 выбрана **прежняя** запись.
- После шага 3 выбрана **новая**, даже если шаг 4 не удался; `write_data()` тогда вернёт эту ошибку. Во Flash могут оказаться две готовые записи — следующий поиск выберет более позднюю.
- Неудачные слоты повторно не используются.

**`read_data()`** копирует только завершённую запись:

| Результат | Когда |
| --- | --- |
| `DATA_OK` | последняя завершённая запись скопирована в буфер |
| `NO_DATA` | журнал пуст |
| `DATA_NOT_VALID` | есть только незавершённые/невалидные/неизвестные записи, либо не было успешного `SetUp()` |

Целостность самих данных не проверяется (CRC нет).

**Почему изменился формат G0.** Прежний шаг фиксации перезаписывал одно ненулевое значение другим, что дало `PROGERR` в тесте на G031. Теперь первый блок завершается **полным 64-битным нулём** — разрешённым исключением повторного программирования основной Flash, — а второй блок пишется один раз, после фиксации более новой записи. См. [RM0444, программирование основной памяти / PROGERR](https://www.st.com.cn/resource/en/reference_manual/rm0444-stm32g0x1-advanced-armbased-32bit-mcus-stmicroelectronics.pdf).

**Несовместимость формата G0:** журналы со старым 8-байтным заголовком не читаются. Начните со стёртого сектора журнала; `SetUp()` не стирает и не преобразует старые записи. Формат F4/F7 не изменился.

> **Ограничение одного сектора:**
>
> - Когда сектор заполнен, он стирается перед следующей записью. Потеря питания во время стирания/перезаписи может уничтожить последнюю сохранённую версию.
> - Ошибка стирания сбрасывает выбор записи в RAM — перед дальнейшей работой повторите `SetUp()`.
> - Нет CRC и восстановления через второй сектор.
> - На Flash с ECC оборванное программирование может вызвать ECCD/NMI при последующем чтении; обработчика восстановления NMI нет.
>
> Одних статусов недостаточно для восстановления после любого обрыва аппаратной операции — см. [ST AN4894, устойчивость эмуляции EEPROM](https://www.st.com/content/st_com/en/technical-documents/an4894-how-to-use-eeprom-emulation-on-stm32-mcus-stmicroelectronics_asset/chunk-003-topic-an4894-high-cycle-data-area-of-flash-memory.html).

## 7. Примеры использования

Используйте сектор, **зарезервированный под настройки**, и никогда — сектор с кодом.

**Байтовый буфер с `constinit`** (рекомендуется — без кода при старте):

```cpp
#include "flash.hpp"

static uint8_t payload[16]{};
// Только пример: блок стирания 3 должен быть явно зарезервирован вне образа прошивки.
constinit flash_data settings(3, payload, sizeof payload);

// В main, после инициализации System/RCC:
if (settings.SetUp() == SysInitStatus::InitOK) {
    auto saved = settings.read_data();
    // Если saved != DATA_OK, заполните payload значениями по умолчанию.
    // При сохранении: проверьте settings.write_data() == SysStatus::OK.
}
```

**Структура с проверкой ошибок.** `reinterpret_cast` не является константным выражением, поэтому такой объект не может быть `constinit` и создаётся во время работы внутри `main`:

```cpp
struct Settings { uint32_t threshold; uint16_t mode; };
Settings cfg{100, 1};

flash_data storage(settings_sector, reinterpret_cast<uint8_t*>(&cfg), sizeof(cfg));
if (storage.SetUp() != SysInitStatus::InitOK) {
    // Обработка ошибки инициализации.
    return;
}
if (storage.read_data() == flash_data::Data_Status::DATA_OK) {
    // В cfg — последняя завершённая запись.
}
cfg.threshold = 150;
const SysStatus saved = storage.write_data();
if (saved != SysStatus::OK) {
    const uint32_t flags = FLASH->SR;
    // Разберите saved и flags до следующей операции с Flash.
    (void)flags;
}
```

## 8. Угловые случаи

| Ситуация | Поведение |
| --- | --- |
| Вызов из прерывания | Запрещено — только основной цикл при работающем SysTick. |
| Код исполняется из записываемого банка | Выборка инструкций и SysTick останавливаются; таймаут не гарантирует реальное время. |
| Вернулся `Timeout` | Аппаратная операция может ещё идти — дождитесь `ready()`. |
| Потеря питания при стирании заполненного сектора | Последняя запись может быть потеряна (второго сектора нет). |
| Повреждённые данные | Не обнаруживаются — CRC нет. |
