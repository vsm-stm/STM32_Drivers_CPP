### 1. Why this is needed

#### Standard CMSIS approach

```c
// Hard-wired to a specific object
extern "C" void USART1_IRQHandler(void) {
    my_usart.HandleIRQ();        // only this one object, forever
}
extern "C" void SPI1_IRQHandler(void) {
    my_spi.HandleIRQ();
}
// ... dozens of such functions
```

**Problems:**
- Each handler is a separate global function tied to a specific object.
- Two objects sharing one IRQ (a shared DMA vector) — no built-in solution.
- Doesn't let you swap the handler at runtime (e.g. when reconfiguring a peripheral).
- All the ISR code is scattered across different files.

#### The IRQ_Registry approach

```c
// All the stubs are identical — they just call the dispatcher
extern "C" void USART1_IRQHandler(void) { IRQ_Registry::Dispatch(USART1_IRQn); }
extern "C" void SPI1_IRQHandler(void)   { IRQ_Registry::Dispatch(SPI1_IRQn);   }
extern "C" void DMA1_Channel2_3_IRQHandler(void) { IRQ_Registry::Dispatch(DMA1_Channel2_3_IRQn); }
```

Who actually handles it is decided at initialization time, through `Register()`.
The handler can be swapped at runtime. Two objects sharing one vector is supported natively.

### 3. Files and their roles

```
cmake/functions.cmake
  └─ stm32_generate_irq_handlers()
       ├─ computes IRQ_TABLE_SIZE from the MCU's vector table
       ├─ picks IRQ_MAX_SHARED by family (G0→3, F4/F7→2)
       └─ generates irq_registry_config.h via configure_file()

cmsis-core/.../cmake/irq_registry_config.h.in    ← template
  #define IRQ_TABLE_SIZE @IRQ_TABLE_SIZE@
  #define IRQ_MAX_SHARED @IRQ_MAX_SHARED@
  #include "irq_registry.hpp"
  IIRQHandler* IRQ_Registry::_table[IRQ_TABLE_SIZE][IRQ_MAX_SHARED] = {};
  extern "C" void XXX_IRQHandler() { Dispatch(XXX_IRQn); }
  ...

cmsis-core/.../Device/Include/irq_registry_config.h    ← generated file
  #define IRQ_TABLE_SIZE 30   ← exact vector count for STM32G030
  #define IRQ_MAX_SHARED 3    ← maximum for G0
  (all stubs substituted in)

Drivers/src/irq_registry.hpp    ← driver, untouched by CMake
  #ifndef IRQ_MAX_SHARED
  #  define IRQ_MAX_SHARED 3   ← default for direct-include
  #endif
  class IRQ_Registry {
      static constexpr int MAX_PER_IRQ = IRQ_MAX_SHARED;
      static IIRQHandler* _table[][MAX_PER_IRQ];   ← open-ended first index
  };

Drivers/src/irq_registry.cpp    ← implementation of Register/Unregister/Dispatch
```

#### Why the first index of _table isn't fixed in the header

In C++ it is legal to declare a static array with an open-ended first dimension:

```cpp
// hpp — declaration
static IIRQHandler* _table[][MAX_PER_IRQ];   // [] — incomplete type, OK

// cpp (via irq_registry_config.h) — definition
IIRQHandler* IRQ_Registry::_table[IRQ_TABLE_SIZE][MAX_PER_IRQ] = {};  // the size is set here
```

This lets `IRQ_TABLE_SIZE` live only in the generated file, rather than in the driver's header.

### 4. The _table array — internal structure

```
_table[IRQ_TABLE_SIZE][IRQ_MAX_SHARED]

  IRQn_Type (an enum) is cast to int → this is the row index
  Each row holds up to IRQ_MAX_SHARED pointers to handlers

  Example for STM32G030 (IRQ_TABLE_SIZE=30, IRQ_MAX_SHARED=3):

  _table[30][3]  →  30 * 3 * 4 bytes = 360 bytes in .bss (zeroed at startup)

  Columns are filled in registration order:
  Register(IRQn, A)  →  _table[IRQn][0] = A
  Register(IRQn, B)  →  _table[IRQn][1] = B
  Register(IRQn, C)  →  _table[IRQn][2] = C
  Register(IRQn, D)  →  BKPT! (all slots taken)
```

#### IRQ_MAX_SHARED by family

| Family | Value | Reason |
|-----------|----------|---------|
| STM32G0 | **3** | `DMA1_Ch4_5_DMAMUX1_OVR_IRQn` = ch4 + ch5 + DMAMUX overrun |
| STM32F4 | **2** | Timer pairs: `TIM1_UP_TIM10`, `TIM8_UP_TIM13`, ... DMA has separate vectors |
| STM32F7 | **2** | Same as F4 |
| Default | **2** | A safe fallback value |

The overall maximum across all families = **3** (used as the default in `irq_registry.hpp`).

### 5. Include order and IRQ_MAX_SHARED

Problem: `irq_registry.hpp` needs to know `IRQ_MAX_SHARED`, but it cannot include
`irq_registry_config.h` (that would create a circular dependency).

Solution: `IRQ_MAX_SHARED` is defined **before** `#include "irq_registry.hpp"` in the config
file.

```
Path 1: tim.cpp  →  tim.hpp  →  irq_registry.hpp
                                   ├─ IRQ_MAX_SHARED is not defined
                                   ├─ #ifndef IRQ_MAX_SHARED
                                   ├─ #  define IRQ_MAX_SHARED 3   ← default
                                   └─ MAX_PER_IRQ = 3

Path 2: irq_registry.cpp  →  irq_registry_config.h
                                   ├─ #define IRQ_TABLE_SIZE 30
                                   ├─ #define IRQ_MAX_SHARED 3    ← from CMake
                                   └─ #include "irq_registry.hpp"
                                             ├─ IRQ_MAX_SHARED is already = 3
                                             ├─ #ifndef → skipped
                                             └─ MAX_PER_IRQ = 3   ← from config
```

On both paths `MAX_PER_IRQ = 3` — the declaration and the definition of `_table` agree.

### 6. The full chain when an interrupt fires

#### Scenario: SPI1 DMA transfer complete (channel 2)

```
Hardware side:
  ┌──────────────────────────────────────────────────────────┐
  │  DMA1_Channel2 has finished the transfer                 │
  │  → sets TCIF2 in DMA1->ISR (bit 5)                       │
  │  → signals the NVIC about DMA1_Channel2_3_IRQn (idx=10)  │
  └────────────────────────┬─────────────────────────────────┘
                           │
  Cortex-M hardware stacking (12 cycles):
  ┌──────────────────────────────────────────────────────────┐
  │  Pushes to the stack: xPSR, PC, LR, r12, r3, r2, r1, r0  │
  │  Loads PC from the vector table → DMA1_Channel2_3_IRQHandler │
  └────────────────────────┬─────────────────────────────────┘
                           │
  ISR stub:
  ┌──────────────────────────────────────────────────────────┐
  │  extern "C" void DMA1_Channel2_3_IRQHandler() {          │
  │      IRQ_Registry::Dispatch(DMA1_Channel2_3_IRQn);       │
  │  }                                                       │
  │  ≈ 2 instructions: MOVS r0, #10  / B Dispatch            │
  └────────────────────────┬─────────────────────────────────┘
                           │
  Dispatch(idx=10):
  ┌──────────────────────────────────────────────────────────┐
  │  if (idx < 0 || idx >= IRQ_TABLE_SIZE) return;           │
  │      // 10 < 30 → OK                                     │
  │                                                          │
  │  s=0: h = _table[10][0] = &NX_Front_spi  (not null)     │
  │       → NX_Front_spi.HandleIRQ()                        │
  │                                                          │
  │  s=1: h = _table[10][1] = &ws_tim        (not null)     │
  │       → ws_tim.HandleIRQ()                               │
  │                                                          │
  │  s=2: h = _table[10][2] = nullptr → break                │
  └────────┬───────────────────────────┬─────────────────────┘
           │                           │
           ▼                           ▼
  NX_Front_spi.HandleIRQ()        ws_tim.HandleIRQ()
  ┌─────────────────────────┐     ┌─────────────────────────┐
  │ GetTC_Flag():           │     │ GetTC_Flag():           │
  │ DMA1->ISR & TCIF2       │     │ DMA1->ISR & TCIF3       │
  │ = 1  → THIS IS MY CHANNEL│    │ = 0  → not mine → return │
  │                         │     └─────────────────────────┘
  │ Stream_EN(DISABLE)      │
  │ ClearFlags()  (TCIF2=0) │
  │ _dma_busy = false       │
  │ OnDmaTxComplete()       │
  └─────────────────────────┘
                           │
  Return from the interrupt:
  ┌──────────────────────────────────────────────────────────┐
  │  Cortex-M restores from the stack: xPSR, PC, LR, ...     │
  │  Main code execution continues                            │
  └──────────────────────────────────────────────────────────┘
```

#### Scenario: WS2812B transfer complete (channel 3)

```
DMA1_Channel3 → TCIF3=1 → NVIC → ISR stub → Dispatch(10)

  s=0: NX_Front_spi.HandleIRQ()
       GetTC_Flag() → TCIF2 = 0 → not mine → return   (1 read of DMA1->ISR)

  s=1: ws_tim.HandleIRQ()
       GetTC_Flag() → TCIF3 = 1 → MY CHANNEL
       Stream_EN(DISABLE)
       ClearFlags()
       TIMx->DIER &= ~TIM_DIER_UDE   // disable the timer's DMA request
       _dma_busy = false
       _dma_cb()                      // on_transfer_done()
```

### 7. Latency estimate in clock cycles

#### What happens from the signal to the first instruction of HandleIRQ

##### Fixed hardware portion (the same for ALL approaches)

| Phase | Cortex-M0/M0+ (G0) | Cortex-M4 (F4) | Cortex-M7 (F7) |
|------|--------------------|-----------------|--------------------|
| Context save (8 registers pushed to the stack) | **12 cycles** | **12 cycles** | **12 cycles** |
| Loading PC from the vector table | included in the 12 | included in the 12 | included in the 12 |
| **Total hardware latency** | **12** | **12** | **12** |

> On M4/M7 with an FPU and lazy stacking — still the same 12 cycles; FPU registers are only
> saved lazily, when actually used.

#### Software portion: IRQ_Registry overhead

The stub is just an entry point reached from the vector. It doesn't add a "phase of its own":
in any approach, the NVIC jumps to *some* function. The stub's overhead is only the call to
Dispatch (`MOVS r0 + B.W` = 3 cycles on M0, 1-2 cycles on M4/M7). That's exactly why it is
folded into the Dispatch row instead of being broken out separately.

```
Stub (entry point reached from the vector — the same in any approach):
  MOVS r0, #<IRQn>             1 cycle
  B.W  IRQ_Registry::Dispatch  2 cycles (M0) / 1 cycle (M4/M7)
  ↑ this is the ENTIRE stub overhead

Dispatch():
  Bounds check (CMP + BLT)  2 cycles
  Computing the address of _table[idx][0]:
    idx * IRQ_MAX_SHARED * 4   3-5 cycles (M0: no single-cycle MUL)
                                1-2 cycles (M4/M7: MUL in 1 cycle)
  LDR h = _table[idx][0]      2 cycles (SRAM, 0 wait states)
  CBZ h, skip                  1 cycle
  Virtual call h->HandleIRQ():
    LDR r1, [h]                2 cycles (loading the vtable pointer)
    LDR r2, [r1, #offset]      2 cycles (function pointer taken from the vtable)
    BLX r2                     2-3 cycles
  If slot[1] is not null — one more such cycle
```

| Phase | M0/M0+ (G0, 64 MHz) | M4 (F4, 168 MHz) | M7 (F7, 216 MHz) |
|------|---------------------|------------------|------------------|
| Call to Dispatch from the stub (BL) | 3 / **47 ns** | 2 / **12 ns** | 1 / **5 ns** |
| Bounds check | 2 / **31 ns** | 2 / **12 ns** | 1 / **5 ns** |
| Addressing _table[idx][s] | 5 / **78 ns** | 2 / **12 ns** | 2 / **9 ns** |
| Loading the pointer from SRAM | 2 / **31 ns** | 2 / **12 ns** | 1 / **5 ns** |
| Null check + branch | 2 / **31 ns** | 1 / **6 ns** | 1 / **5 ns** |
| Virtual call (vtable) | 6 / **94 ns** | 4 / **24 ns** | 3 / **14 ns** |
| **Total Dispatch overhead** | **~20 cycles / ~310 ns** | **~13 cycles / ~77 ns** | **~9 cycles / ~42 ns** |
| **+ hardware latency** | **+12 / +188 ns** | **+12 / +71 ns** | **+12 / +56 ns** |
| **Total latency to HandleIRQ** | **~32 cycles / ~500 ns** | **~25 cycles / ~148 ns** | **~21 cycles / ~97 ns** |

> Figures are approximate — they depend on code alignment, cache state (M7), and the pipeline.
> M0 has no branch pipeline and no single-cycle multiplication — all the numbers above are
> pessimistic for it.

#### Additional overhead for a second handler (shared IRQ)

If the first handler **did not fire** (its flag isn't set), `HandleIRQ()` performs one read of
an ISR register and `return`s. Roughly:

| MCU | Cost of a "dry" HandleIRQ call |
|----|---------------------------|
| M0 (G0) | ~8-12 cycles (~125-188 ns) |
| M4 (F4) | ~4-6 cycles (~24-36 ns) |
| M7 (F7) | ~3-4 cycles (~14-19 ns) |

### 8. Comparison with the direct approach

#### Option A: direct call, no virtual dispatch (C style)

```c
extern "C" void USART1_IRQHandler(void) {
    // direct handling code
    if (USART1->ISR & USART_ISR_RXNE) { buf[idx++] = USART1->RDR; }
}
```

| Phase | M0 (G0) | M4 (F4) | M7 (F7) |
|------|---------|---------|---------|
| Hardware latency | 12 | 12 | 12 |
| Software overhead | **0** | **0** | **0** |
| **Total** | **12** | **12** | **12** |

The minimum possible latency. But: the code is awkward to work with and not reusable.

#### Option B: direct method call (no registry)

```cpp
extern "C" void USART1_IRQHandler(void) {
    my_usart.HandleIRQ();   // direct call, HandleIRQ() is virtual
}
```

| Phase | M0 (G0) | M4 (F4) | M7 (F7) |
|------|---------|---------|---------|
| Hardware latency | 12 | 12 | 12 |
| Call to HandleIRQ (virtual) | ~6 | ~4 | ~3 |
| **Total** | **~18** | **~16** | **~15** |

#### Option C: IRQ_Registry (the current approach)

| Phase | M0 (G0) | M4 (F4) | M7 (F7) |
|------|---------|---------|---------|
| Hardware latency | 12 | 12 | 12 |
| Dispatch + vtable (through the stub) | ~20 | ~13 | ~9 |
| **Total** | **~32** | **~25** | **~21** |

#### Summary table: extra cycles of IRQ_Registry vs. a direct virtual call

```
                 M0/G0 (64 MHz)    M4/F4 (168 MHz)    M7/F7 (216 MHz)
                 ──────────────    ───────────────    ───────────────
  Overhead        ~14 cycles         ~9 cycles          ~6 cycles
  Time            ~219 ns            ~54 ns             ~28 ns
  % of 1 ms       0.022%             0.005%             0.003%
```

**Conclusion:** IRQ_Registry's overhead is under 0.025% of a typical task period (1 ms).
This only becomes significant for interrupts above 100 kHz running on an M0 — for example,
direct DMA-less UART at 4 Mbaud. In every other case the overhead is negligible.

#### When the overhead matters

| Scenario | IRQ frequency | G0 overhead | Critical? |
|----------|-------------|-------------|-----------|
| UART 115200 | 11520 Hz | 2.5 us/s | No |
| SPI 10 MHz (per-byte IRQ) | 10 MHz | 2190 us/s (0.2% CPU) | No |
| WS2812B DMA TC | 1 Hz | 219 ns/s | No |
| Encoder 1 MHz | 1 MHz | 219 us/s (0.02% CPU) | No |
| ADC continuous 1 MSPS | 1 MHz | 219 us/s | Borderline |

### 9. Edge cases

#### 9.1 One object in several slots (TIM1)

TIM1 on G0 has TWO separate vectors: `TIM1_BRK_UP_TRG_COM` and `TIM1_CC`.
`IRQ_en()` registers the very same object into both slots:

```cpp
Register(TIM1_BRK_UP_TRG_COM_IRQn, this);  // _table[13][0] = this
Register(TIM1_CC_IRQn,              this);  // _table[14][0] = this
```

With a **two-dimensional array** this is safe: every IRQn has its own independent row.
A single object may sit in any number of rows at the same time.

Why an **intrusive linked list (`_irq_next`)** breaks in this case:

```
Register(TIM1_BRK_UP, ws_tim):  _table[13] = ws_tim, ws_tim._next = null
Register(TIM1_CC,     ws_tim):  _table[14] = ws_tim, ws_tim._next = null  ← OK so far

Register(DMA_ch23,    spi):     _table[10] = spi, spi._next = null
Register(DMA_ch23,    ws_tim):  spi._next = ws_tim, ws_tim._next = null   ← OK

// Someone registers yet another handler for TIM1_BRK_UP:
Register(TIM1_BRK_UP, third):  ws_tim._next = third  ← CORRUPTED!

// Now the DMA dispatch:
Dispatch(DMA_ch23):
  slot[0] = spi    → spi.HandleIRQ()    ← correct
  slot[1] = ws_tim → ws_tim.HandleIRQ() ← correct
  next via _next = third               ← NO! third was registered for TIM1, not DMA!
```

The **two-dimensional array** is completely free of this problem: every row of _table is
independent.

#### 9.2 Shared DMA vector (DMA1_Channel2_3)

```
Registration:
  NX_Front_spi.AttachDMA(&dma_nx_front_tx) → Register(DMA1_Ch2_3_IRQn, &NX_Front_spi)
  ws_tim.AttachDMA(&dma_ws)                → Register(DMA1_Ch2_3_IRQn, &ws_tim)

  _table[10][0] = &NX_Front_spi
  _table[10][1] = &ws_tim

Dispatch(10):
  We always call [0] and [1].
  Each one checks ITS OWN bit in DMA1->ISR — the wasted call costs ~10 cycles.
```

#### 9.3 DMAMUX1 Overrun (G0-specific)

The vector `DMA1_Ch4_5_DMAMUX1_OVR_IRQn` combines three sources.
`IRQ_MAX_SHARED = 3` makes it possible to register all three:

```cpp
Register(DMA1_Ch4_5_DMAMUX1_OVR_IRQn, &spi_handler);    // slot[0]
Register(DMA1_Ch4_5_DMAMUX1_OVR_IRQn, &i2c_handler);    // slot[1]
Register(DMA1_Ch4_5_DMAMUX1_OVR_IRQn, &dmamux_handler); // slot[2]
```

### 10. Adding a new vector

#### If CMake generation works

Just run CMake — it will automatically add a stub for the new vector if it shows up in the
MCU's vector table.

#### Manual addition (without cmake)

**Step 1** — add a stub to `irq_registry_config.h`:
```cpp
extern "C" void NEW_PERIPH_IRQHandler() {
    IRQ_Registry::Dispatch(NEW_PERIPH_IRQn);
}
```

**Step 2** — check `IRQ_TABLE_SIZE`:
```
NEW_PERIPH_IRQn must be < IRQ_TABLE_SIZE
If not — increase #define IRQ_TABLE_SIZE in the config file
```

**Step 3** — registration inside the driver (done automatically via `IRQ_en()`):
```cpp
IRQ_Registry::Register(NEW_PERIPH_IRQn, this);
NVIC_EnableIRQ(NEW_PERIPH_IRQn);
```

#### If a third handler is needed on a shared vector

`IRQ_MAX_SHARED = 3` already supports this. Just call `Register` once more — slot [2] gets
filled. If all three are already taken, attempting to register a fourth triggers `BKPT`.

### 11. Registration without inheritance (function handlers)

Up to this point, the only way to handle an interrupt has been to inherit `IIRQHandler` and
implement `HandleIRQ()`. For a one-off or test handler (not a full-fledged driver), creating a
dedicated class is overkill. For that there is a second overload of `Register()`:

```cpp
using IRQHandlerFn = void (*)(void* ctx);
static bool Register(IRQn_Type irqn, IRQHandlerFn fn, void* ctx = nullptr);
```

Example — an ordinary function with context:

```cpp
void OnButtonIrq(void* ctx)
{
    auto* btn = static_cast<Button*>(ctx);
    btn->Poll();
}

Button my_button;
IRQ_Registry::Register(EXTI0_IRQn, OnButtonIrq, &my_button);
NVIC_EnableIRQ(EXTI0_IRQn);
```

Or a non-capturing lambda (the context can be ignored when it isn't needed):

```cpp
IRQ_Registry::Register(EXTI1_IRQn, [](void* /*ctx*/) {
    // handler body
});
NVIC_EnableIRQ(EXTI1_IRQn);
```

#### How this works

- Inside `Register(irqn, fn, ctx)` an adapter `FunctionHandler : IIRQHandler` is created (a
  private nested class of `IRQ_Registry`), whose `HandleIRQ()` simply calls `fn(ctx)`.
- Adapters are taken one at a time from a fixed-size static pool,
  `IRQ_MAX_FUNCTION_HANDLERS` (8 by default; overridable with a `#define` placed before
  `#include "irq_registry.hpp"` / `irq_registry_config.h`). The pool is shared across all IRQ
  lines — this is not the same thing as `IRQ_MAX_SHARED` (the limit for a single line).
  Pool slots are never freed: `Unregister()` only clears the `_table` row, same as for an
  ordinary `IIRQHandler*`.
- The adapter is then registered the usual way — through `Register(irqn, IIRQHandler*)`, so
  the same `IRQ_MAX_SHARED` rules apply, along with the same `BKPT` on overflow of a `_table`
  row.
- If the adapter pool itself is exhausted (the number of function registrations exceeds
  `IRQ_MAX_FUNCTION_HANDLERS`) — `BKPT` fires here too; in that case the constant needs to be
  increased.
- `fn` and `ctx` must stay valid forever — just like any `IIRQHandler*` passed to
  `Register()`.

#### When to use it

Function registration is a quick way to attach a handler "for one case" (a one-off diagnostic,
a simple callback) without declaring a separate class. For full-fledged drivers with several
states and methods, inheriting `IIRQHandler` is still preferable — it is clearer and doesn't
consume slots from the shared pool.

### Handler lifecycle

```
Initialization                       Interrupt                      Deinitialization
───────────────                      ──────────                     ────────────────

uart.SetUp()                         NVIC fires                    uart.IRQ_en(RXNE, DISABLE)
  └─ lookup in usart_table              │                            ├─ CR1 &= ~RXNEIE
       │                               ▼                            ├─ all CR1 IRQ bits == 0
       └─ _info → irq = USART1_IRQn  ISR stub                       ├─ Unregister(USART1_IRQn)
                                        │                            │   _table[27] = {0,0,0}
uart.IRQ_en(RXNE, ENABLE)             Dispatch(27)                  └─ NVIC_DisableIRQ(USART1_IRQn)
  ├─ CR1 |= RXNEIE                      │
  ├─ NVIC_GetEnableIRQ() == 0         _table[27][0] = &uart
  │   (first time)                      │
  ├─ Register(USART1_IRQn, this)       uart.HandleIRQ()
  │   _table[27][0] = &uart              ├─ ISR & RXNE → read RDR
  └─ NVIC_EnableIRQ(USART1_IRQn)       └─ return from ISR
```

### Usage examples

#### Via inheritance (a real driver — USART)

This is how all the "real" drivers in `Drivers/src` work (`USART`, `SPI`, `TIM`, `RTC`, `ADC`):
the class inherits `IIRQHandler`, and registration with `IRQ_Registry` is hidden inside the
driver, happening automatically when a specific interrupt source is enabled.

```cpp
// uart.hpp (simplified)
class USART : public IIRQHandler
{
public:
    inline void IRQ_en(IRQ irq, FunctionalState en)
    {
        if (en) USARTx->CR1 |= static_cast<uint32_t>(irq);
        else    USARTx->CR1 &= ~static_cast<uint32_t>(irq);

        // First time any source is enabled — register and enable the NVIC.
        if (en && !NVIC_GetEnableIRQ(_info->irq)) {
            IRQ_Registry::Register(_info->irq, this);
            NVIC_EnableIRQ(_info->irq);
        }
        // Last source disabled — leave the registry and the NVIC.
        else if (!en && /* all CR1 sources are disabled */ true) {
            IRQ_Registry::Unregister(_info->irq);
            NVIC_DisableIRQ(_info->irq);
        }
    }

private:
    void HandleIRQ() override final;   // called from Dispatch()
};

// uart.cpp
void USART::HandleIRQ()
{
    if (USARTx->SR & USART_SR_RXNE) {
        uint8_t byte = USARTx->DR;
        // ... handling of the received byte ...
    }
}
```

```cpp
// main.cpp — the user just needs to call SetUp() and enable the needed source:
USART uart(USART1, 115200, USART::_1::TX::PA9, USART::_1::RX::PA10);
uart.SetUp();
uart.IRQ_en(USART::IRQ::RXNE, ENABLE);   // registration with IRQ_Registry happens inside IRQ_en()
```

The user never calls `IRQ_Registry::Register()` directly — the driver does it on their behalf.
This is the standard path for peripherals that have several interrupt sources and internal
state (buffers, DMA, flags).

#### Direct registration without inheritance (an ordinary function)

For a one-off handler (say, a button on EXTI, or diagnostics on a specific vector), when
writing a separate class would be overkill — we attach an ordinary function directly, without
a single line tied to `IIRQHandler`:

```cpp
// button.cpp
struct Button { volatile bool pressed = false; };
Button my_button;

void OnButtonIrq(void* ctx)
{
    auto* btn = static_cast<Button*>(ctx);
    if (EXTI->PR1 & EXTI_PR1_PIF0) {
        EXTI->PR1 = EXTI_PR1_PIF0;   // clear the flag by writing 1
        btn->pressed = true;
    }
}

void SetupButtonIrq()
{
    IRQ_Registry::Register(EXTI0_IRQn, OnButtonIrq, &my_button);
    NVIC_EnableIRQ(EXTI0_IRQn);
}
```

Or shorter still, a non-capturing lambda instead of a separate function — convenient when the
handler is only used in one place and doesn't need to be referred to by name anywhere else:

```cpp
IRQ_Registry::Register(EXTI1_IRQn, [](void*) {
    if (EXTI->PR1 & EXTI_PR1_PIF1) {
        EXTI->PR1 = EXTI_PR1_PIF1;
        // ...
    }
});
NVIC_EnableIRQ(EXTI1_IRQn);
```

The difference from the first example: no class at all, no `HandleIRQ()` — only a function and
(optionally) a pointer to the data it works with. For the mechanics — the adapter pool, the
`IRQ_MAX_FUNCTION_HANDLERS` limit — see [section 11](#11-registration-without-inheritance-function-handlers).

### 1. Зачем это нужно

#### Стандартный подход CMSIS

```c
// Жёстко привязано к конкретному объекту
extern "C" void USART1_IRQHandler(void) {
    my_usart.HandleIRQ();        // только этот объект, навсегда
}
extern "C" void SPI1_IRQHandler(void) {
    my_spi.HandleIRQ();
}
// ... десятки таких функций
```

**Проблемы:**
- Каждый обработчик — отдельная глобальная функция, привязанная к конкретному объекту.
- Два объекта на одном IRQ (общий DMA-вектор) — нет встроенного решения.
- Не позволяет менять обработчик в рантайме (например, при реконфигурации периферии).
- Весь ISR-код разбросан по разным файлам.

#### Подход IRQ_Registry

```c
// Все стабы одинаковые — просто вызывают диспетчер
extern "C" void USART1_IRQHandler(void) { IRQ_Registry::Dispatch(USART1_IRQn); }
extern "C" void SPI1_IRQHandler(void)   { IRQ_Registry::Dispatch(SPI1_IRQn);   }
extern "C" void DMA1_Channel2_3_IRQHandler(void) { IRQ_Registry::Dispatch(DMA1_Channel2_3_IRQn); }
```

Кто будет обрабатывать — определяется при инициализации через `Register()`.
Обработчик можно переключить в рантайме. Два объекта на одном векторе — поддерживается нативно.

```
cmsis-core/.../Device/Include/irq_registry_config.h    ← сгенерированный файл

  #endif
  class IRQ_Registry {
      static constexpr int MAX_PER_IRQ = IRQ_MAX_SHARED;

  };

Drivers/src/irq_registry.cpp    ← реализация Register/Unregister/Dispatch
```

#### Почему первый индекс _table не задан в заголовке

В C++ допустимо объявить статический массив с незакрытым первым измерением:

```cpp
// hpp — объявление
static IIRQHandler* _table[][MAX_PER_IRQ];   // [] — неполный тип, OK

// cpp (через irq_registry_config.h) — определение
IIRQHandler* IRQ_Registry::_table[IRQ_TABLE_SIZE][MAX_PER_IRQ] = {};  // задаём размер
```

Это позволяет `IRQ_TABLE_SIZE` жить только в сгенерированном файле, а не в заголовке драйвера.

### 4. Таблица _table — устройство

```
_table[IRQ_TABLE_SIZE][IRQ_MAX_SHARED]

  IRQn_Type (enum) кастуется в int → это индекс строки
  Каждая строка — до IRQ_MAX_SHARED указателей на обработчики

  Пример для STM32G030 (IRQ_TABLE_SIZE=30, IRQ_MAX_SHARED=3):

  _table[30][3]  →  30 * 3 * 4 байта = 360 байт в .bss (нули при старте)

  Столбцы заполняются в порядке регистрации:
  Register(IRQn, A)  →  _table[IRQn][0] = A
  Register(IRQn, B)  →  _table[IRQn][1] = B
  Register(IRQn, C)  →  _table[IRQn][2] = C
  Register(IRQn, D)  →  BKPT! (все слоты заняты)
```

#### IRQ_MAX_SHARED по семействам

| Семейство | Значение | Причина |
|-----------|----------|---------|
| STM32G0 | **3** | `DMA1_Ch4_5_DMAMUX1_OVR_IRQn` = ch4 + ch5 + DMAMUX overrun |
| STM32F4 | **2** | Пары таймеров: `TIM1_UP_TIM10`, `TIM8_UP_TIM13`, ... DMA имеет отдельные векторы |
| STM32F7 | **2** | Аналогично F4 |
| Default | **2** | Безопасное значение |

Общий максимум по всем семействам = **3** (используется как дефолт в `irq_registry.hpp`).

### 5. Порядок include и IRQ_MAX_SHARED

Проблема: `irq_registry.hpp` нужно знать `IRQ_MAX_SHARED`, но он не может включать `irq_registry_config.h` (это создаст циклическую зависимость).

Решение: `IRQ_MAX_SHARED` определяется **до** `#include "irq_registry.hpp"` в config-файле.

```
Путь 1: tim.cpp  →  tim.hpp  →  irq_registry.hpp
                                   ├─ IRQ_MAX_SHARED не определён
                                   ├─ #ifndef IRQ_MAX_SHARED
                                   ├─ #  define IRQ_MAX_SHARED 3   ← дефолт
                                   └─ MAX_PER_IRQ = 3

Путь 2: irq_registry.cpp  →  irq_registry_config.h
                                   ├─ #define IRQ_TABLE_SIZE 30
                                   ├─ #define IRQ_MAX_SHARED 3    ← CMake
                                   └─ #include "irq_registry.hpp"
                                             ├─ IRQ_MAX_SHARED уже = 3
                                             ├─ #ifndef → пропускается
                                             └─ MAX_PER_IRQ = 3   ← из config
```

В обоих путях `MAX_PER_IRQ = 3` — объявление и определение `_table` совпадают.

### 7. Оценка задержки в тактах

#### Что происходит с момента сигнала до первой инструкции HandleIRQ

##### Фиксированная аппаратная часть (одинакова для ВСЕХ подходов)

| Фаза | Cortex-M0/M0+ (G0) | Cortex-M4 (F4) | Cortex-M7 (F7) |
|------|--------------------|-----------------|--------------------|
| Сохранение контекста (8 регистров в стек) | **12 тактов** | **12 тактов** | **12 тактов** |
| Загрузка PC из таблицы векторов | включено в 12 | включено в 12 | включено в 12 |
| **Итого аппаратная задержка** | **12** | **12** | **12** |

> На M4/M7 с FPU и lazy stacking — те же 12 тактов, FPU-регистры сохраняются лениво только при использовании.

#### Программная часть: IRQ_Registry overhead

Стаб — это просто точка входа из вектора. Он не добавляет "фазу сам по себе": в любом
подходе NVIC прыгает на какую-то функцию. Overhead стаба — только вызов Dispatch
(`MOVS r0 + B.W` = 3 такта на M0, 1-2 такта на M4/M7). Именно поэтому он входит в строку
Dispatch, а не выделяется отдельно.

```
Стаб (точка входа из вектора — одинакова в любом подходе):
  MOVS r0, #<IRQn>             1 такт
  B.W  IRQ_Registry::Dispatch  2 такта (M0) / 1 такт (M4/M7)
  ↑ это и есть ВЕСЬ overhead стаба

Dispatch():
  Bounds check (CMP + BLT)  2 такта
  Вычисление адреса _table[idx][0]:
    idx * IRQ_MAX_SHARED * 4   3-5 тактов (M0: нет одноциклового MUL)
                                1-2 такта  (M4/M7: MUL за 1 такт)
  LDR h = _table[idx][0]      2 такта (SRAM, 0 wait states)
  CBZ h, skip                  1 такт
  Виртуальный вызов h->HandleIRQ():
    LDR r1, [h]                2 такта (загрузка vtable pointer)
    LDR r2, [r1, #offset]      2 такта (указатель на функцию из vtable)
    BLX r2                     2-3 такта
  Если slot[1] не null — ещё один такой цикл
```

| Фаза | M0/M0+ (G0, 64 МГц) | M4 (F4, 168 МГц) | M7 (F7, 216 МГц) |
|------|---------------------|------------------|------------------|
| Вызов Dispatch из стаба (BL) | 3 / **47 нс** | 2 / **12 нс** | 1 / **5 нс** |
| Bounds check | 2 / **31 нс** | 2 / **12 нс** | 1 / **5 нс** |
| Адресация _table[idx][s] | 5 / **78 нс** | 2 / **12 нс** | 2 / **9 нс** |
| Загрузка указателя из SRAM | 2 / **31 нс** | 2 / **12 нс** | 1 / **5 нс** |
| Null-check + branch | 2 / **31 нс** | 1 / **6 нс** | 1 / **5 нс** |
| Виртуальный вызов (vtable) | 6 / **94 нс** | 4 / **24 нс** | 3 / **14 нс** |
| **Итого Dispatch overhead** | **~20 тактов / ~310 нс** | **~13 тактов / ~77 нс** | **~9 тактов / ~42 нс** |
| **+ аппаратная задержка** | **+12 / +188 нс** | **+12 / +71 нс** | **+12 / +56 нс** |
| **Полная задержка до HandleIRQ** | **~32 такта / ~500 нс** | **~25 тактов / ~148 нс** | **~21 такт / ~97 нс** |

> Цифры приближённые — зависят от выравнивания кода, состояния кэша (M7), конвейера.
> M0 не имеет конвейера ветвлений и одноцикловых умножений — все числа пессимистичны.

##### Дополнительный overhead для второго обработчика (shared IRQ)

Если первый обработчик **не сработал** (его флаг не установлен), `HandleIRQ()` выполняет одно чтение регистра ISR и `return`. Это примерно:

| МК | Цена "холостого" HandleIRQ |
|----|---------------------------|
| M0 (G0) | ~8-12 тактов (~125-188 нс) |
| M4 (F4) | ~4-6 тактов (~24-36 нс) |
| M7 (F7) | ~3-4 такта (~14-19 нс) |

### 8. Сравнение с прямым подходом

#### Вариант A: прямой вызов без виртуальности (C-стиль)

```c
extern "C" void USART1_IRQHandler(void) {
    // прямой код обработки
    if (USART1->ISR & USART_ISR_RXNE) { buf[idx++] = USART1->RDR; }
}
```

| Фаза | M0 (G0) | M4 (F4) | M7 (F7) |
|------|---------|---------|---------|
| Аппаратная задержка | 12 | 12 | 12 |
| Программный overhead | **0** | **0** | **0** |
| **Итого** | **12** | **12** | **12** |

Минимально возможная задержка. Но: код неудобен, не переиспользуем.

#### Вариант B: прямой вызов метода (без реестра)

```cpp
extern "C" void USART1_IRQHandler(void) {
    my_usart.HandleIRQ();   // прямой вызов, HandleIRQ() — виртуальный
}
```

| Фаза | M0 (G0) | M4 (F4) | M7 (F7) |
|------|---------|---------|---------|
| Аппаратная задержка | 12 | 12 | 12 |
| Вызов HandleIRQ (виртуальный) | ~6 | ~4 | ~3 |
| **Итого** | **~18** | **~16** | **~15** |

#### Вариант C: IRQ_Registry (текущий подход)

| Фаза | M0 (G0) | M4 (F4) | M7 (F7) |
|------|---------|---------|---------|
| Аппаратная задержка | 12 | 12 | 12 |
| Dispatch + vtable (через стаб) | ~20 | ~13 | ~9 |
| **Итого** | **~32** | **~25** | **~21** |

#### Итоговая таблица: дополнительные такты IRQ_Registry vs прямой виртуальный вызов

```
                 M0/G0 (64 МГц)    M4/F4 (168 МГц)    M7/F7 (216 МГц)
                 ──────────────    ───────────────    ───────────────
  Overhead        ~14 тактов         ~9 тактов          ~6 тактов
  Время           ~219 нс            ~54 нс             ~28 нс
  % от 1 мс       0.022%             0.005%             0.003%
```

**Вывод:** накладные расходы IRQ_Registry составляют менее 0.025% от типичного периода задачи (1 мс).
Это значимо только для прерываний с частотой выше 100 кГц при работе на M0 — например, прямой DMA-less UART на 4 Мбод.
В остальных случаях overhead пренебрежимо мал.

#### Когда overhead важен

| Сценарий | Частота IRQ | G0 overhead | Критично? |
|----------|-------------|-------------|-----------|
| UART 115200 | 11520 Гц | 2.5 мкс/с | Нет |
| SPI 10 МГц (байт IRQ) | 10 МГц | 2190 мкс/с (0.2% CPU) | Нет |
| WS2812B DMA TC | 1 Гц | 219 нс/с | Нет |
| Encoder 1 МГц | 1 МГц | 219 мкс/с (0.02% CPU) | Нет |
| ADC непрерывный 1 MSPS | 1 МГц | 219 мкс/с | На грани |

### 9. Угловые случаи

#### 9.1 Один объект в нескольких слотах (TIM1)

TIM1 на G0 имеет ДВА отдельных вектора: `TIM1_BRK_UP_TRG_COM` и `TIM1_CC`.
`IRQ_en()` регистрирует один и тот же объект в оба слота:

```cpp
Register(TIM1_BRK_UP_TRG_COM_IRQn, this);  // _table[13][0] = this
Register(TIM1_CC_IRQn,              this);  // _table[14][0] = this
```

С **двумерным массивом** это безопасно: у каждого IRQn — своя независимая строка.
Один объект может стоять в любом количестве строк одновременно.

Почему **intrusive linked list (`_irq_next`)** ломается в этом случае:

```
Register(TIM1_BRK_UP, ws_tim):  _table[13] = ws_tim, ws_tim._next = null
Register(TIM1_CC,     ws_tim):  _table[14] = ws_tim, ws_tim._next = null  ← OK пока

Register(DMA_ch23,    spi):     _table[10] = spi, spi._next = null
Register(DMA_ch23,    ws_tim):  spi._next = ws_tim, ws_tim._next = null   ← OK

// Кто-то регистрирует ещё одного для TIM1_BRK_UP:
Register(TIM1_BRK_UP, third):  ws_tim._next = third  ← ИСПОРЧЕНО!

// Теперь DMA dispatch:
Dispatch(DMA_ch23):
  slot[0] = spi    → spi.HandleIRQ()    ← корректно
  slot[1] = ws_tim → ws_tim.HandleIRQ() ← корректно
  сле адующий по _next = third          ← НЕТ! third зарегистрирован для TIM1, не DMA!
```

**Двумерный массив** этой проблемы лишён полностью: каждая строка _table независима.

#### 9.2 Shared DMA вектор (DMA1_Channel2_3)

```
Регистрация:
  NX_Front_spi.AttachDMA(&dma_nx_front_tx) → Register(DMA1_Ch2_3_IRQn, &NX_Front_spi)
  ws_tim.AttachDMA(&dma_ws)                → Register(DMA1_Ch2_3_IRQn, &ws_tim)

  _table[10][0] = &NX_Front_spi
  _table[10][1] = &ws_tim

Dispatch(10):
  Вызываем [0] и [1] всегда.
  Каждый проверяет СВОЙ бит в DMA1->ISR — лишний вызов стоит ~10 тактов.
```

#### 9.3 DMAMUX1 Overrun (G0 специфика)

Вектор `DMA1_Ch4_5_DMAMUX1_OVR_IRQn` объединяет три источника.
`IRQ_MAX_SHARED = 3` позволяет зарегистрировать все три:

```cpp
Register(DMA1_Ch4_5_DMAMUX1_OVR_IRQn, &spi_handler);    // slot[0]
Register(DMA1_Ch4_5_DMAMUX1_OVR_IRQn, &i2c_handler);    // slot[1]
Register(DMA1_Ch4_5_DMAMUX1_OVR_IRQn, &dmamux_handler); // slot[2]
```

### 10. Добавление нового вектора

#### Если CMake-генерация работает

Просто запустить CMake — он автоматически добавит стаб для нового вектора
если он появится в таблице векторов МК.

#### Ручное добавление (без cmake)

**Шаг 1** — добавить стаб в `irq_registry_config.h`:
```cpp
extern "C" void NEW_PERIPH_IRQHandler() {
    IRQ_Registry::Dispatch(NEW_PERIPH_IRQn);
}
```

**Шаг 2** — проверить `IRQ_TABLE_SIZE`:
```
NEW_PERIPH_IRQn должен быть < IRQ_TABLE_SIZE
Если нет — увеличить #define IRQ_TABLE_SIZE в config-файле
```

**Шаг 3** — регистрация в драйвере (делается автоматически через `IRQ_en()`):
```cpp
IRQ_Registry::Register(NEW_PERIPH_IRQn, this);
NVIC_EnableIRQ(NEW_PERIPH_IRQn);
```

#### Если нужен третий обработчик на общем векторе

`IRQ_MAX_SHARED = 3` уже поддерживает это. Просто вызвать `Register` ещё раз — слот [2] заполнится.
Если все три уже заняты — при попытке зарегистрировать четвёртый сработает `BKPT`.

### 11. Регистрация без наследования (function-обработчики)

До этого момента единственный способ обработать прерывание — унаследовать `IIRQHandler` и
реализовать `HandleIRQ()`. Для одноразового или тестового обработчика (не полноценного драйвера)
заводить отдельный класс избыточно. Для этого есть вторая перегрузка `Register()`:

```cpp
using IRQHandlerFn = void (*)(void* ctx);
static bool Register(IRQn_Type irqn, IRQHandlerFn fn, void* ctx = nullptr);
```

Пример — обычная функция с контекстом:

```cpp
void OnButtonIrq(void* ctx)
{
    auto* btn = static_cast<Button*>(ctx);
    btn->Poll();
}

Button my_button;
IRQ_Registry::Register(EXTI0_IRQn, OnButtonIrq, &my_button);
NVIC_EnableIRQ(EXTI0_IRQn);
```

Или non-capturing lambda (context можно игнорировать, если не нужен):

```cpp
IRQ_Registry::Register(EXTI1_IRQn, [](void* /*ctx*/) {
    // тело обработчика
});
NVIC_EnableIRQ(EXTI1_IRQn);
```

#### Как это устроено

- Внутри `Register(irqn, fn, ctx)` создаётся адаптер `FunctionHandler : IIRQHandler`
  (приватный вложенный класс `IRQ_Registry`), чей `HandleIRQ()` просто вызывает `fn(ctx)`.
- Адаптеры берутся по одному из статического пула фиксированного размера
  `IRQ_MAX_FUNCTION_HANDLERS` (по умолчанию 8; переопределяется `#define`'ом до
  `#include "irq_registry.hpp"` / `irq_registry_config.h`). Пул один общий для всех
  IRQ-линий — это не то же самое, что `IRQ_MAX_SHARED` (лимит на одну линию).
  Слоты пула не освобождаются: `Unregister()` очищает только строку `_table`, как и для
  обычных `IIRQHandler*`.
- Дальше адаптер регистрируется обычным способом — через
  `Register(irqn, IIRQHandler*)`, поэтому действуют те же правила по `IRQ_MAX_SHARED`
  и тот же `BKPT` при переполнении строки `_table`.
- Если исчерпан сам пул адаптеров (превышено число function-регистраций
  `IRQ_MAX_FUNCTION_HANDLERS`) — тоже срабатывает `BKPT`; в этом случае нужно увеличить
  константу.
- `fn` и `ctx` должны оставаться валидными вечно — как и любой `IIRQHandler*`,
  передаваемый в `Register()`.

#### Когда использовать

Function-регистрация — быстрый способ повесить обработчик "для одного случая"
(разовая диагностика, простой callback) без объявления отдельного класса.
Для полноценных драйверов с несколькими состояниями и методами наследование
`IIRQHandler` по-прежнему предпочтительнее — оно нагляднее и не расходует слоты
общего пула.

### Жизненный цикл обработчика

```
Инициализация                        Прерывание                    Деинициализация
─────────────                        ──────────                    ───────────────

uart.SetUp()                         NVIC fires                    uart.IRQ_en(RXNE, DISABLE)
  └─ lookup в usart_table               │                            ├─ CR1 &= ~RXNEIE
       │                               ▼                            ├─ все CR1 IRQ bits == 0
       └─ _info → irq = USART1_IRQn  ISR-стаб                      ├─ Unregister(USART1_IRQn)
                                        │                            │   _table[27] = {0,0,0}
uart.IRQ_en(RXNE, ENABLE)             Dispatch(27)                  └─ NVIC_DisableIRQ(USART1_IRQn)
  ├─ CR1 |= RXNEIE                      │
  ├─ NVIC_GetEnableIRQ() == 0         _table[27][0] = &uart
  │   (первый раз)                      │
  ├─ Register(USART1_IRQn, this)       uart.HandleIRQ()
  │   _table[27][0] = &uart              ├─ ISR & RXNE → читаем RDR
  └─ NVIC_EnableIRQ(USART1_IRQn)       └─ return из ISR
```

### Примеры использования

#### Через наследование (реальный драйвер — USART)

Так работают все "настоящие" драйверы в `Drivers/src` (`USART`, `SPI`, `TIM`, `RTC`, `ADC`):
класс наследует `IIRQHandler`, а регистрация в `IRQ_Registry` спрятана внутри драйвера и
происходит автоматически при включении конкретного источника прерывания.

```cpp
// uart.hpp (упрощённо)
class USART : public IIRQHandler
{
public:
    inline void IRQ_en(IRQ irq, FunctionalState en)
    {
        if (en) USARTx->CR1 |= static_cast<uint32_t>(irq);
        else    USARTx->CR1 &= ~static_cast<uint32_t>(irq);

        // Первое включение любого источника — регистрируемся и включаем NVIC.
        if (en && !NVIC_GetEnableIRQ(_info->irq)) {
            IRQ_Registry::Register(_info->irq, this);
            NVIC_EnableIRQ(_info->irq);
        }
        // Последнее выключение — уходим из реестра и из NVIC.
        else if (!en && /* все источники CR1 выключены */ true) {
            IRQ_Registry::Unregister(_info->irq);
            NVIC_DisableIRQ(_info->irq);
        }
    }

private:
    void HandleIRQ() override final;   // вызывается из Dispatch()
};

// uart.cpp
void USART::HandleIRQ()
{
    if (USARTx->SR & USART_SR_RXNE) {
        uint8_t byte = USARTx->DR;
        // ... обработка принятого байта ...
    }
}
```

```cpp
// main.cpp — пользователю достаточно вызвать SetUp() и включить нужный источник:
USART uart(USART1, 115200, USART::_1::TX::PA9, USART::_1::RX::PA10);
uart.SetUp();
uart.IRQ_en(USART::IRQ::RXNE, ENABLE);   // регистрация в IRQ_Registry — внутри IRQ_en()
```

Пользователь ни разу не вызывает `IRQ_Registry::Register()` напрямую — за него это делает
драйвер. Это стандартный путь для периферии, у которой несколько источников прерываний
и внутреннее состояние (буферы, DMA, флаги).

#### Прямая регистрация без наследования (обычная функция)

Для разового обработчика (например, кнопка на EXTI, или диагностика на конкретном
векторе), когда писать отдельный класс избыточно — вешаем обычную функцию напрямую,
без единой строчки, связанной с `IIRQHandler`:

```cpp
// button.cpp
struct Button { volatile bool pressed = false; };
Button my_button;

void OnButtonIrq(void* ctx)
{
    auto* btn = static_cast<Button*>(ctx);
    if (EXTI->PR1 & EXTI_PR1_PIF0) {
        EXTI->PR1 = EXTI_PR1_PIF0;   // сброс флага записью 1
        btn->pressed = true;
    }
}

void SetupButtonIrq()
{
    IRQ_Registry::Register(EXTI0_IRQn, OnButtonIrq, &my_button);
    NVIC_EnableIRQ(EXTI0_IRQn);
}
```

Или ещё короче, non-capturing lambda вместо отдельной функции — удобно, когда
обработчик используется только в одном месте и не нужен снаружи по имени:

```cpp
IRQ_Registry::Register(EXTI1_IRQn, [](void*) {
    if (EXTI->PR1 & EXTI_PR1_PIF1) {
        EXTI->PR1 = EXTI_PR1_PIF1;
        // ...
    }
});
NVIC_EnableIRQ(EXTI1_IRQn);
```

Разница с первым примером: никакого класса, никакого `HandleIRQ()` — только функция
и (опционально) указатель на данные, с которыми она работает. Детали устройства —
пул адаптеров, лимит `IRQ_MAX_FUNCTION_HANDLERS` — см. [раздел 11](#11-регистрация-без-наследования-function-обработчики).
