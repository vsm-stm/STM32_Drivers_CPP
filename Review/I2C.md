# I2C: проблемы и предложения

Дата: 12.10.2026. Проверена рабочая копия; сборки и аппаратные тесты в этом проходе не запускались.

**Файлы:** [src/i2c.cpp](../src/i2c.cpp), [src/i2c.hpp](../src/i2c.hpp), [src/i2c_defs.hpp](../src/i2c_defs.hpp), [src/tools/i2c_timing_utility.c](../src/tools/i2c_timing_utility.c).

**Зависимости:** System/RCC/GPIO, DMA, IRQ Registry, C timing utility.

Статический разбор transfer engine выполнен по текущему коду. До согласования отсутствующих зависимостей I2C-1 сборка модуля невозможна; аппаратные сценарии ниже не считаются проверенными на плате.

## Список для обсуждения

### I2C-1 — P1 — Модуль требует отсутствующий API зависимостей

**Место:** [src/i2c.hpp](../src/i2c.hpp), строка 193.

**Проблема:** RequestSet не объявлен в DMA. В cpp используются SetUp(cfg,request), Release, CacheRxOk/Clean/Invalidate, GetTE_Flag/ClearTC_Flag, адресное Unregister/HasHandlers и несуществующий в текущих headers IrqLock. Таблицы ссылаются на отсутствующие I2c1::TX_alt, I2c3::RX_alt, I2c4; G0 I2c3 тоже отсутствует.

**Последствие / условие:** Текущая версия I2C не компилируется с текущими DMA/IRQ files; это рассогласование модулей, а не ошибка CMake include paths.

**Возможное решение:** Согласовать API DMA/IRQ и реальные request tables (DMA-2, IRQ-3/4). Вопрос локальной синхронизации решать при разборе I2C, без автоматического внедрения общего lock-фреймворка.

**Статус:** решение не принято, код в рамках этого обзора не изменён.

### I2C-2 — P1 — Timing utility не сбрасывает накопленный список вариантов

**Место:** [src/tools/i2c_timing_utility.c](../src/tools/i2c_timing_utility.c), строка 140.

**Проблема:** I2c_valid_timing_nbr статический и растёт на каждом I2C_GetTiming(), но не сбрасывается. Код пишет элемент массива до проверки >=128.

**Последствие / условие:** Повторные SetUp(), даже для разных I2C, используют старые timing candidates. После заполнения следующий вызов пишет за концом массива. Детали вынесены в [I2C_Timing.md](I2C_Timing.md).

**Возможное решение:** Сбросить счётчик в начале каждого расчёта и проверять вместимость до записи. Отдельно определить, допустимы ли одновременные расчёты, поскольку workspace общий.

**Статус:** решение не принято, код в рамках этого обзора не изменён.

### I2C-3 — P1 — Остановка DMA и выдача RX буфера не подтверждены аппаратно

**Место:** [src/i2c.cpp](../src/i2c.cpp), строка 648.

**Проблема:** Finish() очищает запросы, вызывает Stream_EN(DISABLE) и сразу CacheInvalidate. Текущий DMA только очищает EN. STOPF на шине сам по себе не подтверждает завершение всех записей DMA в SRAM.

**Последствие / условие:** После STOP/Abort/error callback может получить буфер, пока DMA ещё завершает транзакцию. Быстрый следующий start перенастраивает канал до полной остановки.

**Возможное решение:** Порядок: убрать периферийные DMA requests, подтвердить остановку DMA, обслужить RX cache, затем Idle/callback. Точечные примитивы остановки согласовать в DMA-4.

**Статус:** решение не принято, код в рамках этого обзора не изменён.

### I2C-4 — P2 — Кеш-контракт запрещает нормальные короткие RX пакеты F7

**Место:** [src/i2c.hpp](../src/i2c.hpp), строка 149.

**Проблема:** Документирован отказ DMA RX при len не кратной 32. Пример ReadReg_DMA(...,buf,14) этому противоречит; длина I2C пакета и объём принадлежащих буферу cache lines — разные величины.

**Последствие / условие:** Чтение 1/2/6/14 байтов DMA на F7 с включённым кешем недоступно даже из большого правильно выделенного буфера.

**Возможное решение:** Согласовать отдельную ёмкость/диапазон владения линиями и фактическую len передачи либо ясно ограничить API и пример. Не отключать D-cache и не вводить bounce buffers без решения пользователя.

**Статус:** решение не принято, код в рамках этого обзора не изменён.

### I2C-5 — P2 — В F4 Finish() вновь используется условное число проходов

**Место:** [src/i2c.cpp](../src/i2c.cpp), строка 661.

**Проблема:** Ожидание STOP ограничено SystemCoreClock/1000 итераций. Число итераций не является 1 мс; время зависит от оптимизации, памяти и содержимого цикла. Recover() использует такой же принцип и называет его ~25 кГц.

**Последствие / условие:** Предел ожидания и частота восстановления не обоснованы. Длинный цикл внутри IRQ/маски IRQ тормозит другие события.

**Возможное решение:** Для Finish согласовать неблокирующее ожидание STOP или завершение в main с реальным GetTick(). Для Recover использовать доступную документированную задержку; если выбран Delay_us(), CYCCNT должен быть заранее включён. Не добавлять скрытую шкалу «проходов».

**Статус:** решение не принято, код в рамках этого обзора не изменён.

### I2C-6 — P2 — Recover() не подтверждает высокий SCL на каждом импульсе

**Место:** [src/i2c.cpp](../src/i2c.cpp), строка 294.

**Проблема:** После отпускания open-drain SCL идёт только условная задержка, уровень SCL не читается до конца. STOP также формируется без подтверждённого SCL high.

**Последствие / условие:** При удерживаемом SCL/clock stretching фактических девяти тактов и STOP может не быть; возвращаемый Error уже не объясняет, на каком этапе восстановление не удалось.

**Возможное решение:** Описать Recover как операцию для заведомо зависшей single-master шины. Проверять release SCL по согласованному таймауту; не посылать recovery такты на нормально занятую другим master шину.

**Статус:** решение не принято, код в рамках этого обзора не изменён.

### I2C-7 — P2 — F4 polling не защищает короткие аппаратные последовательности приёма

**Место:** [src/i2c.cpp](../src/i2c.cpp), строка 558.

**Проблема:** В Poll mode Run() вызывает Process() без ограничения прерываний. ACK/POS, очистка ADDR и STOP для 1/2 последних байтов могут быть разделены длительным чужим ISR.

**Последствие / условие:** При неблагоприятном прерывании соблюдение последовательности ACK/STOP может нарушиться; timeout не исправляет уже отправленный ACK.

**Возможное решение:** При разборе F4 сверить последние 1/2/3 байта с RM и согласовать только необходимые короткие критические последовательности. Не помещать весь transfer engine/ожидания под запрет IRQ.

**Статус:** решение не принято, код в рамках этого обзора не изменён.

### I2C-8 — P2 — Асинхронная операция может оставаться Busy без доступного результата

**Место:** [src/i2c.cpp](../src/i2c.cpp), строка 154.

**Проблема:** IRQ/DMA режимы не имеют watchdog или срока. Если не приходит ожидаемое событие/STOP, завершения нет; Abort доступен, но callback/error при Abort намеренно подавляется.

**Последствие / условие:** Пользовательский while(IsBusy()) из примера может ждать бесконечно при физически зависшей шине.

**Возможное решение:** Сначала задокументировать обязанность main ограничивать ожидание по GetTick() и вызывать Abort/Recover. Если нужен timeout внутри API, отдельно согласовать простой способ обслуживания из main, без фоновых потоков.

**Статус:** решение не принято, код в рамках этого обзора не изменён.

### I2C-9 — P3 — Документация зависит от ещё не выбранной модели синхронизации

**Место:** [src/i2c.hpp](../src/i2c.hpp), строка 232.

**Проблема:** Комментарии ссылаются на IrqLock, Reserve/Config и callback-after-lock; в репозитории этого типа нет. Header обещает отсутствие DMA IRQ на G0/F7, хотя TE IRQ включается.

**Последствие / условие:** Публичное описание не соответствует доступным зависимостям и скрывает DMA error IRQ.

**Возможное решение:** После обсуждения привести описание к выбранной простой модели; исправить «нет DMA IRQ» на «TC завершает I2C STOP; DMA TE обрабатывается отдельно». Callback после выхода из локального участка всё равно выполняется в ISR.

**Статус:** решение не принято, код в рамках этого обзора не изменён.
