## Приоритеты и работа со списком

- **P1:** препятствие сборке заявленного пути, неправильные данные/регистры, доступ за границами, незавершаемая операция или потеря независимого обработчика.
- **P2:** ошибка в отдельном сценарии, ограничение поддержки, неполный контракт или вопрос поведения, который нужно согласовать.
- **P3:** документация, чистота кода, требования к типам и необязательные уточнения API.

Номера `RCC-1`, `DMA-2` и т. п. используются для обсуждения. Каждый пункт содержит место, условие/последствие и возможное решение. Предложения **не являются разрешением на исправление**. После выбора пользователя меняем только согласованный модуль и его необходимые зависимости; в отчёте помечаем решение и результат. Уже согласованные особенности System перечислены отдельно и не предлагаются заново к изменению.

## Общие зависимости

`System/RCC/GPIO` задают время, частоты и пины. `IRQ Registry` управляет dispatch и shared IRQ. `DMA` задаёт передачу, остановку, requests и cache contract. Дальше:

- UART → DMA/IRQ; Modbus → UART/DMA/GPIO DE.
- SPI → DMA/IRQ.
- TIM → DMA/IRQ; WS2812B → TIM_PWM/DMA.
- ADC → DMA/IRQ/TIM; актуального trigger API в TIM нет.
- I2C → DMA/IRQ/GPIO и I2C timing utility.
- Flash → generated sector map base_files; RTC → RCC/PWR/EXTI/IRQ.
- PID/CRC/containers не требуют hardware drivers; DSP подключается отдельно как внешний subset.

Повторяемые корневые вопросы: единый IRQ_MAX_SHARED и адресное unregister; минимальный согласованный DMA API; подтверждение остановки DMA; обслуживание кеша и владение его строками. Эти вопросы сначала согласуются в инфраструктуре, затем применяются в потребителях. В ADC вопрос IrqLock исключён из нового списка по прежнему решению пользователя.

## Предлагаемый порядок после System

1. RCC и GPIO/Flash — независимо друг от друга, по одному модулю.
2. IRQ Registry и DMA — определить минимальные общие API.
3. TIM, UART, SPI, I2C вместе со своим timing helper, ADC.
4. RTC, DAC, Modbus, WS2812B.
5. PID, CRC, DSP и контейнеры.
6. Проверка выбранных комбинаций с base по [Build.md](Build.md).

Порядок не фиксирует архитектуру и не запускает исправления автоматически.

## Что уже намеренно оставлено

- System::Init() выбирает HSI, делители /1, питание и Flash latency. Восстановления/отключения PLL/HSE в нём нет.
- Первые HSI waits без таймаута, ограничения SysTick описаны, новые IPSR/PRIMASK guards не предлагаются.
- L0 сохраняет прежнюю ограниченную ветку System; это не заявление поддержки всех драйверов L0.
- Карты Flash/base поддерживают согласованные single/dual режимы; в новой
  матрице использован текущий режим по умолчанию каждого устройства. Bank swap
  остаётся запрещённым; аппаратная проверка option bytes в этом прогоне не выполнялась.
- D-cache F7 сохраняется. Cache maintenance будем добавлять в transfer drivers по согласованным шагам, для нужных строк, с владением буфером CPU/DMA.
- CRC и базовые операции контейнеров не признаны неисправными из-за отсутствия аппаратных locks или универсального storage layer.

## Подтверждение после будущих правок

Для очередного модуля нужна base-сборка с реально вызываемым API и фактическими dependencies, а затем отдельные аппаратные сценарии. Простой include/компиляция объекта не доказывает link всех методов; успешный link не доказывает DMA, тайминги и работу на плате.

При изменении исходников строки в старом отчёте могут сдвинуться: сохраняем ID пункта и уточняем ссылку. Новая проверка должна отмечать, какие проблемы действительно устранены и на каких файлах/MCU это подтверждено.
