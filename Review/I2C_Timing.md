# I2C timing utility: проблемы и предложения

Дата: 12.10.2026. Проверена рабочая копия; сборки и аппаратные тесты в этом проходе не запускались.

**Файлы:** [src/tools/i2c_timing_utility.c](../src/tools/i2c_timing_utility.c), [src/tools/i2c_timing_utility.h](../src/tools/i2c_timing_utility.h).

**Зависимости:** C helper для TIMINGR I2C F7/G0; параметры должны соответствовать реальным фильтрам и фронтам шины.

## Список для обсуждения

### I2CT-1 — P1 — Счётчик кандидатов не сбрасывается и выходит за границу

**Место:** [src/tools/i2c_timing_utility.c](../src/tools/i2c_timing_utility.c), строка 126.

**Проблема:** Глобальный I2c_valid_timing_nbr не обнуляется в I2C_GetTiming(). Запись I2c_valid_timing[nbr] происходит до проверки границы в строке 242.

**Последствие / условие:** При repeated SetUp список растёт; новый расчёт смешивает разные clocks/speeds. После достижения 128 следующий расчёт пишет элемент 128 за пределами массива.

**Возможное решение:** Обнулить count для каждого вызова и проверять count < capacity перед записью. Корректный один вызов способен добавить не более одного candidate на каждый из 16 prescalers: текущая ёмкость 128 — отдельный вопрос экономии RAM.

**Статус:** решение не принято, код в рамках этого обзора не изменён.

### I2CT-2 — P2 — Общий workspace не позволяет независимые вложенные вызовы

**Место:** [src/tools/i2c_timing_utility.c](../src/tools/i2c_timing_utility.c), строка 126.

**Проблема:** Все I2C используют один static array/count; даже исправление сброса не сделает функцию reentrant.

**Последствие / условие:** SetUp двух I2C из разных вложенных контекстов может смешать candidates; обычный последовательный startup этим не затрагивается.

**Возможное решение:** Минимальный вариант: документировать последовательный вызов из main. Если вложенные вызовы действительно нужны, передавать workspace или хранить его локально с оценкой stack; не добавлять глобальную блокировку без требования.

**Статус:** решение не принято, код в рамках этого обзора не изменён.

### I2CT-3 — P2 — Расчёт использует номинальную скорость режима вместо входного запроса

**Место:** [src/tools/i2c_timing_utility.c](../src/tools/i2c_timing_utility.c), строка 150.

**Проблема:** i2c_freq выбирает только диапазон 80..120/320..480/800..1200 кГц; ti2cspeed дальше рассчитывается из фиксированных 100/400/1000 кГц. trise/tfall/filters жёстко зашиты.

**Последствие / условие:** Вызов utility с 90 кГц рассчитывает около 100 кГц; реальная RC-нагрузка шины может не соответствовать предположениям. Текущий I2C SPEED из трёх номиналов этим не нарушается.

**Возможное решение:** Либо явно ограничить utility тремя скоростями, либо учитывать requested frequency и согласованные board timings. Проверить соответствие analog filter/DNF фактическому CR1.

**Статус:** решение не принято, код в рамках этого обзора не изменён.

### I2CT-4 — P3 — C header не содержит собственного extern C guard

**Место:** [src/tools/i2c_timing_utility.h](../src/tools/i2c_timing_utility.h), строка 29.

**Проблема:** i2c.cpp вручную оборачивает include в extern C, но header публично виден через include directory и сам guard не содержит.

**Последствие / условие:** Прямой include из другого C++ файла объявит C++ symbol и приведёт к несовпадению с C object.

**Возможное решение:** Добавить обычный __cplusplus / extern C guard в header; убрать необходимость ручной обёртки в каждом потребителе.

**Статус:** решение не принято, код в рамках этого обзора не изменён.
