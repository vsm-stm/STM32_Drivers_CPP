# I2C timing utility: актуальные проблемы и предложения

Пересмотрено: **16.10.2026** по текущим исходникам.
Сборки и тесты в этом проходе не запускались; исходники не изменялись.
Номера I2CT-1…I2CT-4 сохранены.

**Файлы:** [i2c_timing_utility.c](../src/tools/i2c_timing_utility.c),
[i2c_timing_utility.h](../src/tools/i2c_timing_utility.h).
**Потребитель:** [I2C](I2C.md), расчёт TIMINGR на F7/G0.
F4 использует отдельный расчёт CCR/TRISE и этой utility не пользуется.

## I2CT-1 — P1 — Счётчик не сбрасывается; проверка границы стоит после записи

**Место:** [i2c_timing_utility.c:126](../src/tools/i2c_timing_utility.c#L126),
[i2c_timing_utility.c:140](../src/tools/i2c_timing_utility.c#L140),
[i2c_timing_utility.c:236](../src/tools/i2c_timing_utility.c#L236).

I2c_valid_timing_nbr общий и не обнуляется в I2C_GetTiming.
Повторный расчёт использует варианты для предыдущей частоты/скорости.
После заполнения 128 элементов следующий вызов начинает запись с индекса 128;
проверка границы выполняется уже после этой записи и инкремента счётчика.
Остановка/освобождение DMA и прочие изменения зависимостей это не исправили.

**Предложение:** сбрасывать счётчик перед каждым расчётом и проверять вместимость
до записи. Проверить последовательную настройку разных I2C с разными
скоростями/PCLK и повторный вызов utility.

**Статус:** открыто; непосредственно связано с I2C-2.

## I2CT-2 — P2 — Общий workspace требует последовательного вызова

**Место:** [i2c_timing_utility.c:126](../src/tools/i2c_timing_utility.c#L126).

Массив и счётчик общие для всех I2C. Даже исправленный сброс не сделает
вложенные/одновременные расчёты независимыми.
Обычная последовательная настройка из main после исправления I2CT-1 допустима.

**Предложение:** определить контракт вызова из main без вложенной настройки.
Если действительно нужны независимые контексты, отдельно согласовать
workspace и его размещение. Общую блокировку или расход stack автоматически
не добавлять.

**Статус:** ограничение контракта; не подтверждённая гонка при обычном startup.

## I2CT-3 — P2 — Входная частота выбирает номинал, параметры фронтов зашиты

**Место:** [i2c_timing_utility.c:80](../src/tools/i2c_timing_utility.c#L80),
[i2c_timing_utility.c:150](../src/tools/i2c_timing_utility.c#L150).

i2c_freq выбирает диапазон 80…120, 320…480 либо 800…1200 кГц.
Сам расчёт дальше использует соответственно 100, 400 либо 1000 кГц.
Например, прямой вызов utility для 90 кГц рассчитывает номинал 100 кГц.
Текущий публичный I2C::SPEED задаёт ровно три номинала — для его обычного
использования это расхождение входной частоты не возникает.

trise/tfall и фильтры также заданы константами. Текущий I2C после reset оставляет
analog filter включённым и DNF=0; это соответствует I2C_USE_ANALOG_FILTER=1
и I2C_DIGITAL_FILTER_COEF=0 в utility. Ошибка рассогласования фильтров сейчас
не подтверждается. Соответствие фронтов реальной плате код не устанавливает.

**Предложение:** явно описать три поддерживаемых номинала и предположения
о фронтах. Если нужны произвольные частоты/параметры платы, изменение входных
параметров и расчёта согласовать отдельно.

**Статус:** уточнено; без запроса расширять конфигурацию платы не предлагается.

## I2CT-4 — P3 — C header не содержит собственного extern C guard

**Место:** [i2c_timing_utility.h:29](../src/tools/i2c_timing_utility.h#L29).

i2c.cpp вручную оборачивает include в extern "C", поэтому его текущее подключение
правильно связывается с C-функцией. Прямой include из другого C++ файла
объявит символ с C++ linkage и не совпадёт с C object.

**Предложение:** поместить обычный __cplusplus / extern "C" guard в header,
чтобы потребителям не требовалось помнить ручную обёртку.

**Статус:** открыто; не является причиной текущей ошибки сборки самого i2c.cpp.

## I2CT-5 — P2 — Массив кандидатов занимает 2560 байт RAM

**Место:** [i2c_timing_utility.c:36](../src/tools/i2c_timing_utility.c#L36),
[i2c_timing_utility.c:126](../src/tools/i2c_timing_utility.c#L126).

128 элементов по пять uint32_t занимают 2560 байт статической RAM на STM32.
Корректный отдельный расчёт добавляет не более одного кандидата на каждый
из 16 значений prescaler. Накопление между расчётами не является полезной
вместимостью — это дефект I2CT-1. На младших G0 такой расход RAM существенен.

**Предложение:** после исправления счётчика согласовать сокращение массива
до 16 элементов либо поиск лучшего результата без большого списка.
Это альтернативы для обсуждения; реализация в этом проходе не выбиралась.

**Статус:** новое замечание по размеру, без изменений алгоритма.
