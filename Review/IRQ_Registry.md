# IRQ Registry: проблемы и предложения

Дата: 12.10.2026. Проверена рабочая копия; сборки и аппаратные тесты в этом проходе не запускались.

**Файлы:** [src/irq_registry.cpp](../src/irq_registry.cpp), [src/irq_registry.hpp](../src/irq_registry.hpp), [CMakeLists.txt](../CMakeLists.txt).

**Зависимости:** System, CMSIS NVIC; irq_registry_config.h.in и vector-файлы STM32-base_files.

## Список для обсуждения

### IRQ-1 — P1 — IRQ_MAX_SHARED различается между translation units

**Место:** [src/irq_registry.hpp](../src/irq_registry.hpp), строка 84.

**Проблема:** Обычные драйверы получают fallback IRQ_MAX_SHARED=3. irq_registry.cpp сначала включает сгенерированный config, где CMake для F4/F7 выставляет 2. Это меняет MAX_PER_IRQ и объявление _table в одном классе между файлами.

**Последствие / условие:** Нарушается единое определение класса; публичный лимит в драйвере не соответствует реально используемой таблице.

**Возможное решение:** Передавать один общий compile definition или включать общий header с константами во всех translation units. Сгенерированные ISR и определения таблицы оставить отдельно от header констант.

**Статус:** решение не принято, код в рамках этого обзора не изменён.

### IRQ-2 — P1 — Лимит двух обработчиков не покрывает три ADC F4/F7

**Место:** [CMakeLists.txt](../CMakeLists.txt), строка 57.

**Проблема:** IRQ_MAX_SHARED=2 для F4/F7, но ADC1/2/3 используют одну ADC_IRQn. Register() при заполнении всегда останавливает программу.

**Последствие / условие:** Регистрация IRQ всех трёх ADC невозможна даже после согласования API и определения IRQ-1.

**Возможное решение:** Выбрать общий лимит по максимальному числу реально используемых обработчиков либо дать проекту простую настройку. Для G0 учитывать число каналов общего IRQ выбранного MCU, а не только family name.

**Статус:** решение не принято, код в рамках этого обзора не изменён.

### IRQ-3 — P1 — Unregister() удаляет всю общую IRQ-строку

**Место:** [src/irq_registry.cpp](../src/irq_registry.cpp), строка 42.

**Проблема:** Есть только Unregister(irqn), а ADC/I2C уже вызывают Unregister(irqn,this) и HasHandlers(). TIM/UART/SPI/RTC используют удаление всей строки и NVIC state как признак своей регистрации.

**Последствие / условие:** Новые ADC/I2C не компилируются; выключение одного TIM/DMA/RTC обработчика отключает соседний. Уже включённый общий NVIC не означает, что текущий объект зарегистрирован.

**Возможное решение:** Согласовать адресное Unregister(irqn,handler) и HasHandlers(); каждый драйвер хранит факт своей регистрации и отключает NVIC только после удаления последнего обработчика.

**Статус:** решение не принято, код в рамках этого обзора не изменён.

### IRQ-4 — P1 — Повторная регистрация того же объекта расходует слоты

**Место:** [src/irq_registry.cpp](../src/irq_registry.cpp), строка 11.

**Проблема:** Register() не ищет существующий handler; всегда берёт следующий пустой слот. I2C BindDmaIrqs() прямо рассчитывает на идемпотентность и может зарегистрировать один объект дважды на shared TX/RX IRQ.

**Последствие / условие:** Повторные callbacks и останов при исчерпании таблицы, включая повторный AttachDMA().

**Возможное решение:** До вставки проверять, что этот указатель уже есть в строке; возвращать true без дубликата. Нулевой handler отвергать.

**Статус:** решение не принято, код в рамках этого обзора не изменён.

### IRQ-5 — P2 — Неудачная регистрация функции расходует adapter pool

**Место:** [src/irq_registry.cpp](../src/irq_registry.cpp), строка 37.

**Проблема:** Слот _function_pool_used увеличивается до проверки IRQ-номера. Unregister() не освобождает адаптеры; fn==nullptr тоже занимает слот.

**Последствие / условие:** Неверный IRQ возвращает false, но всё равно уменьшает доступную ёмкость. Циклы регистрации/удаления функций кончаются остановом после восьми выделений.

**Возможное решение:** Проверять IRQ/fn до выдачи адаптера. Для повторных регистраций выбрать контракт «только одна регистрация за жизнь» либо простое повторное использование освобождённых слотов.

**Статус:** решение не принято, код в рамках этого обзора не изменён.

### IRQ-6 — P2 — Изменение таблицы из callback не имеет определённого контракта

**Место:** [src/irq_registry.cpp](../src/irq_registry.cpp), строка 51.

**Проблема:** Dispatch() проходит живую таблицу, а Register/Unregister меняют её без ограничений. Обработчик может удалить/добавить соседей прямо во время обхода.

**Последствие / условие:** Новый handler может выполниться в том же IRQ; удалённый сосед может не выполниться. Пул функций также не рассчитан на вложенную модификацию.

**Возможное решение:** Описать допустимый порядок: регистрация до разрешения соответствующего IRQ, изменение из main при маскировке этой линии. Если изменения внутри callback нужны, сначала согласовать ожидаемую семантику; не добавлять универсальный механизм синхронизации.

**Статус:** решение не принято, код в рамках этого обзора не изменён.

### IRQ-7 — P3 — Комментарии обещают неподтверждённые свойства

**Место:** [src/irq_registry.hpp](../src/irq_registry.hpp), строка 60.

**Проблема:** Точные цифры тактов/процентов указаны без измерения конкретной сборки. Комментарий о Debug-only trap не соответствует безусловным __BKPT и while(1).

**Последствие / условие:** Читатель получает неверное представление о Release и стоимости диспетчера.

**Возможное решение:** Описывать порядок работы и ограничения без точных чисел до измерений. Либо вернуть false при заполнении, либо явно описать останов во всех сборках — выбор пользователя.

**Статус:** решение не принято, код в рамках этого обзора не изменён.
