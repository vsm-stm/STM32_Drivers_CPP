# SPI: проблемы и предложения

## Перенос DMAReq и выбор атомарности — 19.10.2026

- SPI_USE_ATOMIC в spi.hpp: 0 по умолчанию, 1 включает ATOMIC_* ST для управляющих
  битов и полей тактирования/сброса. SR/DR и W1C/rc_w0 не переводятся в RMW.
- Конструктор принимает DMAReq: именованные маршруты F4/F7 либо физические каналы
  G0. SPI содержит оба DMA_Sx. Принадлежность/направление F4/F7 и разные ресурсы
  TX/RX проверяются через DebugTrap в конструкторе. G0 сам выбирает TX/RX request.
- Дублирующая spi_dma_req_table удалена; SetUpDMA использует выбор конструктора.
- Подробные комментарии и примеры обновлены. Сборки и тесты не запускались.

## Чтение регистров и маска ошибок — 18.10.2026

- HandleIRQ читает CR2/SR один раз для начальных проверок ERR/RX/TX; повторных
  чтений CR2 в условиях и SR перед первым RX-кадром нет. Ошибочная ветка отключает
  источники записью CR2 из снимка. Последующие изменения CR2 через callbacks
  используют обычный read/modify/write, сохраняя изменённые биты.
- ReadErrors/DrainRx получают общий SR и остаток FIFO. На F4 обычный RX не
  перечитывает SR; на F7/G0 SR обновляется для следующего кадра. После DR при
  очистке OVR чтение SR обязательно и сохранено. Лимит кадров не изменён.
- CRCERR/FRE исключены из маски и enum Error: аппаратный CRC и TI mode не
  используются. Поддерживаются Overrun/ModeFault/DmaTx/DmaRx.
- По разрешению пользователя в DMA добавлен GetIRQFlags: один снимок TC и ошибок,
  без HT/FEIF. Обработчики DMA TX/RX SPI используют его вместо двух чтений ISR.
  Если запрос остановки создаёт TC после снимка, событие собирает следующий IRQ.
  Ожидание TC/TE в main-only DeInit также читает один снимок за проход.
- Process сохраняет свежее чтение физического статуса после проверки счётчиков:
  между начальным снимком и проверкой мог завершиться DMA IRQ. Finish проверяет
  ошибки после дочитывания хвоста и его callbacks. Ожидания в IRQ не добавлены.
- Комментарии, SPI.md и DMA.md обновлены. Выполнен просмотр исходников/diff;
  сборка, тесты и измерение ассемблера/тактов не запускались.

## Предел обработки FIFO в IRQ — 18.10.2026

По выбору пользователя чтение RX и отбрасывание при overrun ограничены глубиной
FIFO: F4 — один кадр; F7/G0 — четыре 8-битных либо два 16-битных кадра.
ReadErrors и DrainRx получают общий счётчик остатка на один вход в SPI IRQ:
два вызова не удваивают предел. NSS IRQ использует такой же предел.
Process дочитывает остановленный FIFO перед завершением. TX IRQ уже обрабатывает
не больше одного кадра. Изменения не вводят ожиданий и не меняют модель NSS/Process.
Публичный SPI API и привязки внешних DMA в этом шаге не менялись.
Комментарии и SPI.md обновлены; сборка/тесты/аппаратные измерения не запускались.

Обзор: 12.10.2026. Согласованные правки внесены: 15.10.2026.

## Исходные замечания и выполненные правки

Номера строк в описаниях ниже относятся к исходному обзору до правок.

### SPI-1 — P1 — PIN{} для SS приводит к доступу к адресу 0

**Место:** [src/spi.cpp](../src/spi.cpp), строка 97.

**Проблема:** SS необязателен в конструкторе, но SetUp() безусловно вызывает _ss.SetLevel(1); Software SlaveSelect() в master также безусловно пишет SS.

**Последствие / условие:** Пример из заголовка SPI(SPI1,SCK,MOSI) попадает в fault при SetUp(), даже при hardware NSS.

**Возможное решение:** Пропускать операции GPIO для невалидного SS и согласовать режим software NSS без управляемого пина. Общую проверку PIN::SetUp() см. GPIO-1.

**Статус:** Исправлено: SS остаётся необязательным параметром конструктора. Программный master пропускает операции с PIN{}; без SS выбор устройства выполняет приложение. Hard NSS требует пин.

### SPI-2 — P1 — Byte mode F7/G0 не настраивает RX FIFO threshold и ширину доступа

**Место:** [src/spi.cpp](../src/spi.cpp), строка 85.

**Проблема:** CR2 получает DS=7, но FRXTH остаётся 0. RXD() — uint32_t read; IRQ/polling сохраняют только uint8_t. Half_Word представлен enum, однако buffers и DMA width всегда Byte.

**Последствие / условие:** Ожидание RXNE для одного байта может зависнуть: threshold остаётся half-word. При доступе шире frame теряются/упаковываются байты; 16-bit mode не обслуживается корректно.

**Возможное решение:** Для Byte установить FRXTH и 8-bit DR accesses; для Half_Word реализовать 16-bit buffer/счётчик и DMA width либо пока отвергать режим. Источник: [ST F7 HAL SPI Init](https://raw.githubusercontent.com/STMicroelectronics/stm32f7xx-hal-driver/master/Src/stm32f7xx_hal_spi.c).

**Статус:** Исправлено: 8/16-битные перегрузки, доступ к DR выбранной ширины, FRXTH для Byte у F7/G0 и соответствующий размер DMA. len — количество кадров.

### SPI-3 — P1 — Timeout оставляет SPI и CS активными

**Место:** [src/spi.cpp](../src/spi.cpp), строка 148.

**Проблема:** Send() и Send_Receive() возвращают Timeout непосредственно из циклов, не выключая SPE и не снимая CS. Receive() делает cleanup только в собственном пути.

**Последствие / условие:** Внешнее устройство остаётся выбранным, следующая операция начинается из незавершённого состояния.

**Возможное решение:** Один короткий cleanup для всех выходов операции: прекратить передачу, убрать временный режим, снять CS, завершить status. Существующий spi_end_transfer() сейчас не вызывается и SS не снимает, несмотря на комментарий.

**Статус:** Исправлено: общий путь завершения останавливает источники/SPI/DMA, возвращает кеш и снимает автоматический SS. Timeout/Error сбрасывает очередь прерванного SPI.

### SPI-4 — P1 — Ожидание BSY в IRQ/RXONLY может никогда не закончиться

**Место:** [src/spi.cpp](../src/spi.cpp), строка 453.

**Проблема:** OnRxByte() и OnDmaRxComplete() ждут BSY=0 до выключения SPE. В RXONLY master включённый SPI продолжает генерировать приёмные такты. Все ожидания в callbacks бесконечны.

**Последствие / условие:** Receive_IRQ()/Receive_DMA() способны зависнуть внутри ISR и заблокировать остальную программу. Застрявший BSY slave также не имеет выхода.

**Возможное решение:** Для RXONLY соблюсти аппаратную последовательность остановки генерации до ожидания завершения; для остальных режимов определить завершение без бесконечного busy-wait в IRQ. Сверить ограничения конкретного SPI IP/errata.

**Статус:** Исправлено: IRQ не ждёт BSY. Process() в main проверяет физическое завершение master; slave завершается по NssReleased() из пользовательского EXTI. RXONLY удалён.

### SPI-5 — P1 — TX не вычитывает принимаемые данные и не очищает ошибки

**Место:** [src/spi.cpp](../src/spi.cpp), строка 136.

**Проблема:** TYPE::TX не переключает SPI в однонаправленный режим; на full-duplex каждый TX создаёт RX. Send/Send_IRQ/Send_DMA не drain RX; OnError() пустой.

**Последствие / условие:** OVR и старые RXNE/FIFO данные остаются после TX. Следующий Receive/Send_Receive читает прошлые данные; ERRIE может вызвать повторяющийся IRQ.

**Возможное решение:** Для выбранного режима организовать discard RX или подходящий однонаправленный режим, очищать OVR установленной последовательностью. Error path должен завершать transfer и освобождать CS.

**Статус:** Обновлено 18.10.2026: направление фиксируется в конструкторе. TX использует BIDIMODE/BIDIOE без RX, RX — full duplex с dummy через TX IRQ у master; TXRX сохраняет обслуживание обеих сторон. Ошибки SPI/DMA завершаются через Process и OnError(mask).

### SPI-6 — P1 — DMA F7 не обслуживает кеш

**Место:** [src/spi.cpp](../src/spi.cpp), строка 293.

**Проблема:** Все TX/RX DMA методы работают напрямую с buffers без clean/invalidate, включая spi_dummy_byte.

**Последствие / условие:** Передаются старые TX данные, RX выглядит устаревшим либо перезаписывается грязными строками CPU.

**Возможное решение:** Внести обслуживание затронутых линий на границах передачи согласно DMA-8; RX буфер возвращать CPU после подтверждённой остановки. Dummy TX также должен быть доступен DMA и иметь согласованные атрибуты.

**Статус:** Исправлено: SPI вызывает System::CacheClean/CacheCleanInvalidate/CacheInvalidate на границах владения. Некешируемые области пропускает System; F4/G0 используют пустые helpers.

### SPI-7 — P2 — Hardware NSS фактически остаётся software NSS у master

**Место:** [src/spi.hpp](../src/spi.hpp), строка 89.

**Проблема:** Master_sel::Master включает SSM|SSI|MSTR. SetUp(Hard,Master) добавляет SSOE, но SSM не снимает.

**Последствие / условие:** Параметр Hard не задаёт ожидаемый режим внутреннего NSS; GPIO/NSS поведение расходится с API.

**Возможное решение:** Разделить бит выбора master и управление NSS; установить SSM/SSI/SSOE по выбранному NSS_ctrl. Проверить роль master/slave и поведение отсутствующего SS.

**Статус:** Исправлено: MSTR задаёт только роль; Software master включает SSM/SSI, Hard master — SSOE, Hard slave очищает SSM/SSOE.

### SPI-8 — P2 — AttachDMA() и transfer methods не проверяют InitOK/ошибки DMA

**Место:** [src/spi.cpp](../src/spi.cpp), строка 250.

**Проблема:** SetUp DMA result игнорируется; после ошибки выполняется Enable_IRQ(), который разыменовывает _info DMA. Blocking/IRQ методы отвергают только Busy, некоторые не проверяют pointers/len. len DMA uint32 без 65535 limit.

**Последствие / условие:** Запуск до SetUp(), неправильный/занятый DMA либо len>65535 приводит к fault или незавершённой операции.

**Возможное решение:** AttachDMA возвращает проверяемый статус; канал публикуется только при успехе. Единые простые входные проверки и лимит DMA; прежние ошибки не маскировать.

**Статус:** Обновлено 18.10.2026: DMA передаются в конструктор и настраиваются внутри SetUp, AttachDMA удалён. Проверки полного DMAReq, аргументов старта и результата настройки/регистрации сохранены. При отказе освобождаются только полученные этим SetUp ресурсы.

### SPI-9 — P2 — Режим и завершение передачи сохраняются непоследовательно

**Место:** [src/spi.cpp](../src/spi.cpp), строка 111.

**Проблема:** Receive() принудительно ставит RXONLY и снимает его независимо от setup; после SetUp(TYPE::RX) Send/Send_Receive не восстанавливают TXRX. Blocking методы не выставляют Busy, _status изменяется ISR без volatile.

**Последствие / условие:** Разрешённый API может запустить передачу в неподходящем CR1 mode; polling состояния из main может не увидеть завершение.

**Возможное решение:** Согласовать допустимые операции после каждого TYPE; задавать временные поля режима при каждом старте и восстанавливать договорённое idle state. Сделать видимым одиночный ISR/main status, без нового многопоточного слоя.

**Статус:** Обновлено 18.10.2026: направление неизменно и задаётся в конструкторе; BIDIMODE/BIDIOE фиксируются при SetUp только для TX, RXONLY не включается. Структура настроек остаётся в SetUp. Все старты выставляют Busy; завершение IRQ/DMA требует Process().

### SPI-10 — P2 — Shared IRQ и повторная регистрация зависят от состояния NVIC

**Место:** [src/spi.hpp](../src/spi.hpp), строка 266.

**Проблема:** IRQ_en ориентируется на NVIC enable, удаляет все handlers; AttachDMA() регистрирует заново и не учитывает результат. Ряд SPI runtime rows не совпадает с pin/DMA tables (SPI4 без pin/request table, SPI3 без capability guard).

**Последствие / условие:** Отключается чужой shared handler; повторное подключение расходует slots; поддержка устройства неоднородна.

**Возможное решение:** Применить согласованный IRQ-3/IRQ-4 API и синхронизировать capability guards/runtime/pin/request tables.

**Статус:** Обновлено 18.10.2026: SetUp отдельно регистрирует SPI, DMA TX и DMA RX. Общий вектор TX/RX использует две записи. DeInit удаляет только собственные записи. Таблицы SPI1–SPI6 F4/F7 и SPI1–SPI3 G0 сохранены.

### SPI-11 — P3 — Заголовок и cleanup helper дают ложные обещания

**Место:** [src/spi.hpp](../src/spi.hpp), строка 20.

**Проблема:** Примеры вызывают отсутствующий EnableNVIC_IRQ(); Receive docs обещают восстановить исходный RXONLY, cpp просто очищает его. spi_end_transfer self не использует и нигде не вызывается.

**Последствие / условие:** Часть кода выглядит остатком прежних правок и затрудняет валидацию.

**Возможное решение:** После выбора transfer contract убрать мёртвый helper/неиспользуемый self либо сделать его действующим cleanup, исправить примеры и комментарии.

**Статус:** Исправлено: комментарии и примеры обновлены в spi.hpp/spi.cpp/spi_defs.hpp, SPI.md и ReadMe.md. Описаны Process, NSS EXTI, dummy после TX, усечение, кеш и ограничения задержки обслуживания.

## Ограничения и проверка на плате

- В slave NSS обслуживает пользователь: EXTI по нарастающему фронту вызывает NssReleased(). Обработчики NSS/SPI/DMA не должны прерывать друг друга; следующий пакет начинается после Process() и повторного взведения.
- После заполнения RX сохраняется префикс с IsTruncated(); после TX передаются 0xFF/0xFFFF через TXE IRQ. Допустимая SCK зависит от задержки обслуживания.
- У IRQ/DMA нет внутреннего дедлайна; приложение при необходимости отменяет обмен через DeInit().
- Проверка корпуса/доступности вывода, DMA-доступности памяти и владения кеш-линиями остаётся за приложением.
- Сборка и работа на плате здесь не подтверждались. Для аппаратной проверки нужны короткий/длинный slave-пакет, TX dummy, 8/16 бит, IRQ/DMA, timeout/error, повторный запуск и F7 RX с кешем и без него.


## Изменение API — 18.10.2026

- Конструктор: `SPI(SPIx, Direction, SCK, MOSI={}, MISO={}, SS={}, dma_tx=nullptr, dma_rx=nullptr)`.
- Направление и DMA неизменны. Структура и перегрузки SetUp сохранены. Повторный SetUp — ошибка до DeInit.
- AttachDMA удалён; SetUp настраивает DMA и регистрирует три независимых обработчика. Реестр IRQ не менялся.
- TX использует только TX: нет RX DMA, RX IRQ или чтения RX на завершении.
- RX master: RX DMA и TX IRQ для dummy, второй DMA не нужен. RX slave не выдаёт dummy.
- Blocking/IRQ/DMA методы сохранены. Несовместимое с направлением действие возвращает Error.
- NSS/IRQ не ждут аппаратных флагов. F4/F7 фиксируют остановку по TC в DMA IRQ; Process остаётся Busy до завершения остановки и физического обмена.
- Slave завершается только по NSS. У G0 последний DMA-запрос должен быть обслужен до запроса остановки по NSS; остановленный счётчик читает Process. Ошибочные пакеты отбрасываются без использования длины.
- Кеш возвращается после остановки: успешный RX — записанный префикс, ошибка/отмена — весь выделенный RX-буфер. CPU не использует данные ошибочного пакета.
- DeInit вызывается из main; он может ждать остановку DMA и освобождает регистрации/ресурсы. Указатели из конструктора остаются для следующего SetUp.
- Комментарии, примеры, SPI.md, ReadMe.md, DMA.md и пример GPIO обновлены.

Проведён просмотр исходников и diff. Сборка, тесты и аппаратная проверка не запускались.
