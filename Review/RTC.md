# RTC: проблемы и предложения

Дата: 12.10.2026. Проверена рабочая копия; сборки и аппаратные тесты в этом проходе не запускались.

**Файлы:** [src/rtc.cpp](../src/rtc.cpp), [src/rtc.hpp](../src/rtc.hpp).

**Зависимости:** System, IRQ Registry, RCC/PWR/RTC/EXTI CMSIS. Реализован IP STM32G0; F4/F7 не имеют соответствующей ветки.

## Список для обсуждения

### RTC-1 — P1 — Ожидания не имеют выхода при отсутствии RTC clock

**Место:** [src/rtc.cpp](../src/rtc.cpp), строка 21.

**Проблема:** LSE/LSI readiness, INITF, ALRAWF/ALRBWF, WUTWF и RECALPF ожидаются бесконечно. SetUp разрешает CLK_Source::NO/HSE без полноценного запуска HSE/проверки готовности.

**Последствие / условие:** Без кварца или RTC clock вызов зависает; NO приводит к INITF wait с выключенным источником. Ошибка не отражается в SysInitStatus.

**Возможное решение:** Ввести простые статусы/таймауты по согласованному GetTick() при работоспособном SysTick; NO отвергать, HSE либо полноценно проверять, либо документировать обязательную подготовку. Источник времени/контекст IRQ явно указать.

**Статус:** решение не принято, код в рамках этого обзора не изменён.

### RTC-2 — P1 — RTCSEL меняется без политики backup domain

**Место:** [src/rtc.cpp](../src/rtc.cpp), строка 41.

**Проблема:** При already_running=false переписывается RTCSEL, но выбор существующего источника backup domain требует соответствующей процедуры reset. Код не возвращает ошибку при несовпадении и не проверяет фактическое применение.

**Последствие / условие:** Повторный SetUp с другим источником может сохранить старый clock, но вернуть InitOK; prescalers/ожидания перестают соответствовать источнику.

**Возможное решение:** По умолчанию вернуть ошибку для смены уже выбранного источника. Отдельный явно запрошенный reset backup domain допустим после обсуждения потери времени/backup registers.

**Статус:** решение не принято, код в рамках этого обзора не изменён.

### RTC-3 — P2 — GetTime() оставляет calendar shadow lock без чтения даты

**Место:** [src/rtc.hpp](../src/rtc.hpp), строка 255.

**Проблема:** Чтение TR блокирует обновление shadow-регистра даты до чтения DR. GetTime() не читает DR и не описывает обязательное парное чтение. Здесь не утверждается, что одно чтение TR само по себе замораживает младший регистр времени.

**Последствие / условие:** При повторных чтениях только времени shadow date остаётся прежней; позднее GetDate() может вернуть дату, не соответствующую последнему считанному времени, особенно при смене суток.

**Возможное решение:** Дать единый snapshot Time+Date либо документировать и обеспечить чтение DR после времени. Источник: [ST HAL RTC GetTime/GetDate](https://raw.githubusercontent.com/STMicroelectronics/stm32g0xx-hal-driver/master/Src/stm32g0xx_hal_rtc.c).

**Статус:** решение не принято, код в рамках этого обзора не изменён.

### RTC-4 — P2 — SetUp() не синхронизирует shadow registers после reset

**Место:** [src/rtc.cpp](../src/rtc.cpp), строка 36.

**Проблема:** already_running учитывает RTCEN/RTCSEL и сохраняет calendar, но после system reset не ждёт RSF. В комментарии прямо отмечено, что RSF очищается.

**Последствие / условие:** Сразу после SetUp чтение времени/даты может вернуть несинхронизированное shadow значение.

**Возможное решение:** Не переинициализировать calendar, но выполнить предусмотренную IP синхронизацию shadow с таймаутом, если BYPSHAD не выбран.

**Статус:** решение не принято, код в рамках этого обзора не изменён.

### RTC-5 — P1 — Timestamp IRQ объявлен, но не обслуживается

**Место:** [src/rtc.hpp](../src/rtc.hpp), строка 74.

**Проблема:** IRQ_s::TS разрешает TSIE. RtcHandler обрабатывает только WUTF/ALRAF/ALRBF и не снимает timestamp flag; enabled-source masks также не проверяются.

**Последствие / условие:** При включённом timestamp событие способно непрерывно вызывать IRQ. Общий RTC/TAMP IRQ может вызвать callback для выключенного RTC источника.

**Возможное решение:** Либо пока убрать TS из supported API, либо реализовать минимальные clear/read/callback для timestamp. Обрабатывать только включённые свои источники.

**Статус:** решение не принято, код в рамках этого обзора не изменён.

### RTC-6 — P1 — Регистрация на общей RTC/TAMP линии зависит от NVIC

**Место:** [src/rtc.hpp](../src/rtc.hpp), строка 382.

**Проблема:** Если TAMP ранее включил RTC_TAMP_IRQn, RTC handler не регистрируется. При последнем disable RTC удаляет всю IRQ строку и отключает NVIC.

**Последствие / условие:** RTC события теряются либо прекращается работа другого TAMP handler.

**Возможное решение:** Хранить факт own registration, применять адресное unregister и выключать NVIC только при отсутствии всех handlers. Зависимость IRQ-3.

**Статус:** решение не принято, код в рамках этого обзора не изменён.

### RTC-7 — P2 — Границы prescaler/calendar/alarm параметров не проверяются

**Место:** [src/rtc.cpp](../src/rtc.cpp), строка 49.

**Проблема:** PREDIV_A маскируется 0x7FFF, хотя поле 7-bit. SetTime/Date проверяют только общий to_bcd<=99, не диапазоны часов/минут/месяца/дня. Alarm subsecond/WUTR также принимают широкие типы без проверки.

**Последствие / условие:** Недопустимые значения попадают в соседние/зарезервированные поля либо создают некорректный calendar. SetUp LSI с default 127/255 рассчитан на 32768 Гц, не на номинальные 32000.

**Возможное решение:** Проверять реальные поля и возвращать ошибку. Для LSI выбрать делители по согласованной частоте/калибровке либо объяснить приблизительный ход часов.

**Статус:** решение не принято, код в рамках этого обзора не изменён.

### RTC-8 — P2 — Повторное arm не снимает stale RTC flags

**Место:** [src/rtc.hpp](../src/rtc.hpp), строка 311.

**Проблема:** Перед разрешением WUT/ALR не очищаются WUTF/ALRAF/ALRBF, callback заменяется до прекращения старой операции.

**Последствие / условие:** Событие прежнего таймера/будильника может немедленно вызвать новый callback, хотя новый период ещё не прошёл.

**Возможное решение:** При rearm сначала выключить свой источник, очистить его pending flag, записать настройки и callback, затем arm. Сохранить другие RTC/TAMP источники.

**Статус:** решение не принято, код в рамках этого обзора не изменён.

### RTC-9 — P3 — Комментарии WUT/MASKSS/инициализации неверны

**Место:** [src/rtc.hpp](../src/rtc.hpp), строка 293.

**Проблема:** WUCKSEL 000..011 описан как /2,/4,/8,/16; фактически /16,/8,/4,/2. 17-bit ck_spre код — 110, не указанный 101. MASKSS=0 не сравнивает subseconds, а не сравнивает все. Header SetUp описывает RSF вместо фактического RTCEN/RTCSEL check.

**Последствие / условие:** Пользователь задаёт другой период или маску по документации. Комментарий RECALPF о ≤2 RTCCLK тоже следует сверить с реальным calibration cycle.

**Возможное решение:** Исправить комментарии/примеры по [ST RTCEx constants](https://raw.githubusercontent.com/STMicroelectronics/stm32g0xx-hal-driver/master/Inc/stm32g0xx_hal_rtc_ex.h) и [ST alarm masks](https://raw.githubusercontent.com/STMicroelectronics/stm32g0xx-hal-driver/master/Inc/stm32g0xx_hal_rtc.h).

**Статус:** решение не принято, код в рамках этого обзора не изменён.

### RTC-10 — P2 — Ограничение G0 не закреплено на уровне выбора модуля

**Место:** [src/rtc.cpp](../src/rtc.cpp), строка 13.

**Проблема:** Header/cpp напрямую используют APBENR1, ICSR/SCR/SR и RTC_TAMP_IRQn G0. CMake позволяет запросить RTC на F4/F7.

**Последствие / условие:** Получается набор неясных compile errors вместо понятного ограничения поддержки. Это не дефект работающей ветки G0.

**Возможное решение:** Явно диагностировать unsupported family при выборе RTC. Новые family implementations добавлять только после отдельного решения; не подставлять похожие регистры.

**Статус:** решение не принято, код в рамках этого обзора не изменён.
