# Flash / flash_data: проблемы и предложения

Дата: 12.10.2026. Проверена рабочая копия; сборки и аппаратные тесты в этом проходе не запускались.

**Файлы:** [src/flash.cpp](../src/flash.cpp), [src/flash.hpp](../src/flash.hpp).

**Зависимости:** System; flash_config.h и секторная карта, генерируемые из STM32-base_files. Рассматривается single bank; dual bank не предлагается к реализации.

## Список для обсуждения

### FLASH-1 — P1 — Новая запись помечается валидной раньше записи данных

**Место:** [src/flash.cpp](../src/flash.cpp), строка 157.

**Проблема:** write_data() сначала пишет DATA_OK, затем payload; предыдущую запись инвалидирует ещё до этого. Комментарий утверждает противоположное поведение при потере питания.

**Последствие / условие:** Питание пропало после DATA_OK: find_offset() примет незавершённые данные за валидные. Потеря питания после инвалидирования старой записи уничтожает единственную последнюю корректную версию.

**Возможное решение:** Согласовать простой commit-протокол: payload до отдельного признака готовности, старая версия сохраняется до commit новой. На ECC Flash каждый программируемый блок должен записываться допустимым способом; см. FLASH-3.

**Статус:** решение не принято, код в рамках этого обзора не изменён.

### FLASH-2 — P1 — Проверки вместимости позволяют читать и писать за концом сектора

**Место:** [src/flash.cpp](../src/flash.cpp), строка 138.

**Проблема:** Для текущего offset проверяется (offset+1)*stride, после чего offset увеличивается и пишется следующий слот. Проверка find_offset() использует > вместо >= и не проверяет вместимость полной записи перед чтением.

**Последствие / условие:** При offset=последний слот условие может быть ложным, но новая запись выходит в следующий сектор. Сканирование полностью заполненного сектора также может читать за границей.

**Возможное решение:** Проверять конечный адрес именно новой полной записи перед увеличением offset; сканировать только полные слоты. Проверять sector, data, size и переполнение расчёта stride до обращения к карте.

**Статус:** решение не принято, код в рамках этого обзора не изменён.

### FLASH-3 — P3 — Комментарий о перепрограммировании G0 слишком общий

**Место:** [src/flash.cpp](../src/flash.cpp), строка 148.

**Проблема:** Инвалидирование пишет целый doubleword нулями. Это разрешённое исключение в RM0444/RM0454 и само по себе не является ошибкой. Однако комментарий утверждает, что любая смена битов 1→0 всегда допустима, что для ECC Flash G0 неверно.

**Последствие / условие:** При дальнейшей правке commit-протокола можно ошибочно начать повторно программировать ненулевой статус в тот же блок.

**Возможное решение:** Описать допустимое исключение записи полного нуля. При исправлении FLASH-1 сохранять аппаратные ограничения ECC; отдельный ненулевой commit-маркер программировать в ранее стёртом блоке. Источник: [ST RM0444, §3.3.8](https://www.st.com/resource/en/reference_manual/DM00371828-.pdf).

**Статус:** решение не принято, код в рамках этого обзора не изменён.

### FLASH-4 — P1 — Программирование безусловно разрешает IRQ после выхода

**Место:** [src/flash.hpp](../src/flash.hpp), строка 99.

**Проблема:** write() вызывает __disable_irq(), а в конце __enable_irq(), не сохраняя исходную маску.

**Последствие / условие:** Если вызов сделан внутри существующей критической секции, метод неожиданно разрешит прерывания.

**Возможное решение:** Сохранить исходный PRIMASK и восстановить его после записи. Обсудить необходимость запрета IRQ на всю операцию, особенно при длительных записях; не вводить общий lock-фреймворк.

**Статус:** решение не принято, код в рамках этого обзора не изменён.

### FLASH-5 — P1 — Ошибка Flash не отражается в результате операции

**Место:** [src/flash.hpp](../src/flash.hpp), строка 91.

**Проблема:** write/erase/mass_erase возвращают void, ожидают только BSY и очищают ошибки до операции. write_data() безусловно ставит DATA_OK. enable_access() использует программный bool вместо проверки LOCK и не проверяет результат ключей.

**Последствие / условие:** Защита записи, ошибка выравнивания, ECC или неверный режим программирования воспринимаются как успешное сохранение.

**Возможное решение:** Возвращать простой статус с проверкой SR после операции и аппаратного LOCK после unlock. DATA_OK устанавливать только после успешного commit. Ожидания и источник их таймаута согласовать отдельно: SysTick не идёт при запрете IRQ.

**Статус:** решение не принято, код в рамках этого обзора не изменён.

### FLASH-6 — P1 — F7 кеши могут скрыть результат записи и стирания Flash

**Место:** [src/flash.hpp](../src/flash.hpp), строка 141.

**Проблема:** Программирование и erase не обслуживают кеш, хотя System включает D-cache/I-cache F7. read_data() использует обычный memcpy из Flash.

**Последствие / условие:** После модификации CPU может прочитать прежние кешированные данные; исполнение изменённого кода также требует согласованного I-cache обслуживания.

**Возможное решение:** После операции обслуживать затронутый диапазон Flash по правилам ядра/Flash accelerator. Разделить обычное хранение данных и перепрограммирование исполняемого кода; не очищать весь D-cache без необходимости.

**Статус:** решение не принято, код в рамках этого обзора не изменён.

### FLASH-7 — P2 — Контракт write<T>() допускает недопустимые адреса и источники

**Место:** [src/flash.hpp](../src/flash.hpp), строка 105.

**Проблема:** Не проверяется адрес/размер/выравнивание. G0 читает произвольный byte-buffer как const uint64_t*, что требует выравнивания/допустимого доступа к объекту. F4/F7 разрешён sizeof(T)==8 без проверки условий питания для такого PSIZE.

**Последствие / условие:** Невыровненный источник или запись вне Flash может вызвать fault; неподдерживаемая ширина даст ошибку программирования.

**Возможное решение:** G0 собирать doubleword через memcpy, проверять адрес 8-byte aligned и вместимость дополненного хвоста. Для F4/F7 разрешённую ширину увязать с VDD/VPP; базовый безопасный режим определить явно.

**Статус:** решение не принято, код в рамках этого обзора не изменён.

### FLASH-8 — P2 — Параметры стирания и bank API не полностью соблюдаются

**Место:** [src/flash.cpp](../src/flash.cpp), строка 60.

**Проблема:** Номер сектора добавляется через |= без предварительной очистки SNB/PNB. mass_erase(2) принимается, хотя MER2 закомментирован; init() в single bank возвращает true и для DUAL_BANK.

**Последствие / условие:** Унаследованное поле SNB/PNB может выбрать другой сектор; неподдерживаемый запрос банка завершается без ошибки.

**Возможное решение:** Заменять поле номера через маску. В текущей реализации принимать только single bank и возвращать ошибку для остальных запросов. Dual bank оставить вне объёма.

**Статус:** решение не принято, код в рамках этого обзора не изменён.
