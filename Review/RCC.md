# RCC / ClockSystem: проблемы и предложения

Дата: 12.10.2026. Проверена рабочая копия; сборки и аппаратные тесты в этом проходе не запускались.

**Файлы:** [src/rcc.cpp](../src/rcc.cpp), [src/rcc.hpp](../src/rcc.hpp).

**Зависимости:** System, Flash/PWR/RCC CMSIS; результаты используются GPIO-периферией, DMA, TIM, UART, SPI, I2C, ADC.

## Список для обсуждения

### RCC-1 — P1 — Неверная запись и проверка источника SYSCLK

**Место:** [src/rcc.cpp](../src/rcc.cpp), строка 132.

**Проблема:** Источник добавляется через |=, без очистки SW; ожидание проверяет лишь ненулевой SWS, а не требуемый источник.

**Последствие / условие:** Init(HSI) при уже выбранном HSI заканчивается таймаутом. При смене ненулевого источника можно получить другой SW либо принять старый SWS за завершённое переключение.

**Возможное решение:** Записывать только поле SW через маску; сравнивать SWS с кодом выбранного источника, с правильным сдвигом полей.

**Статус:** решение не принято, код в рамках этого обзора не изменён.

### RCC-2 — P1 — Расчёт частоты не соответствует ClkSrc

**Место:** [src/rcc.cpp](../src/rcc.cpp), строка 27.

**Проблема:** Без PLL sys_clk выбирается по HSE_Clk == 0. При включённой конфигурации PLL используется её выход даже когда ClkSrc обозначает HSI/HSE. G0 допускает LSI/LSE в enum, но отдельного расчёта и запуска этих источников нет.

**Последствие / условие:** Например HSI с ненулевым HSE_Clk объявляется частотой HSE; UART, SysTick и TIM получают неверные частоты.

**Возможное решение:** Расчёт и проверки строить по ClkSrc; отдельно согласовать разрешённые сочетания ClkSrc и PLLCfgr. LSI/LSE реализовать полностью либо исключить из поддерживаемого API.

**Статус:** решение не принято, код в рамках этого обзора не изменён.

### RCC-3 — P1 — Повторная настройка пытается отключить активную системную PLL

**Место:** [src/rcc.cpp](../src/rcc.cpp), строка 54.

**Проблема:** Перед очисткой PLLON нет перехода с текущей PLL на другой источник SYSCLK.

**Последствие / условие:** Повторный Init() на работающей PLL не сможет её выключить и вернёт ошибку после ожидания. Изменение коэффициентов нельзя выполнять на активной PLL.

**Возможное решение:** В RCC перед перенастройкой перейти на готовый HSI и подтвердить SWS. Ответственность оставить в RCC; System::Init() не должен сбрасывать PLL.

**Статус:** решение не принято, код в рамках этого обзора не изменён.

### RCC-4 — P1 — Flash latency кратковременно обнуляется до переключения

**Место:** [src/rcc.cpp](../src/rcc.cpp), строка 123.

**Проблема:** ACR latency сначала очищается, затем отдельной записью устанавливается. При снижении целевой частоты уменьшение выполняется, пока ещё работает прежняя высокая частота.

**Последствие / условие:** Повторное переключение вниз может нарушить допустимые условия исполнения из Flash; даже повышение включает промежуточную запись 0 WS.

**Возможное решение:** Сформировать latency одной записью поля. Повышать до увеличения HCLK; снижать после подтверждённого уменьшения HCLK. Расчёт вести от HCLK и допустимого напряжения, а не только SYSCLK/30 или /24.

**Статус:** решение не принято, код в рамках этого обзора не изменён.

### RCC-5 — P1 — Валидация PLL зависит от двух конкретных устройств

**Место:** [src/rcc.cpp](../src/rcc.cpp), строка 185.

**Проблема:** Проверки M/N/P/Q/R для F4/F7 включены только для F446 и F767. F407/F429/F746/F722 также заявлены в rcc.hpp, но до деления M и P их диапазоны не проверяются.

**Последствие / условие:** Нулевой M/P приводит к делению на ноль; неверные значения записываются в PLLCFGR.

**Возможное решение:** Общие проверки F4/F7 применять к каждой поддерживаемой модели; отличающиеся поля проверять по возможностям устройства. Проверять фактически используемые делители, без лишних требований к отсутствующему R.

**Статус:** решение не принято, код в рамках этого обзора не изменён.

### RCC-6 — P1 — InitCalcPLL() не рассчитывает требуемую частоту в общем случае

**Место:** [src/rcc.cpp](../src/rcc.cpp), строка 311.

**Проблема:** Алгоритм фиксирует P/R=2 и округляет вход к делителю около 2 МГц, а N — к req_freq/1 МГц. Реальный дробный вход не учитывается. На G0 с HSI получаются M=8 и вход 2 МГц, ниже собственных 2,66 МГц валидации.

**Последствие / условие:** G0 InitCalcPLL() от HSI отклоняется; HSE, не кратный 2 МГц, даёт частоту, отличную от запроса. Для ряда низких/высоких частот допустимые коэффициенты существуют, но не находятся.

**Возможное решение:** Небольшой перебор допустимых M/N/P или R с 64-битным расчётом частоты и явным правилом допустимой погрешности. Не выдавать приблизительный результат за точный.

**Статус:** решение не принято, код в рамках этого обзора не изменён.

### RCC-7 — P1 — Высокая частота не увязана с VOS и возможностями питания

**Место:** [src/rcc.cpp](../src/rcc.cpp), строка 70.

**Проблема:** F7 включает overdrive при SYSCLK >180 МГц, но VOS не устанавливает; F4 не содержит настройки питания для моделей/режимов, которым она нужна. LATENCY_DIV фиксирован независимо от питания.

**Последствие / условие:** Допустимость высокой частоты зависит от текущего диапазона напряжения и модели. Одних численных SYS/APB limits недостаточно.

**Возможное решение:** Для поддерживаемых моделей согласовать VDD/VOS и overdrive перед ускорением. Либо документировать обязательную подготовку пользователем и проверять условия. Таблицы брать из RM/datasheet конкретной модели.

**Статус:** решение не принято, код в рамках этого обзора не изменён.

### RCC-8 — P2 — InitTicks() после переключения игнорируется

**Место:** [src/rcc.cpp](../src/rcc.cpp), строка 154.

**Проблема:** Возвращаемое значение System::InitTicks() не проверяется. Во время перехода ожидания используют SysTick со старым reload, хотя HCLK уже изменяется.

**Последствие / условие:** InitOK не гарантирует рабочую миллисекундную базу; длительность позднего ожидания переключения может отличаться от заданной.

**Возможное решение:** Проверять InitTicks() и возвращать ошибку. В порядке перехода явно учесть временную частоту SysTick; без резервного таймера или подсчёта операций как миллисекунд.

**Статус:** решение не принято, код в рамках этого обзора не изменён.

### RCC-9 — P2 — Не все перечисленные MCU имеют согласованную поддержку

**Место:** [src/rcc.hpp](../src/rcc.hpp), строка 46.

**Проблема:** Внешний #if F4/F7 не имеет #else для неизвестной модели внутри списка лимитов; cpp и таблицы драйверов покрывают иные наборы устройств.

**Последствие / условие:** Для ряда F4/F7 отсутствуют SYS_CLK_LIMIT/APB limits, вместо обещанного ясного #error получается ошибка использования неопределённых имён.

**Возможное решение:** Зафиксировать список поддерживаемых MCU, добавить явную диагностику для остальных; новые лимиты и PLL особенности добавлять после проверки модели.

**Статус:** решение не принято, код в рамках этого обзора не изменён.

### RCC-10 — P3 — Комментарии и параметры не описывают фактический контракт

**Место:** [src/rcc.hpp](../src/rcc.hpp), строка 196.

**Проблема:** PLLCfgr описан как игнорируемый для HSI/HSE, но cpp это не делает. В G0 комментарии VOS упоминают 170 МГц; есть неиспользуемые timeout constants и закомментированные варианты питания.

**Последствие / условие:** Сложнее проверить порядок переключения и понять ограничения API.

**Возможное решение:** После решений RCC-1..RCC-9 привести комментарии и примеры к одному контракту, убрать устаревшие варианты. Не переносить сброс всего тактирования в System.

**Статус:** решение не принято, код в рамках этого обзора не изменён.
