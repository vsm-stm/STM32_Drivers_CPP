# ADC: проблемы и предложения

Дата: 12.10.2026. Проверена рабочая копия; сборки и аппаратные тесты в этом проходе не запускались.

**Файлы:** [src/adc.cpp](../src/adc.cpp), [src/adc.hpp](../src/adc.hpp), [src/adc_defs.hpp](../src/adc_defs.hpp).

**Зависимости:** System/GPIO, DMA, IRQ Registry, TIM; shared ADC common registers. Вопрос IrqLock исключён из нового списка по ранее принятому решению удалить его из ADC.

Отчёт учитывает выбранную модель: setup → addchannel → при необходимости DMA/trig → start → повторный start; callback при IRQ. Временные состояния и ограничения ниже предлагается обсудить, а не автоматически расширять архитектуру.

## Список для обсуждения

### ADC-1 — P1 — Отсутствуют зависимости публичного DMA/trigger API

**Место:** [src/adc.hpp](../src/adc.hpp), строка 360.

**Проблема:** DMA_Sx::RequestSet и вызываемые SetUp(cfg,req)/Release/GetTE_Flag/ClearTC_Flag/Cache* отсутствуют. TIM_TriggerGenerator вообще не объявлен в tim.hpp. В IRQ Registry отсутствуют HasHandlers и Unregister(irqn,this).

**Последствие / условие:** ADC не компилируется с текущим набором модулей даже если удалить прежние locks.

**Возможное решение:** Сначала согласовать минимальную связь с DMA/IRQ и форму trigger. Не создавать новый большой TIM API только ради типа в ADC: выбрать имеющийся TIM с явным trigger descriptor либо компактный согласованный интерфейс.

**Статус:** решение не принято, код в рамках этого обзора не изменён.

### ADC-2 — P2 — Текущая модель управления сложнее согласованной пользователем

**Место:** [src/adc.cpp](../src/adc.cpp), строка 169.

**Проблема:** BeginConfig/RunActive/RequestStop/FinishStop, Mode::Config, отмена поздних событий и adc_thread_context ограничивают control methods; Start() молча возвращается при Busy/ошибке и запрещает управление из IRQ.

**Последствие / условие:** Последовательность «повторить Start» не имеет прозрачного результата, а разрешённые контексты и состояния приходится восстанавливать по нескольким helpers.

**Возможное решение:** При отдельном разборе привести API к согласованной модели. Явно выбрать, что Start делает с активным запуском: перезапускает или возвращает Busy; результат не скрывать void. Ограничения необходимых blocking waits документировать, без новой thread/lock архитектуры.

**Статус:** решение не принято, код в рамках этого обзора не изменён.

### ADC-3 — P1 — CacheRxOk привязывает размер одной последовательности к 32 байтам

**Место:** [src/adc.cpp](../src/adc.cpp), строка 514.

**Проблема:** StartDMA(buf) проверяет bytes=_ch_count*2. Предполагаемый контракт CacheRxOk у потребителя требует целые 32-byte lines, но не знает фактической выделенной ёмкости буфера.

**Последствие / условие:** При таком контракте обычные 1..15 каналов F7 отвергаются, даже если buf выделен alignas(32) на 32 байта. Пока helper отсутствует, это подтверждённая несовместимость требований API, а не измеренный runtime result.

**Возможное решение:** Разделить число samples DMA и принадлежащий буферу cache span/ёмкость. Согласовать минимальный контракт выделения полного последнего line; не добавлять bounce buffers или отключение D-cache.

**Статус:** решение не принято, код в рамках этого обзора не изменён.

### ADC-4 — P1 — Circular DMA не передаёт CPU стабильную часть буфера

**Место:** [src/adc.cpp](../src/adc.cpp), строка 866.

**Проблема:** При TC circular DMA продолжает работу, handler инвалидирует весь _buf и вызывает callback на том же буфере. DMA уже начинает следующий круг; HT/половины не используются.

**Последствие / условие:** Callback/main может читать смесь двух последовательных кругов. Invalidate обеспечивает видимость памяти, но не останавливает запись DMA и не создаёт snapshot.

**Возможное решение:** Выбрать ownership: две части с HT/TC и отдельным aligned cache span либо остановка захвата на обработку. Определить допустимое время CPU обработки до повторного использования части DMA.

**Статус:** решение не принято, код в рамках этого обзора не изменён.

### ADC-5 — P1 — RequestStop считает DMA выключенным без подтверждения

**Место:** [src/adc.cpp](../src/adc.cpp), строка 714.

**Проблема:** Комментарий утверждает, что Stream_EN(DISABLE) ждёт остановки; текущая функция DMA этого не делает. Сразу очищаются flags и инвалидируется/освобождается буфер, _mode становится Idle.

**Последствие / условие:** Следующий start/config и CPU-чтение буфера могут пересечься с последней DMA записью. На G0 подтверждение остановки ADC отдельно отложено до будущего control call.

**Возможное решение:** Увязать остановку с реальным контрактом DMA-4 и не публиковать буфер как готовый раньше аппаратного завершения. Договориться об одном простом месте подтверждения остановки.

**Статус:** решение не принято, код в рамках этого обзора не изменён.

### ADC-6 — P2 — SetUp меняет общие настройки работающих ADC

**Место:** [src/adc.cpp](../src/adc.cpp), строка 209.

**Проблема:** ADC1 SetUp/ClearChannels выключают shared TSVREFE/VBATE; F4/F7 SetUp меняет общий ADCPRE без проверки активности других ADC.

**Последствие / условие:** При наличии нескольких ADC общий prescaler изменится во время чужой последовательности. Несколько объектов одного ADC также ничем не исключены.

**Возможное решение:** Либо зафиксировать единую настройку common ADC clock перед setup всех экземпляров, либо проверять изменение только при остановленных ADC. Владелец каждого hardware ADC должен быть один; не вводить отдельный manager без необходимости.

**Статус:** решение не принято, код в рамках этого обзора не изменён.

### ADC-7 — P2 — Внутренние каналы используют слишком короткий default sampling

**Место:** [src/adc_defs.hpp](../src/adc_defs.hpp), строка 152.

**Проблема:** F4/F7 default CH_SMPL=CYC_15, а AddChannel(INTERNAL) использует этот же default. Задержка после включения сенсора не увеличивает acquisition time каждого измерения.

**Последствие / условие:** При ADC clock PCLK2/4 acquisition ~15/f_ADC значительно короче указанного в header требования нескольких микросекунд для внутренних источников.

**Возможное решение:** Назначить документированный безопасный internal default для поддерживаемой модели либо потребовать явный sampling для внутренних каналов. Проверять по datasheet, не применять Delay_ms вместо достаточного sampling time.

**Статус:** решение не принято, код в рамках этого обзора не изменён.

### ADC-8 — P2 — Проверки контекста не гарантируют работающий SysTick

**Место:** [src/adc.cpp](../src/adc.cpp), строка 12.

**Проблема:** adc_thread_context проверяет IPSR/PRIMASK, но не запущенный SysTick и не BASEPRI. G0 waits и F4/F7 стабилизация используют GetTick/Delay_ms.

**Последствие / условие:** Control call из main до System::Init() или при маскировке SysTick через BASEPRI всё равно может зависнуть, несмотря на успешную проверку.

**Возможное решение:** В согласованной простой модели указать порядок System::Init() до ADC setup/start и требования blocking waits. Не расширять проверку контекста дополнительными регистрами, пока это не согласовано.

**Статус:** решение не принято, код в рамках этого обзора не изменён.

### ADC-9 — P3 — Возвраты и callbacks требуют более точного описания

**Место:** [src/adc.cpp](../src/adc.cpp), строка 348.

**Проблема:** При Busy некоторые AddChannel/ClearChannels вызывают DebugTrap, другие операции возвращают Busy/InitError, а Start() молча ничего не делает. DMA callback вызывается и при TE; ошибки конверсии OVR и DMA представлены разными способами.

**Последствие / условие:** Одинаковые неправильные последовательности по-разному останавливают программу; пользователь callback не отличает valid data от cancelled/error без чтения дополнительных полей.

**Возможное решение:** Согласовать единый способ ошибок и короткие комментарии по каждой операции. Сохранить простые callbacks; не добавлять hidden queues или threads.

**Статус:** решение не принято, код в рамках этого обзора не изменён.
